# 17 — Marketing & Loyalty

**Module spec — Draft 1, July 2026** · Parent: `00-platform-overview.md` (conventions §5–§7 inherited), `01-kernel-sync.md` (customer file 01-F23, event contracts). Concept doc §4.7. Wave 4; requires docs 06 (storefront) and 07 (WhatsApp) live.

## 1. Purpose & scope

WhatsApp broadcast campaigns, promo/discount campaigns, simple count-based loyalty, and an honest campaign-vs-lift view. The module rides entirely on assets that already exist — the org's customer file (01-F23) and the WhatsApp rail (doc 07) — and introduces **no new data capture**: every fact it uses or produces is a side-effect of selling or an ingestion from the messaging channel.

- **Who uses it:** owner or marketing role (campaign creation in back office doc 14; lift views in docs 12/14); customers (storefront doc 06, WhatsApp doc 07); POS staff only at coupon/reward application (doc 02).
- **Runs on:** cloud (`marketing` backend module + jobs) + back office UI; application surfaces are existing apps (POS, storefront).
- **Tiers/profiles:** all profiles; most valuable where own channels are active. Feature-flagged per org (Wave 4 rollout).
- **Explicitly NOT:** ad-platform integrations (Meta/Google), a full CRM segmentation builder, email marketing, points-currency loyalty with tiers/expiry.

## 2. Position in platform

- **Events consumed:** `customer.created / merged / address_added`, `order.created / channel_tagged` and settlement (`payment.recorded`), `discount.recorded`; WhatsApp delivery/read receipts and opt-out messages ingested via doc 07 webhooks.
- **Events emitted:** `campaign.*`, `loyalty.*` — added to the 01 §4 catalog by this spec (§5). `customer.opted_out / opted_in` are **owned and emitted solely by doc 07** (07-F18); this module only consumes the shared suppression read model. `discount.recorded` gains an optional `campaign_id` payload field (additive change under the same schema version, 00 §6).
- **Integrates:** doc 07 (template registry, send infrastructure, metering, opt-out ingestion), doc 02 + doc 06 (coupon/deal validation and application; campaign definitions arrive as reference data over the kernel channel, 01 §8), doc 12/14 (lift views), doc 13 (may narrate lift in the brief — this module owns the numbers, doc 13 owns the words).

## 3. Functional requirements

**Audience segments**
- 17-F1 Preset segment types only, parameterized: `all_opted_in`; `lapsed` (no settled order in N days, default 30); `top_spenders` (top N by trailing 90-day spend); `channel` (ordered via channel C in trailing M days); `frequency` (≥ K settled orders in M days). A free-form segmentation builder is explicitly out of scope.
- 17-F2 Segments are stored definitions evaluated at send time — never static lists; every evaluation is logged with its resulting count and parameters. Preset parameters and bounds:

| Segment type | Parameters (Layer 2, within bounds) | Default |
|---|---|---|
| `all_opted_in` | — | — |
| `lapsed` | N days since last settled order (14–90) | 30 |
| `top_spenders` | top N by trailing 90-day spend (10–500) | 50 |
| `channel` | channel C, ordered in trailing M days (7–90) | 30 |
| `frequency` | ≥ K settled orders in M days (K 2–20, M 7–90) | 5 in 60 |
- 17-F3 A segment can only ever include customers whose opt-in status (doc 07 registry) permits marketing messages. This filter is applied inside the send path, not left to the campaign author.

**Broadcast campaigns**
- 17-F4 A broadcast campaign = WhatsApp-approved template (doc 07 registry) + segment + schedule window + optional attached promo (17-F10/F11). Draft → active → completed/paused lifecycle, all state changes evented.
- 17-F5 Opt-out is honored absolutely: checked per recipient at send time; an opt-out message (recognized variants, Urdu included) ingested by doc 07 takes effect immediately and permanently unless the customer explicitly re-opts-in. No role can override; no exception path exists in code.
- 17-F6 Per-org send metering: Layer 1 daily/monthly caps plus WhatsApp tier limits enforced in doc 07. When capped, sends throttle or halt and the campaign shows sent/pending/capped counts honestly — messages are never silently dropped.
- 17-F7 Delivery and read statuses from WhatsApp webhooks are attached to the send log (`campaign.message_status_ingested`). *(Ingestion.)*
- 17-F8 Quiet hours: broadcasts send only inside a platform-preset local-time window (default 11:00–21:00); a campaign scheduled across the boundary pauses and resumes. Not org-overridable beyond the preset bounds.
- 17-F9 Campaign completion produces a summary on the campaign record: audience count, sent/delivered/read, coupons redeemed, attributed orders/revenue, total discount value — the raw material of the lift view (17-F19).

**Promo / discount campaigns**
- 17-F10 Coupon codes: shared code or unique per-customer batch; constraints: validity window, channel scope, item scope, minimum order value, single-use or single-use-per-customer. Codes are short, uppercase, with a checksum character for typo detection at POS.
- 17-F11 Automatic deals: no code — time-window + channel + item scoped (e.g. "Tuesday 20% off karahi, storefront only"), applied automatically at POS/storefront when conditions match.
- 17-F12 Every promo application emits `discount.recorded` with `campaign_id`. Campaign discounts are pre-approved by the campaign definition: within its bounds, no manager PIN is required at POS (interplay with doc 02 approval thresholds); outside its bounds the normal threshold rules apply untouched.
- 17-F13 Offline validation: campaign definitions and shared codes validate from synced reference data with no cloud round-trip. Single-use enforcement is merge-checked: duplicate redemption across partitioned devices is append-and-merge (01-F20) — both stand, the duplicate is flagged to the manager and marked in the campaign report. A sale is never blocked by coupon arbitration.

**Loyalty (simple)**
- 17-F14 Count-based only: "every Nth order → reward" (free item or % off), one active program per org. Deliberately absent: points currencies, tiers, expiry mechanics.
- 17-F15 Progress is derived from settled orders on the customer file — org-wide, all channels, ~~no punch cards,~~ no manual adjustment. ~~Crossing the threshold emits `loyalty.reward_earned`.~~ *(Derived from side-effects; nothing to capture.)* **AMENDED August 2026, twice, and each half points at the ruling that won.** **(i) The punch-card ban is OVERRULED by founder ruling R79 — see `17-F21`.** The ban was written against a second *progress mechanism* (a counter a human can stamp), and that reading is preserved verbatim and is what the surviving clause still forbids: for **account** loyalty, derived progress remains the only mechanism — no manual stamp, no adjustment, no counter anyone can type into. A bearer card is a campaign **kind** and not a progress mechanism, which is why the amendment is this narrow: written any wider, the FR's real protection (*nobody can hand-edit a loyalty balance*) is lost. **(ii) `loyalty.reward_earned` is WITHDRAWN from the `01 §4` catalog — see `17-F23`.** This clause said progress is *derived* and then said crossing the threshold *emits*, and a derivation is not an act: every device would compute the crossing independently, so either all of them emit or one does and the others do not, and either way a projected value would depend on which device folded first — standing law 1's break (`01-F34`). `17-F23`'s arithmetic makes the event unnecessary rather than merely unbuilt, and an event nobody can legitimately emit is worse than a missing one. The name is retained in this prose for the audit trail, on `07-F7`/`07-F18`'s precedent for `whatsapp.optin_recorded`.
- 17-F16 Balance visibility: on the storefront (phone-keyed lookup) and in WhatsApp order notifications ("2 more orders to your free deal") via doc 07 templates.
- 17-F17 Redemption at POS or storefront is an attributed discount event: `discount.recorded` (with campaign/program ref) + `loyalty.reward_redeemed`. POS flow: customer phone lookup → reward visible → apply. Redemption resets the counter by event, append-only. **AMENDED August 2026 — *"resets the counter"* is superseded by `17-F23`'s `orders_consumed`, and the two are not the same idea.** A reset is sequence-dependent (it means *everything before this point stops counting*, which needs a before); consuming `N` is the same fact stated as arithmetic, and it survives `N` changing — a redemption taken at `N = 10` consumed ten orders and goes on consuming ten forever, exactly as `01-F53` freezes a price and `01-F85` snapshots a tender's posture. That is what stops an owner moving `N` from 10 to 8 and silently re-awarding every customer in the org, permanently, in a ledger `01-F1` forbids correcting.

**Campaign-vs-lift view**
- 17-F18 Attribution rule (fixed, printed on every report): an order is campaign-attributed if (a) it carries a `discount.recorded` with that `campaign_id`, or (b) the ordering customer received that campaign's broadcast within the attribution window (default 7 days) before the order. An order attributable to multiple campaigns counts once, assigned to the most recent qualifying campaign (§9.4).
- 17-F19 Lift view (read model, surfaced in docs 12/14): attributed orders/revenue during the campaign window vs baseline = the same segment's trailing 4-week same-weekday average; total discount value given is shown alongside so the owner sees cost, not just lift.
- 17-F20 Honesty gating (design law 6): with insufficient baseline history the view states "not enough history to compute lift — showing raw campaign totals" rather than a fabricated comparison.

**Loyalty forms, the campaign carrier and the approval predicate (August 2026 — founder rulings R71 and R79)**
- 17-F21 **THREE LOYALTY FORMS, AND A BEARER CARD IS A CAMPAIGN *KIND* RATHER THAN A SECOND PROGRESS MECHANISM (founder ruling R79; overrules `17-F15`'s punch-card ban).** `17-F15` banned punch cards **by name** and the founder asked for them **by name** — *"some restaurants want to really use card stamping, some might prefer our system"* — so the ban is overruled and the reason is recorded rather than the ban quietly deleted. **They are not the same object, and collapsing them is how this gets built wrong:**

| | **Account loyalty** (`17-F14`/`17-F15` as written) | **Bearer card** (the founder's coffee shop) |
|---|---|---|
| Identity | `01-F23`'s phone key | **the card itself** — no customer record at all |
| Progress | derived from settled orders in the ledger (`17-F23`) | physical stamps on paper, invisible to us |
| Needs `02-F64`'s order→customer link | **yes** | no |
| Fraud model | replay/partition — solvable, and `17-F13` already rules it | forgery + photocopy — **not** solvable at the till (`17-F25`) |
| Serves a walk-in who gives no number | no | **yes** |
| What the ledger can verify | everything | **nothing** — it records an attestation |

  - **A coffee shop's printed card works precisely *because* it asks nobody for a phone number at 08:00**, and account loyalty cannot serve that customer; a bearer card cannot serve the phone-order customer who never touches paper. So both ship, they share one event vocabulary and one campaign model (`17-F22`), and **they differ in exactly one field**: a redemption's `phone_e164` is present for `account_loyalty` and **`null`** for `bearer_card`. `null` is a stated fact and `undefined` is a writer who forgot, on `registry.ts`'s standing rule for `customer.created.name`.
  - **A bearer redemption carries `orders_consumed: 0`** — no account counter moves, because the counter was paper. That is not a special case in the fold: `17-F23`'s sum is over a unique-keyed map and a zero member contributes zero, so the same arithmetic serves both forms with no arm keyed on the kind.
  - **Serialized or plain is the ORG's choice and neither is specified here**, because the two differ in what a report can say and not in what the ledger holds: a serialized card (a printed number the cashier keys into `proof_ref`) makes a duplicate detectable at merge — exactly `17-F13`'s coupon shape — and a plain card makes a photocopy **indistinguishable from the real thing forever**, whose only controls are the physical card in the drawer and `17-F25`'s statistical report. Both are `proof: bearer_card` on `17-F22`'s row; the serial rides `proof_ref` and its absence is the plain card.
- 17-F22 **CAMPAIGN DEFINITIONS ARE CONFIGURATION, AND THEIR CARRIER IS A FIFTH `01-F75` RESOURCE NAMED `campaign` (org-scoped).** `17 §3`'s own automation-law register classifies *"Campaigns, segments, loyalty program definitions"* as **configuration, not facts**, and `17 §7` puts them at **layer 2 (org)** — so the corpus had already answered the two hardest questions about them and this FR reads that answer rather than inventing one.
  - **The row, typed and validated at the WRITER** (`01-F75`: *"`entries[]` is typed PER RESOURCE and validated at the WRITER, never only at the device"*, because one unparseable member refuses the entire update under `01-F56`): `campaign_id` (org-unique, minted at the writer) · `kind` (`auto_deal | coupon | bearer_card | account_loyalty`, **CLOSED at the writer**) · `status` (`active | paused | completed` — a departure is a MARK and never an absence, `01-F75`'s own rule for every resource) · `valid_from` / `valid_to` (business-day bounds, Asia/Karachi 05:00 per `01-F46`) · `branches` (`null` = whole org, else branch ids — the branch axis as DATA, `01-F60`'s precedent) · `channels` (subset of `02-F42`'s `ORDER_CHANNELS`; empty = every enabled channel) · `item_scope` (`null` = whole order, else catalog entry ids, `01-F21`) · `min_order_paisa` · `benefit { form: percent_bps | amount_paisa | free_item, value, cap_paisa }` · `proof` (`none | code | bearer_card | attested`) · `code` (`17-F10`'s uppercase base32 + one check character, unchanged) · `use_limit` (`unlimited | once_per_order | once_per_customer`) · `requires_customer` · `every_n` (`account_loyalty` only).
  - **Money obeys `DEC-MONEY-005` without exception:** a percentage is integer **basis points**, a cap is integer **paisa**, computed with `applyRateBps` and then `min(cap)` — never a float and never a division. `benefit.form: free_item` resolves through the catalog and yields the LINE's own snapshotted `unit_price_paisa` (`01-F53`), so a free coffee is worth what the coffee was rung at and not what the menu says today. **AMENDED August 2026 (adversarial review): `percent_bps` is bounded at 10,000 at the WRITER, and the bound is a refusal rather than a clamp.** The row carried five `superRefine` arms and no upper bound on the rate, so a seed typo of `500000` for `5000` parsed clean — and because `17-F24` makes a within-bounds citation pre-approved *regardless of magnitude*, the resulting benefit is `min(gross, base)` = **the whole bill, with no manager, permanently** (`01-F1`). 10,000 bps is 100%, which is the largest discount that can exist: a benefit can never exceed what it is taken off (`01-F30` has no room for a negative total). It is refused rather than clamped for `01-F75`'s stated reason — a writer that published 5000% did not mean 100%, and honouring a number nobody typed is how a bad row becomes invisible.
  - **WHY A FIFTH RESOURCE AND NOT A KEY INSIDE `config` — the argument is `01-F87`'s own rule turned on itself.** `01-F87` (b): *"An UNKNOWN key is ignored; a **MALFORMED known key refuses the whole artifact**."* A campaign set is owner-authored, unbounded in cardinality and edited weekly, so riding it inside `config` means **one bad campaign row refuses the org's tax posture, its charge-rounding granularity and its discount threshold at every till**. `01-F87` argues its own carrier's size explicitly (*"the whole of layer 2 is a handful of scalars and two small tables"*) and campaigns are neither. A separate resource keeps `01-F56`'s `malformed` scoped to the thing that was malformed. **The act is an amendment to `01-F75`'s closed-set clause — TAKEN, August 2026.** ⚠ **`01-F75` also demands *"its own golden fixture"* and THAT HALF IS OWED, stated here rather than left to look done.** `20 §2.7`'s fixtures are `packages/sync-protocol`'s and pin a message KIND, and this resource adds none — it rides the existing `reference_request` / `reference_response` / `reference_notice` triple. So the fixture is owed **with the wire arm**, in the same change, and until then `campaign` is in exactly the state `01-F87`'s `config` has been in since it joined the set: **spec-closed and wire-owed**. A pilot device gets its campaigns as a v0 seed (`plans/v0.md` gap 3 names the tax cell, R70's rounding granularity and R71's campaigns together, and says `01-F87`'s carrier deletes all three at once). **An earlier draft of this clause said the fixture had been written; it had not, and the correction is recorded rather than quietly applied** — a spec sentence claiming a deliverable exists is read by the next session as a deliverable that exists, which is the same failure mode `L11` records for a shipped comment.
  - **Everything else is inherited and costs ZERO new message kinds:** the `reference_request` / `reference_response` / `reference_notice` triple, `01-F71` (e)'s serve-path enforcement (the key comes from the session; a stated one is refused, never clamped), `at_version`-is-a-continuation, `have_version` deltas carrying one entry per changed id at the greatest version ≤ target, `01-F56`'s monotonic apply, `01-F76`'s device-side `foreign_artifact` refusal, and `01-F75`'s named-producer rule. `form: "snapshot"` may be the only form this resource ever answers, and `01-F75` makes that legal rather than a gap. **The artifact carries no credential and no PII**, so `01-F87`'s org-scope reasoning transfers intact and `01-F81`'s signature question is not re-opened.
  - **One consequence for `17-F10`: unique-per-customer coupon BATCHES do not travel in the artifact.** A phone→code table on a till is exactly the credential-shaped blast radius `01-F76` scopes `staff` to a branch to avoid. The artifact carries the batch's *rule*; the code itself is the bearer token, checksum-validated offline and arbitrated at merge (`17-F13`).
  - **TWO NAMED REFUSALS, so a later reader does not read them as omissions.** There is **no `budget_paisa` and no `max_redemptions`**: an org-global cap is a *distributed* limit, and enforcing one offline would either block a sale (Commandment 4, `01-F17`) or be a number that is always wrong — `17-F13` already rules the shape (append, merge, flag, never block), and a cap that can only be reported after the fact must be presented as a **report** and not as a control. And there is **no `effective_at`**: `01-F75` specifies no scheduling field and `01-F87` puts application time on the **act**, so a second field would be a second answer to one question.
  - **This closes `28 §9.25`, which doc 28 routes to doc 17 by name.** `28-F7` excludes marketing/loyalty from entitlement and names the shape it suspects — *"if a disabled module publishes no campaign reference data the branch-side absence is total"* — and with campaigns as their own resource that shape is exact and needs no flag: `01-F77`'s omitted-never-zero rule already makes an org that has published no campaigns **indistinguishable** from a gateway that does not serve the resource, because in both cases the device simply never asks. So there is no enablement bit to distribute, no cache, no TTL, no staleness policy, and nothing commercial anywhere near `01-F17`'s sale (`28-F8`).
  - **Offline, and `17-N3`'s 100 ms:** the till holds the artifact and validation is a synchronous read of its own store — no WAN, no hub, no clock and no ordering metadata, on the pattern `DEC-MONEY-009`'s settlement guard already ships. A device that has never received the artifact has **no campaigns**, which is the safe direction and never blocks a sale. ⚠ **The market's answer is the one we must not copy:** Square Loyalty requires points from offline payments to be manually linked after reconnect; `17-F13` rules the opposite and Commandment 4 forbids it.
- 17-F23 **THE LOYALTY COUNTER IS ARITHMETIC, NEVER A SEQUENCE — the fold projects two counts and the division happens at RENDER TIME.** *"Every Nth order → reward"* reads as a sequence, and a sequence is illegal twice over: `01-F34` forbids a fold reading **any** ordering metadata, and `01-F87` forbids a fold reading configuration at all — so a fold may neither order the orders nor divide by `N`. One move satisfies both.
  - **The projection, per `phone_e164`** (a device fold; the projected fields and their merge rules are declared per `01-F34`): `linked_orders` — a **G-set** of `order_id`s carrying `02-F64`'s link to this phone, each holding whether an `order.settlement_closed` has arrived and that act's **attested** `billed_paisa` (`01-F63`'s snapshot — a payload value, never re-derived). Set membership is commutative, idempotent and order-free, and duplicate delivery collapses. `redemptions` — a **unique-keyed map** by `adjustment_attempt_id` (`01-F31`/`01-F83`) → `{ campaign_id, orders_consumed }`; members diverging in any field mark the key **disputed**, contribute **zero**, raise an anomaly and are all retained, and a fold never picks a winner. `orders_consumed_total` — Σ of that map's `orders_consumed`, accumulated in **BigInt** (standing law 3: a running double lets delivery order decide an outcome). `exceptions` — a sorted G-set; `loyalty_overdrawn` when `orders_consumed_total` exceeds the eligible count.
  - **The rendering, which reads the campaign artifact freely** — `01-F87`'s explicit carve-out for a value computed at display time, whose shipped precedent is `03-F14`/`03-F47`'s aging thresholds in the pass screen's badge: `eligible = |{ o ∈ linked_orders : o.settled ∧ o.billed_paisa ≥ campaign.min_order_paisa }|` and `available = floor( (eligible − orders_consumed_total) / campaign.every_n )`.
  - **⚠ THE RENDER MUST NOT SHOW A CLAIMABLE COUNT WHILE NOTHING CAN CONSUME ONE — August 2026 (adversarial review), and this is `00 §5.7` applied to a number rather than to a link.** `available` is `floor((eligible − orders_consumed_total) / every_n)` and `orders_consumed_total` moves only on `loyalty.reward_redeemed`, which **no surface in this product emits** (`17-F17`'s *"→ apply"* has no producer). So the subtrahend is structurally zero and the counter only ever goes UP: measured at 50 settled linked orders it read **5 rewards to claim** with `orders_consumed_total` `"0"`, and a regular who had already taken five free coffees is presented to the cashier as owed five more, climbing for the life of the ledger. `use_limit: once_per_customer` bounds nothing, because `17-F22`'s row is not read by the counter. **Until a redemption producer exists the reward line states the fact and NAMES the degradation** — the threshold has been passed, and this till cannot record a redemption — **and renders no count.** The countdown below the threshold is unaffected and correct, because a customer who has redeemed nothing has consumed nothing. **The day a producer lands, the count comes back**; the tripwire that says so is a hand-written assertion, because no rail can see a missing producer for an event type.
  - **⚠ THE BREAK IS ONE KEYSTROKE AWAY AND `01-F87` NAMES IT: memoizing that rendering into a materialized state table.** At that moment the value stops being recomputed per read and becomes a *projected* one, and two tills holding different artifact versions project different rewards from an identical event set. **The counter is a render.** This must be written at the code, not only here.
  - **Why `orders_consumed` and not a reset:** see `17-F17`'s amendment. A redemption consumes `N` **as `N` stood when it was taken**, permanently.
  - **Partition is `17-F13`'s ruled disposition and not a new one.** Two tills each see ten eligible orders and zero consumed; both redeem. On merge the set holds ten and consumed is twenty, `available` goes negative, `loyalty_overdrawn` is raised for the manager surface, **both discounts stand**, and no sale was ever blocked (`01-F17`, `01-F20`). Detection is a predicate over the delivered set, so it is order-free too.
  - **What can and cannot count.** `17-F15` says org-wide, all channels. Measured: `08-F2` has aggregator orders reach settlement **writing no customer file at all**, so a foodpanda order cannot be linked and therefore cannot count — the question answers itself today, and it becomes a real one (a discount on an order the aggregator already discounted) only if doc 08 ever links them.
  - **`loyalty.reward_earned` is WITHDRAWN** — see `17-F15` (ii). Nothing emits it, nothing may, and `17-F16`'s *"2 more orders to your free deal"* is a rendering of these same two counts.
- 17-F24 **CAMPAIGN DISCOUNTS ARE PRE-APPROVED BY THE CAMPAIGN DEFINITION — `canDiscount` GAINS A CAMPAIGN ARM (founder ruling R71, routing `17-F12`'s predicate).** R71 does not invent a mechanism; `17-F12` has said since Draft 1 that *"campaign discounts are pre-approved by the campaign definition: within its bounds, no manager approval"*, and R71 makes that live by **routing the predicate**.
  - **The arm.** A discount citing a campaign whose scope matches the order and whose computed amount is **within** the campaign benefit's `cap_paisa` takes the `order.discount_within_threshold` row **regardless of magnitude** — that is the whole of R71's *"50% off if you use Visa Signature with a cap of 10,000pkr"* case. Outside its bounds it falls through to the discretionary predicate **untouched**, which is `17-F12`'s own last clause.
  - **⚠ WHAT THE ARM CAN AND CANNOT RESOLVE — AMENDED August 2026 (adversarial review), and the amendment is a REFUSAL rather than a feature.** `17-F22`'s row carries three fields the pre-approval predicate cannot evaluate from an order total alone, and the first shipped implementation read none of them while still answering *within bounds*: **`item_scope`** (the base is then the scoped lines' total and not the order's, so a *20% off pizzas* campaign pre-approved 20% of the whole bill — measured at **20× the intended bound** on a Rs 10,000 order carrying one Rs 500 pizza), **`use_limit`** (`once_per_order` / `once_per_customer` need a count of prior citations, which the predicate has no input for — measured: one citation repeated 50 times, all within bounds), and **`proof`** (`code` / `bearer_card` / `attested` name something the cashier must be holding, and nothing collects it — a coupon was pre-approved with no code). **A campaign whose row sets any of the three does not take this arm at all: the citation resolves to `null` and the discretionary predicate runs untouched**, which is `17-F12`'s own last clause and is exactly the exit `free_item` already takes for the same reason — *a bound this predicate cannot compute is not a blessing*. The consequence is that a large scoped, limited or proof-carrying discount asks for a manager, which is the safe direction and the honest one. **The class this closes and the one it does not (`L11`):** it closes *the arm blessing an amount it never bounded*; it does **not** implement any of the three — an item-scoped campaign is refused, not scoped, and whoever builds the scoped base, the use counter or the proof capture removes an arm here rather than adding one.
  - **NO NEW PERMISSION ACTION, and this is a decision rather than an omission.** The money outcome is identical to a within-threshold discount, and `02-F47`'s reasoning binds: two actions whose cells are identical differ in nothing an implementation can observe. `loyalty.reward_redeemed` is authorized by the same act as the `discount.recorded` it accompanies, on `02-F47`'s one-action-for-both precedent.
  - **THE CUMULATIVE BASE IS DOC 02'S AND IS NOT SPECIFIED HERE.** R71's other half — *"consider the discount cumulatively … owner should be able to set a percentage after which Manager's approval is required"* — is a change to the discretionary predicate's BASE, which `02-F20` owns; this FR neither states it nor depends on it. ⚠ **The two halves interact and the interaction is the point of the ruling:** a 50% cumulative cap would otherwise make the *second* bank promo on one order escalate, which R71 calls the outcome the founder called stupid, and it only dissolves because campaign discounts **do not count against the discretionary running total**. So whoever builds the cumulative base must exclude campaign-cited discounts from it, and that exclusion is stated here because it is a property of this arm.
  - **⚠ A FOLD MAY BRANCH ON THE PRESENCE OF `campaign_id`, NEVER ON ITS VALUE.** `01-F85` bans a fold arm keyed on an owner-typed id, because a renamed tender would change a projected value. Presence is not value — renaming a campaign changes nothing a fold sees — and the distinction is load-bearing precisely here, because the cumulative running total must *partition* campaign discounts, which means it must read that field. **Write the distinction down at the fold, or the next reader deletes the arm citing `01-F85`.**
  - **Campaign authoring in the back office needs `14-F43`'s `config.manage`** (owner-only, spec-closed and code-owed), because campaigns are configuration by `17 §3`'s own register. **This FR mints no action.** `services/api` refuses at boot to host an ungated procedure, so the authoring surface cannot be booted until `14-F43` lands — a dependency, not a blocker to route around.
- 17-F25 **A REDEMPTION RECORDS AN ATTESTATION, NOT A VERIFICATION, AND THE FR SAYS SO OUT LOUD.** The founder's concern is a procedural one — *"would also be very bad if the person at reception have to ask Manager's approval for things which can simply have proof attached like the card with receipt"* — so the ledger's job here is to record what the cashier held in her hand, and to be honest that it cannot check it. Three fields on `loyalty.reward_redeemed`, each answering a different question a reviewer will ask: `campaign_id` + `campaign_version` answer *under what rule?*; `proof_kind` + `proof_ref` answer *what did she hold?*; and the envelope's `actor_user_id` answers *who attested?* — already there under `02-F41`/`02-F45`, and **never** copied into the payload.
  - **The physical half is what makes it auditable and it is a procedure, not code:** the surrendered card staples to the receipt copy, and the end-of-day report says *"6 bearer redemptions recorded on this till"*. Six cards in the drawer against six rows is a reconciliation a branch manager can do in ten seconds without having been present.
  - **The honest limit, stated because a design that hides it will be trusted too far:** attestation without verification means a cashier can give a free coffee to a friend and record a card that never existed. **The control is statistical and after the fact** — a cashier whose redemption rate is three times the branch's — and never preventive. **R77's vocabulary discipline binds here exactly as it does for stock:** the report says *unmatched redemptions*, and the words **shrinkage, loss, theft, missing** are banned; every alert is on a sustained same-signed run and never one day, because measurement error is zero-mean and flips while a pattern does not.
  - **The alternative is refused with its argument recorded:** a manager PIN on every campaign redemption is exactly what the founder called bad and what R71 ruled against, and `02-F46`'s own argument applies unchanged — `27-F11e` makes a branch with no manager on the floor the common deployment, so a control whose only holder may not be in the building is a control that does not exist.
- 17-F26 **WALLET PASSES (Apple/Google) ARE A THIRD BEARER FORM — COSTED HERE, DELIBERATELY NOT BUILT (founder ruling R79).** *"There is another google/apple wallet based system. we want that as well."* A wallet pass is **bearer-shaped**, exactly like the printed card: the pass IS the identity, the customer needs no account with us, and the till verifies nothing it can trust. That is why it is the same `17-F22` campaign kind rather than a fourth model, and it is the whole of what this FR decides.
  - **⚠ THE ISSUANCE HALF IS A GENUINE PLATFORM INTEGRATION AND IS NOT STARTED.** **Apple Wallet** needs a pass-type identifier registered on an Apple Developer account, a pass-signing certificate and the WWDR intermediate, a `pass.json` + manifest signed per pass, and — for a stamp to appear without the customer reopening anything — a web service implementing Apple's registration/update endpoints plus APNs push. **Google Wallet** needs a Google Wallet API issuer account, a class and per-object definition, and a **signed JWT** for the save link, with updates pushed through the REST API. Both therefore need a cloud-plane service holding a **signing credential**, which is a new secret with a rotation story and an expiry (Apple's certificate expires annually and every issued pass stops updating when it does).
  - **What this FR does NOT decide, so that nobody reads a name as a promise (`01-F81`'s rule):** which plane hosts issuance, how a pass is bound to a campaign version, what a revoked or expired pass does at the till, and whether a pass carries a serial the cashier can key into `17-F25`'s `proof_ref`. **No wire kind, no event type and no artifact field is minted for it here.** The `01-F75` artifact carries campaign *rules* and no credential, and that must stay true when this lands (`17-F22`).
  - **What it inherits for free the day it is built:** `17-F22`'s row, `17-F24`'s pre-approval, `17-F23`'s arithmetic and `17-F25`'s attestation — because a wallet pass redeemed at the counter is a `bearer_card` redemption whose `proof_ref` happens to have been read off a phone.
- 17-F27 **A CAMPAIGN DISCOUNT IS CITED BY THE CASHIER, AND ITS `campaign_version` IS STAMPED BY THE WRITER (August 2026; the producer `17-F24` assumed and no FR required).** `17-F24` routed `17-F12`'s predicate and `registry.ts` declared `campaign_id` / `campaign_version` on `discount.recorded` — and **nothing anywhere in the product produced either field**, so the arm was unreachable from the shipped binary: measured comment-blind and symbol-precise across every renderer, the back office, the manager and owner apps and `services/api`, the only shipping producer of `discount.recorded` built a payload of five literal fields and `campaign_id` was not among them. That is `L8`'s recurring defect in the shape `pnpm seams:check` says out loud it cannot see — **a missing producer for a payload key** — and it is why this FR exists at all.
  - **(a) The offer list is computed on the TRUSTED side and is a display-only read.** The till answers *which campaigns reach THIS order* from its own `17-F22` artifact, through the **same resolution** `17-F24`'s citation uses — one function, not two, on `02-F45`'s argument: two resolutions of one question disagree, and here the disagreement is a cashier offered a campaign the write guard then refuses. The read authorizes nothing (`02-F20`'s `escalationFor` precedent), so a renderer that forged the list gains nothing; every fact that decides the verdict is re-read at the writer (Commandment 8).
  - **(b) The cashier CITES; she does not compute.** The correction surface (`02-F61`) offers one tile per reaching campaign, carrying the campaign's own id and the bound it allows, and the citation travels on the payload as `campaign_id`. **No offer is auto-applied and no amount is derived from a tile**, because `01-F30`'s discount is per line and the campaign's base is the order — resolving one into the other is the scoped-base problem `17-F24`'s amendment refuses, and a tile that silently clamped would be that refusal undone at the surface. The tile is a citation, the amount stays the operator's, and `17-F24` decides whether the pair is pre-approved.
  - **(c) `campaign_version` is taken off the DEVICE's artifact at the writer, never from the payload.** `17-F25` makes the pair answer *under what rule?* years later, and a version the renderer supplied answers it with a number no publisher minted. The writer stamps it — overwriting whatever arrived — for exactly the campaign the artifact holds. **A cited campaign this device's artifact does not hold cannot be paired, so the claim is DROPPED rather than recorded:** the authorization already fell through to the discretionary predicate (`17-F24`), so a payload naming a rule this device cannot state would make `17-F25`'s question permanently unanswerable (`01-F1`) while the verdict said discretionary. Same division as `01-F23`'s phone key: validate the VALUE in `registry.ts`, put the POLICY at the writer.
  - **⚠ Why the pairing is NOT a `superRefine` on the payload schema, restated because a reader will reach for it first:** `parseEvent` runs over the FULL ledger at store open, so a retroactive tightening is a till that will not start, on every launch, permanently (`01-F1`, `01-F17`). `registry.ts` records the two green oracles that caught that. This FR is what makes that file's *"enforced at the WRITER, structurally"* claim true — **it was false when written**, and a protection claimed in prose retires the assertion the next session would have written (`L11`).
  - **What this FR does NOT build, named so the arm is not read as complete.** It mints no permission action (`17-F24` decided that). It does not link an order to a customer that was not linked at `startOrder` (`02-F64`'s cheap half is still unbuilt), so a `requires_customer` campaign reaches only a phone order. It produces no `loyalty.reward_redeemed` — see `17-F23`'s render amendment — so an `account_loyalty` reward is still not claimable through any surface. And the offer tile shows the `campaign_id` itself, because `17-F22`'s row carries **no display name** and inventing one here would be a field no FR asked for (Commandment 2); a name belongs to the authoring surface `17-F24` routes to `14-F43`.

## 4. Key flows

**Flow A — Broadcast campaign lifecycle**
1. Marketer drafts in doc 14: template (from the doc 07 approved registry) + segment + schedule window; optionally attaches a coupon batch or deal.
2. Activation validates the template status and metering headroom; campaign → active, `campaign.activated`.
3. At the send window, the job evaluates the segment (17-F2), then filters through opt-out (17-F5) and metering (17-F6).
4. Doc 07 sends, throttled to tier limits; each send logged (`campaign.message_sent`).
5. Delivery/read statuses arrive via webhook and attach to the send log (`campaign.message_status_ingested`).
6. The lift view starts populating from the first attributed order.
7. *Failure — template rejected by WhatsApp:* campaign blocked at draft with the reason shown; nothing sends.
8. *Failure — cap hit mid-send:* remaining recipients shown as capped, honestly; resumes at the next window; never silently dropped.

**Flow B — Coupon at POS (incl. offline)**
1. Cashier enters the code; checksum catches typos before any lookup.
2. Validation against locally synced campaign reference data — offline OK, < 100 ms (17-N3).
3. Constraints checked (window, channel, min order, item scope); discount applied without manager PIN within campaign bounds.
4. `discount.recorded` with `campaign_id` persists locally and syncs.
5. *Duplicate redemption across partitioned devices:* both events stand at merge (01-F20); the duplicate is flagged to the manager and marked in the campaign report; the sale is never unwound.

**Flow C — Loyalty earn and redeem**
1. A settled order increments the customer's derived progress (any channel, org-wide).
2. Threshold crossed → the reward is *available*, which is a reading of the counts and not an emission (`17-F23`; `loyalty.reward_earned` withdrawn); the customer hears about it in their next WhatsApp order notification and sees it on the storefront.
3. On a later order, POS (phone lookup) or storefront shows the redeemable reward.
4. Applying it emits the attributed discount + `loyalty.reward_redeemed`; the counter resets by event.
5. *Merge case:* concurrent redemption attempts across devices resolve like Flow B step 5 — append, flag, never block.

**Flow D — Automatic deal on the storefront**
1. Customer opens the storefront during the deal window; deal-scoped items show the deal price.
2. Cart applies the discount automatically; the order goes through the normal doc 06 flow.
3. `discount.recorded` with `campaign_id` rides the order events; kitchen and POS see an ordinary discounted order.
4. Window ends → prices revert; an in-flight cart revalidates at submission, and whatever price is confirmed is snapshotted on the line (01-F18) — no post-hoc repricing.

**Flow E — Opt-out**
1. Customer replies "STOP" (or a recognized Urdu variant) to any message.
2. Doc 07 ingests it → `customer.opted_out` → registry updated.
3. Every subsequent segment evaluation and send-time check excludes the customer, effective < 1 min (17-N2).
4. Re-inclusion happens only on an explicit customer opt-in (`customer.opted_in`); no org-side path exists.

## 7. Customizability

- **Layer 1 (platform admin):** module feature flag; per-org send metering caps; attribution-window bounds (org value must fall inside them).
- **Layer 2 (org):** campaign definitions; segment parameters within preset bounds (e.g. lapsed N ∈ 14–90 days); loyalty program parameters (N, reward); send windows; coupon constraints.
- **Layer 3 (branch/device):** none.
- **Deliberately not configurable:** opt-out honoring and its permanence; metering bypass; the attribution formula; segment types beyond the preset five; loyalty mechanics beyond order-count.

## 8. Tech notes

- Backend `marketing` module + BullMQ scheduled sends via the jobs service; segment evaluation is SQL over the customer/order read models — no data duplication.
- Campaign/coupon reference data distributes over the kernel reference channel (01 §8) so POS/storefront validation is local and offline-capable — one replication path, already tested.
- WhatsApp specifics (template approval, tier management, webhook handling) stay in doc 07; this module calls its internal tRPC surface and never talks to Meta directly.
- Lift computed nightly with on-demand refresh; reports carry their attribution rule text and input windows for doc 13 citation compatibility.
- Coupon checksum: single check character (Luhn-style over base32) — catches fat-finger entry at POS before any lookup.
- Status-webhook ingestion is idempotent (message id dedupe) and tolerant of out-of-order delivery, matching the kernel's soft-reference discipline (00 §6).
