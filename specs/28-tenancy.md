## 1. Purpose & scope

RestOS was built as installed software for one restaurant and is being run as a multi-tenant service. This document owns what a **tenant** is, what a tenant is **entitled** to, what changes when a tenant stops being entitled, how a tenant **comes into existence**, and where the vendor stands relative to all three. It exists because the absence of a document owning these questions let each module answer them locally, and the deployment then acquired a per-process tenant identity that no module spec is responsible for.

The founder ruling this document is written against (August 2026): **5–10 free pilot restaurants on one pooled deployment, self-serve onboarding, real multi-tenancy now. Billing is deferred.**

**In scope:** the tenant record's lifecycle as a tenancy (on top of `01-F68`'s directory record); entitlement as a resolved, orthogonal gate; suspension and closure as they touch a tenant's entitlement; self-serve signup; the vendor's identity relative to tenant roles; and tenant isolation as it extends from `01-F71`'s register to the serving layer.

**Explicitly OUT of scope. Each is routed — but one of the routes is to this document later and one is to a document that does not exist yet, so both are named as such rather than counted as owned.**
- **Billing, metering, invoicing, payment collection, price tiers, dunning — deferred by founder ruling, and UNOWNED rather than owned.** Pilots are free; `15-F24` makes metering measurement-only and `15 §9.7` forbids writing any FR that makes a payment state gate a service until `15 §9.4`'s invoicing handoff has an owner — and `15 §9.4` says in terms that it *needs* one *"at build time"*. **This document is its chartered home**: `plans/saas-pivot/plan-of-record.md` A1 titles it *"28 — Tenancy, entitlement & billing"* and puts invoicing and collection in its ownership list, and §3's gate makes W6's commercial plane wait on this document existing. So the deferral is this document's to absorb when the ruling lifts, not another document's to hold meanwhile; naming `15 §9.7` as the *owner* would be false, and it is named here only as the **prohibition**, which is **restated, not lifted** (`28-F22`). What is in scope is the *shape* a subscription will attach to, and only the shape.
- **Deployment, environments, regions, the image contract, observability, and the signed edge agent** — doc 29 (`plans/saas-pivot/plan-of-record.md` A1), which is **chartered and unwritten**: a reader routed there today lands on four lines of a plan, not on a spec, and `specs/` ends at this document.
- **The vendor's operational surfaces** — provisioning tooling, fleet health, support, release channels, meters — doc 15. This document says what a vendor operator *is*; doc 15 says what they *use*.
- **Backup, restore, retention, erasure and export** — doc 22, which `22 §1` already binds to every org with nothing tier-dependent. A free pilot gets the same posture as a paying tenant.
- **The tenancy records themselves** — `01-F68` (org), `01-F69` (branch), `01-F70` (device). This document adds a lifecycle *on top of* them and re-decides none of their fields.

- **Emits:** **nothing new** — no event type is introduced by this document (`28-F14`, §5). Lifecycle transitions remain `config.changed` in the org's own ledger with the layer-1 actor, exactly as `15-F25` already rules. **⚠ That is a claim about the catalog, not about buildability:** `config.changed` has no payload schema in `packages/domain`, so the lifecycle path is *unbuildable* until doc 15 declares one and doc 01 absorbs it (`28-F14`).
- **Consumes:** the authenticated subject's `org_id` (`01-F71` (b)) and the per-org entitlement record (`28-F6`). Nothing else; in particular, no fold consumes anything this document owns (`28-F7`).
- **Constrains:** `services/api` and `apps/backoffice` (per-process org configuration, `28-F20`), the internal/tenant router split (`15 §8`, `28-F16`/`28-F17`), and any future signup surface (`28-F12`–`28-F15`).

## 3. Functional requirements

### The tenant

- 28-F1 **A TENANT IS AN ORG, AND THERE IS NO RECORD ABOVE IT.** The unit of tenancy is exactly `01-F68`'s org, and `org_id` is the tenancy key on both planes — the same key the envelope, the device registry, the catalog and every one of `01-F71`'s enforcement points already share. This document introduces no account, group, holding or customer record above the org.
  - **The reason is the isolation register.** All four points in `01-F71` are keyed on org: the permission matrix's org arm, the subject-derived org on the cloud plane, the gateway's cross-org quarantine, and the structured `(org, branch)` fan-out key. A scope above the org would be a fifth tenancy axis that **none of those four points knows about**, so it would be enforced nowhere while looking like tenancy everywhere.
  - **What it costs, stated rather than hidden:** a chain owner operating two legal entities is two tenants — two logins, two ledgers, no consolidated view, and no way to move a branch between them (`01-F69`: a branch is under exactly one org, and its record is never deleted). Multi-branch *within* one org is already served and is not this case. Whether one human may hold accounts in several orgs is **not decided here** (§9.18); today a global case-folded unique email makes it structurally impossible, which is a constraint nobody chose.
  - **This FR re-decides nothing about the org record.** `01-F68` closes its field list at four and names plan, billing, quota and metering as deliberately absent. That stands; `28-F6` is where tenancy state that is not those four things lives.

- 28-F2 **THE TENANT LIFECYCLE IS `15-F25`'s TWO STATES, AND THIS DOCUMENT ADDS NONE.** `active ⇄ suspended`. A free pilot org is **`active`** — it is not a third state, not a flag on the lifecycle field, and not a variant of `suspended`.
  - **This is a decision, not an inheritance.** A document chartered above the module specs is exactly the place a `trial`, `pending`, `onboarding`, `unverified`, `past_due`, `grace` or `closed` value would be added, and each of the seven was considered and refused on `15-F25`'s own test, which this document adopts verbatim: *two states differing in nothing an implementation can observe are one state* (`14-F30`'s precedent). None of the seven changes what a device, a session or a query can observe that the existing two plus `28-F6`'s entitlement record do not already decide.
  - **The specific trap this closes:** "free pilot" feels like a lifecycle value because it is a commercial fact, and the org record already carries a lifecycle field with a closed set validated at the writer. Writing `trial` into it produces a value the writer rejects, or — worse — a widened set with no enforcement path behind it. `01-F1` then makes the resulting `config.changed` transitions permanent.
  - **What it costs:** the question *"is this org a pilot?"* has no answer in the lifecycle field. Whether it needs one anywhere — an org `class` on `01-F49`'s branch precedent, or nothing at all — is **not decided here** (§9.3). What is decided is that it is not a lifecycle state.

- 28-F3 **MISSING TENANT ADMINISTRATIVE STATE IS NEVER A REFUSAL.** An org with no entitlement record, no plan, no subscription and no directory row **folds, syncs, prints and settles exactly as any other**. This is `01-F68`'s *"an org with events and no record is UNNAMED, not invalid"* carried one level out to everything this document owns, and it is stated as its own FR because the natural shape of an entitlement system is a lookup that returns nothing and a caller that reads nothing as *no*.
  - **The failure it forbids is silent and total.** A deployment where an absent record means "refuse" stops every tenant whose administrative state was never written — which, in a pooled deployment with self-serve signup and no billing, is most of them.
  - **⚠ WHAT AN ABSENT RECORD RESOLVES TO IS A SEPARATE QUESTION FROM THIS ONE, AND DRAFT 1 ANSWERED ONLY THIS ONE.** *"Folds, syncs, prints and settles"* are all device-plane verbs, and `28-F7` exempts the device plane from entitlement entirely — so that sentence is true and decides nothing about a **cloud** capability, which is the only kind there is. It matters because **every self-serve pilot is in this state on day one** (`28-F13` creates two records and no entitlement record). Decided, for the members that are flags: a flag is a thing that is *enabled* (`15-F5`: *"plan & feature-flag **enablement** per org"*), so one never enabled is **not enabled**, and an absent record resolves each of `15-F5`'s three cloud channel flags to *not enabled*. That is not a refusal of service and does not contradict this FR — it is the absence of an optional cloud module, and all three are unbuilt stubs today. **Not decided:** what an absent record means for the two members that are not booleans — the configuration-surface tier gate and the intelligence rung cap — where "resolve to nothing" would be a refusal wearing a default's clothes (§9.22).
  - **Corollary for the resolver:** `entitled(org, capability)` distinguishes *"this org is not entitled"* from *"this org's entitlement state could not be read"*, and the second is not the first (`01-F48`'s posture, carried by `28-F8`). A resolver that collapses them is wrong in the direction that stops service.

### Entitlement

- 28-F4 **ENTITLEMENT IS A SECOND, ORTHOGONAL GATE — IT IS NEVER BOLTED INTO THE PERMISSION MATRIX.** `entitled(org, capability)` composes **with** `can()`; it is not an action in `PERMISSION_ACTIONS`, not a role column, and not a cell in the verdict matrix.
  - **The predicate's shape is SOURCED, not designed here, and the source is cited because the next reader will check.** `plans/saas-pivot/plan-of-record.md` §2 states it in those words — *"Entitlement must not be bolted into `PERMISSION_ACTIONS`. The 25-action matrix is among the cleanest artifacts in the repo. `entitled(org, capability)` composes **with** `can()` at the choke points that already exist"* — and this FR supplies the reasons the plan compresses into one line.
  - **The capability vocabulary is `15-F5`'s enumeration and nothing else**, which §7 already binds as `00 §7`'s *presets, not knobs*: a capability is one of the levers `15-F5` lists, resolved per org (`28-F6`). It is **not** a per-procedure key. That is why the bullet below can say most procedures declare none without leaving a hole — minting a capability name to give a procedure something to declare would be inventing the vocabulary this clause closes.
  - **The reason is that the two questions differ in kind.** `can()` answers *who may do this* — a safety and separation-of-duties policy whose widening rules `14-F30` already fixed (widening additive and safe; narrowing stops a till mid-service). Entitlement answers *what this tenant has* — a commercial fact that changes on a contract, not on a role. Fusing them makes a lapsed subscription and an unauthorised cashier the **same refusal** to every caller and every log line, and it makes an owner's permission row change when a plan does.
  - **Mechanically it also fails.** The verdict table is exhaustive by construction: a new action or column forces a decision in every cell in one edit, under type-checker pressure. Entitlement capabilities do not have per-role answers — they are org-wide — so every such cell would be invented to satisfy a compiler.
  - **Where it composes, stated so the checker cannot force an invention.** `services/api` already refuses at boot to host a procedure not built with an authorization gate. The entitlement gate rides the same construction, and the boot assertion is: **every procedure either DECLARES an entitlement capability or appears on a named exemption list** — the shipped `PUBLIC_PROCEDURES` and `SESSION_ONLY_PROCEDURES` sets are that list's starting point.
  - **Most procedures declare no capability, and that is the expected state.** The login procedure — the corpus's one public one — is unauthenticated: there is no subject, therefore no org, therefore an entitlement gate on it is structurally impossible (`28-F5` (b)). The catalog router's `save`, `enabled` and `history`, the device router's `list` and `revoke`, the nightly summary and the tenancy directory map to no `15-F5` flag, and minting one per procedure to satisfy a type checker is commandment 2 at scale — the same failure the bullet above names for the verdict matrix, and the shipped comment on `SESSION_ONLY_PROCEDURES` already refuses it in those words. **Declaration is a boot-time property of a procedure; entitlement is a per-org runtime fact resolved from data (`28-F5`) and can never be one.** "An ungated or unentitled procedure is a boot failure" is therefore wrong as Draft 1 wrote it: what boot can see is a missing *declaration*.
  - **⚠ THE GATE HAS NO CONSUMER AND NO WRITER TODAY, AND BUILDING IT AHEAD OF ONE WOULD BE THIS CORPUS'S OWN NAMED DEFECT.** Measured August 2026: every capability `28-F6` enumerates gates a module that is a two-line stub (`apps/storefront`, `services/whatsapp`, `services/foodpanda`, `services/intelligence`); the bullet above records that every procedure `services/api` actually ships declares none; and **nothing writes a flag** — `15-F5`'s console does not exist and `15-F27`'s declared provisioning steps include no flag or entitlement command. A resolver, a record and a boot assertion with **zero call sites** is *a correct subsystem with no seam to the product*, which `AGENTS.md` counts fifteen instances of and which no rail can see (§8's last bullet). **So this FR is the SHAPE the gate takes when it lands with its first capability consumer — it is not a licence to land it first.** `plans/saas-pivot/plan-of-record.md` §3 already sequences it that way (entitlement is W6, after the control plane W5), and a session that reads this section as a build ticket for the pilots is reading it wrong.
  - **Order is decided:** `can()` first, `entitled()` second. Authorization is about the subject and must not leak the tenant's commercial state to someone who had no right to ask; and a refusal message that names a missing entitlement is only honest (`00 §5.7`, `14-F37`) to a subject entitled to hear it.

- 28-F5 **ENTITLEMENT IS RESOLVED FROM PER-ORG DATA, NEVER FROM THE PROCESS ENVIRONMENT, AND NEVER FROM THE CALLER.** Two clauses, and each closes a defect this repo has already paid for.
  - **(a) Not from the environment.** No layer-1 or layer-2 fact **about a tenant** may be read from `process.env` in shipping code **on the cloud plane**. ⚠ The two qualifiers are load-bearing and Draft 1 carried neither: a **device host's own identity** is `00 §7` layer-3 deployment configuration, and `01-F65` *requires* it to come from configuration and requires a host that was not told which device it is to refuse to start rather than default — so read unbounded this clause would forbid what the kernel mandates and what `28-F13` cites approvingly one page later (`01-F65`/`01-F67`). The ban is on a **process being told which tenant it serves**, which is `28-F20`'s measured gap, not on a machine being told which machine it is. The measured precedent is the enabled `(branch, channel)` set: it was declared twice — once on `services/api`, once in `apps/backoffice` — so the axes the editor drew and the axes the writer refused against could disagree **silently**, and restoring the client-side fallback failed **0 of the 95** pre-existing back-office tests while `pnpm verify` and `pnpm seams:check` stayed clean. The fix was one declaration with **no fallback**, and it is the shape every entitlement read takes: one authority, no default, and a grid drawn from a guess is how the drift returns.
  - **(b) Not from the caller — on the TENANT plane.** The org is taken from the authenticated subject and never from a **tenant-facing** request's parameter, header or path — `01-F71` (b), unchanged. There is no tenant-context header, no `?org=` on a tenant API and no impersonation shortcut through one. This matters more here than anywhere: today the tenant plane is safe partly *by construction*, because org is not an input to any tenant port; the moment a tenant-facing entitlement API takes an `org_id` argument, that axis reopens and `can()`'s org arm becomes the only thing standing on it.
  - **(b′) The INTERNAL plane is the opposite by construction, and the clause above must not be read onto it.** `15 §8` puts internal routers on a separate auth domain whose tokens are never valid on tenant APIs and vice versa; a **service credential is not a subject**, and `01-F71` (b) — which is about an authenticated subject's org — has nothing to say about it. Measured August 2026, `services/api` already reaches the gateway's internal tenancy, device, org-event and published-catalog routes with `org_id` **as a query parameter**, and it must: naming which tenant's data a vendor-plane caller wants is what a cross-tenant surface *does*. Read absolutely, (b) would delete that parameter and leave the API unable to serve an org name, a branch list, a device list or a catalog history at all. What constrains that hop instead is `28-F18` (c) — it is a cross-tenant enforcement point owed a `01-F71` clause, and Draft 1 asserted that constraint against a register the hop was not in — and `28-F17`'s owed boot-asserted internal gate. If §9.4 puts entitlement in platform tables, its read crosses this hop and inherits exactly those two constraints and no weaker ones. **The reciprocal pointer is landed in `01-F71` itself, in the same change**, on the discipline this document's status note commits to: a narrowing recorded only in the narrowing document is one a session routed to doc 01 by the `AGENTS.md` table never sees, and the specific harm is concrete — reading (b) absolutely, that session deletes the `org_id` parameter eight internal routes require and calls it a fix.
  - **What it costs:** a deployment can no longer be reconfigured by restarting a process with different variables. That is the point — a per-process tenant identity is `28-F20`'s measured gap.

- 28-F6 **THE ENTITLEMENT RECORD IS SEPARATE FROM THE ORG RECORD, AND IT IS A SHAPE WITHOUT NUMBERS.** A record keyed by `org_id`, holding what `15-F5` already enumerates as layer-1 levers resolved for this org — `15-F5`'s three **cloud channel flags** (storefront, WhatsApp, foodpanda), **tier gates in `15-F5`'s own sense**, and the intelligence rung cap (`13-F28`) — plus `15-F5a`'s single plan structure **less the take-rate**.
  - **"Tier gates" means what `15-F5` says it means and nothing wider:** *"which T1/T2/T3 surfaces the org can configure"* — a gate on a **configuration surface**, never a claim about what hardware a branch has. `DEC-HW-001` (accepted, ratified August 2026) forbids the wider reading in terms — *"no code may branch on the tier to decide whether a piece of hardware exists"* — and `DEC-HW-003` (status **`proposed`**, founder ruling owed) recommends the ladder survive as a derived label over `02-F31`'s capability set. Neither is amended here; what this FR does is refuse to let a per-org commercial value become a **second writer** of a fact the corpus derives from the device registry.
  - **⚠ `15-F5`'s MODULE FLAGS ARE BOTH EXCLUDED, SO THAT MEMBER IS EMPTY TODAY — and Draft 1 excluded one of them in the same paragraph that kept the other.** `15-F5` lists exactly two module flags: the tax add-on (doc 16) and marketing/loyalty (doc 17). **Both have an in-branch function**, so both fail `28-F7`'s cut and are routed to their owning docs rather than carried here (§9.19 for tax, §9.25 for loyalty). Stated plainly because the consequence is easy to miss: what this record holds today is three cloud channel flags, a configuration-surface tier gate and a rung cap.
  - **`15-F6`'s `effective_from` is NOT carried, and Draft 1's citation for it did not support it.** `15-F6` effective-dates **the own-channel take-rate and nothing else** — the take-rate is its entire subject, and `28-F22` records R5 as dropping it — while `15-F5`, which owns every member this record actually holds, requires only a `config.changed` per flag change with **no date at all**, and `15-N2`/`15-F22` size flag propagation in minutes, which is the opposite posture from a future-dated write. Generalising a take-rate rule to a feature flag invents a resolution-at-time-`T` semantics nobody has specified, against an NFR that assumes there is none. It is also precisely the shape a billing period will attach to, so it is **§9.24** and not a member.
  - **Not on the org record**, whose four fields `01-F68` closes and which names *"anything to do with plan, billing, quota or metering"* as deliberately absent. A `plan` column there is the single likeliest edit a reader of `15-F5a` will make.
  - **Not on the event envelope.** `01-F49` argued this exact shape down for the training discriminator and gave the reason: an envelope flag makes correctness depend on every fold, report, export and analytics query remembering to filter, and `01-F1` makes one forgotten filter permanent. Tenancy state is a **record**, enforced once, at a gate.
  - **No tiers, no SKUs, no quotas, no prices, no seat counts, no trial length.** `15-F5a` fixes plan shape at one plan with no tier SKUs; no quota of any kind is specified anywhere in this corpus and none is invented here (§9.9). A free pilot is an org whose plan carries no billable subscription — **whether that is a plan record with a zero value, a plan record marked non-billable, or no plan record at all is not decided here** (§9.2), because whichever is chosen is the shape billing later attaches to and that is a founder decision. `28-F3` guarantees that all three readings serve the tenant identically today.
  - **Nothing keys on a name.** `01-F70` makes a device name a label and never an identifier; the same holds for org and branch names. A seat count, quota or invoice line keyed on a display name is silently wrong the first time an owner renames a till.
  - **⚠ IT DOES NOT CARRY `01-F60`'s ENABLED `(branch, channel)` SET, AND CONFLATING THE TWO WOULD PUT A VENDOR LEVER ON A SALE.** `15-F5`'s channel flags are three **cloud** channels. `01-F60`'s enabled set is a **price key** over `02-F42`'s closed five — including `counter`, which has no `15-F5` flag — crossed with the org's branches, which has no `15-F5` flag either; and `01-F60` sources it from *"`00 §7` layer 2: 'channels enabled' and the org's branches"*. They are not the same object, and the second is not layer 1. If entitlement gates channels at all it **composes with** the layer-2 set and never *is* it. The failure the separation prevents is total and silent: `01-F60` makes the set a **required** input and its writer refuses an empty one outright, so an org with no entitlement record — which `28-F3` requires to serve identically, and which every self-serve signup is on day one — would publish no menu at all, every tile would read `no price set`, `addLine` would refuse, and all four processes would report success. **Which layer owns that set is RULED, and Draft 1 parked a question the corpus answers in the clause quoted above.** `01-F60` names its source outright — *"`00 §7` layer 2: 'channels enabled' and the org's branches"* — `00 §7` lists *channels enabled* under **layer 2 and nowhere else** (layer 1 reads *"feature flags/tier enablement"*, so the two do not both list it, and Draft 1's *"`00 §7` lists it in both"* was simply wrong), and `14-F19` makes layer-2 channel configuration *gated by* layer-1 flags — which is **composition, not ownership**. So: **the enabled `(branch, channel)` set is layer-2 data, per `01-F60` and `00 §7`**, including `counter`, which has no layer-1 flag at all. This record is not it, and `28-F20` (iii) is unblocked. What remains open is the narrow composition residual (§9.15).
  - **The take-rate is the one member of `15-F5a`'s structure this record does not carry.** `plans/saas-pivot/plan-of-record.md` R5 drops it, and `28-F22` records the amendment as owed across four documents. Carrying it here would ship a field nothing writes and nothing reads — *a field that reads as a capability*, the defect `28-F22` names in those words — so it is excluded pending §9.13 rather than left implicit, because implicit is how it gets built.
  - **Where the durable copy lives — org ledger or platform tables — is not decided here** (§9.4). The corpus points both ways for neighbouring facts: `15-F5` makes every flag change an org-ledger `config.changed` with an actor, while `15 §2`/`15 §5` put staff accounts, meters and the platform audit log in platform tables outside org ledgers. Both readings have precedent, so picking one silently is exactly what this document exists to stop.

- 28-F7 **ENTITLEMENT IS A CLOUD-PLANE GATE ONLY. NO DEVICE ASKS IT, SO IT HAS NO CACHE, NO TTL AND NO STALENESS POLICY.** No till, pass screen or edge process resolves an entitlement; nothing entitlement-shaped is distributed to a device as reference data, and no fold reads it.
  - **Why this is the right cut, for what it covers.** What is left inside this document after the two exclusions below is a cloud service or a cloud *configuration* surface — storefront, WhatsApp, foodpanda, the intelligence rung cap, and which surfaces an org may configure. For those the gate has no business in a branch, and refusing to put it there dissolves an entire class of question rather than answering it: there is no cached entitlement to go stale, no TTL to pick, no fail-open-versus-fail-closed argument on a WAN-down till, and no possibility of a commercial state reaching `01-F17`'s sale.
  - **⚠ BOTH OF `15-F5`'s MODULE FLAGS ARE EXCEPTIONS, AND THEY ARE EXCLUDED RATHER THAN ASSUMED AWAY.** Draft 1 asserted that *none* of `15-F5`'s flags is an in-branch function; the correction caught the first and **repeated the error one flag over, inside the paragraph correcting it.**
  - **(i) The tax add-on (doc 16).** `16 §1` runs it partly on *"a POS-side fiscal queue component inside doc 02 hosts"*; `16-F11` persists the fiscal row in POS SQLite **before the receipt prints** and demands *"zero invoice loss, ever"*. So a till must know whether the add-on is on — offline, per branch — which is exactly the distribution-and-staleness argument this FR declines to make. **The basis is stated precisely, because Draft 1 overread its own citation:** the *flag* is per-org **layer 1** (`15-F5`; `16 §7` — *"Layer 1 (platform admin): add-on enablement per org"*; `16 §4`'s flow step 1 — *"platform admin enables the flag (doc 15)"*), and `16-F25` adds a **per-branch certification precondition** on the act of enabling (*"only when the applicable authority adapter is certified for it"*, and `16 §5` keys `adapter_certifications` on *authority adapter × org/branch*). So the enablement axis is not what is unspecified — **distribution to a branch is** (§9.19). What is decided here is only that it is not an entitlement under this document; nothing about its behaviour is.
  - **(ii) Marketing and loyalty (doc 17), on the same terms.** Doc 17 puts its application surface inside the POS, offline, on the critical path: `17-F11` applies automatic deals *"at POS/storefront"*, `17-F17` redeems *"at POS or storefront"*, §4's Flow B is *"Coupon at POS (incl. offline)"*, and `17-N3` requires validation *"< 100 ms from local reference data (no network on the critical path)"*. That is the identical shape, so it takes the identical treatment: excluded from `28-F6`'s record and routed to doc 17 (§9.25). It differs from the tax add-on in one respect worth naming rather than smoothing over — the failure is commercial rather than statutory, and there is a plausible resolution in which the branch-side absence is *total* (a disabled module publishes no campaign reference data, so `17-N6`'s reference channel carries nothing and a lookup finds nothing). **That is a shape, not a decision, and doc 17 is where the decision belongs** — asserting it here would be this FR's original error a third time.
  - **It could not be a fold input in any case.** `01-F52`/`01-F74` put reference data on a versioned snapshot-plus-delta path applied monotonically (`01-F56`) and forbid it as a fold input, because a projected value that read sync state at fold time is the `01-F34` break law 1 exists to prevent. Entitlement is strictly weaker than a roster and gets no such path.
  - **Suspension is different and stays different.** `15-F7` puts a status banner on a suspended org's devices, so *suspension* is a device-visible fact where entitlement is not, and the two must not be merged into one "tenant state" push. **⚠ But the banner is specified and unbuilt, and this FR leans on it, so the gap is named here rather than assumed:** measured August 2026, `hello_ack` carries `session_id`, `hub`, `resume_from`, `relay_authorized`, `renewed_token`, `compression` and `catalog_version` and **no org status field**; device admission never reads the org record at all; and the only readers of an org's status anywhere are the vendor-plane tenancy directory and its API passthrough, neither of which reaches a device. So the banner today has **no producer, no wire field and no consumer** — `01-F63`'s shape, and `28-F14`'s treatment applies: **owed by name**, the wire field to doc 01 and the effect to doc 15 (`15-F7`). `28-N2` therefore sizes no device leg for it.
  - **What it costs:** a capability that must be gated *inside a branch* cannot be an entitlement under this document. If one is ever wanted, it is a new FR with its own distribution and staleness argument — not a widening of this one. Both of `15-F5`'s module flags are already exactly that case, which is why they are named above rather than discovered later.

- 28-F8 **NOTHING COMMERCIAL MAY REACH THE INGEST PATH OR A SALE — AND "UNREADABLE" REFUSES ONLY WHAT IT GATES.** No plan state, entitlement, quota, expiry, trial end or payment state may appear on `hello`, on the `push` arm, in the merge gateway, in device admission, or anywhere a till persists or acknowledges an order.
  - **Five laws converge here and it is the ceiling of this whole document:** `01-F17` (a sale is never blocked), `00 §5.1`, commandment 4, `15-F7` (*in-branch POS billing never stops — `00 §5.1` is not a business lever*), and `01-F68`'s foreign-key ban, whose reasoning generalises past foreign keys: refusing ingest is refusing a sale a till has already rung and persisted (`01-F2`), and admission is the gate, one layer up.
  - **If a refusal is ever specified at the gateway for any reason, it fills its lamport slot.** `01-F37` durably stores a quarantined event precisely so the push ack advances past it and the device outbox never wedges. A tenancy refusal that leaves a hole in the sequence wedges that device permanently.
  - **The fail-closed posture applies to the gate, not to the product.** Where entitlement state cannot be read, the **cloud capability** it gates is refused, per `01-F48` and `01-F71`'s fail-closed clause — an unreadable state is not proof of entitlement. Ingest, local persistence and the sale are not entitlement-gated at all, so there is nothing there to fail closed on; that is the whole benefit of `28-F7`'s cut.
  - **The ban covers the CAUSE, not only the payload.** A device-visible state whose only writer is a payment state **is** a payment state on `hello`, arriving one indirection later — `15-F7`'s suspension banner already rides the admission path, so the mechanism that would carry it is built. `28-F9` (a) forbids that writer today, and this clause adds the second half: answering §9.10 in that direction requires amending **both** FRs by name, because amending `28-F9` alone would leave this ban reading as untouched while the payment state reaches the handshake.
  - **And a credential lapse is not a service lapse.** `01-F47` already rules the shape: expiry withdraws cloud/LAN *admission* only, and an expired-but-unrevoked device is still admitted to drain its backlog and take a renewal. No tenancy state may be made to do what that FR refuses to do.

### Suspension and closure

- 28-F9 **SUSPENSION STAYS `15-F7`'s, IT HAS NO COMMERCIAL WRITER TODAY, AND THE `00 §5.1` EXCEPTION IS NARROWER THAN THE PLAN ASSUMED.** This document restates none of `15-F7`'s effects and changes none of them; it rules two things about who may cause them.
  - **(a) No entitlement, plan, quota or payment state sets `suspended`.** Suspension is an administrative act by a platform-admin under `15-F2`'s typed confirmation, for an administrative reason. `15 §9.7` forbids writing an FR that makes a payment state gate a service until the invoicing handoff has an owner, and billing is deferred, so there is no such state to gate on. Abuse and breakage are administrative reasons and remain available. A grace period, a dunning schedule and an automatic suspension on non-payment are **not specified here and must not be invented** (§9.10).
  - **(b) The exception `00 §5.1` creates is smaller than `plans/saas-pivot/plan-of-record.md` A3 states, and naming it precisely is the point.** `00 §5.1` promises that *every in-branch function works with WAN down* and that cloud-originated orders queue for the branch. `15-F7` blocks **new cloud-originated orders** and takes the storefront down — both cloud functions on the cloud plane — while sync is still accepted and in-branch billing never stops. So the two do not contradict on in-branch service at all. The one sentence that is genuinely owed to `00 §5.1` is that *a cloud-originated order may be refused at its source by an administrative act, which is not a degradation of the branch*; that is a one-line editorial cross-reference to doc 00 and it is **owed, not performed here** (§9.1), because `00 §5` sits at authority position 2.

- 28-F10 **CLOSURE IS `15-F25`'s PROCEDURE, AND THE EXPORT STEP IS NOT COMPLETE WHILE A DEVICE HOLDS UNPUSHED EVENTS.** Closure remains: offer and generate the owner's export (`22-F16`) → revoke every device (`14-F13`, `01-F42`) → suspend (`15-F7`) with the reason recorded. Nothing in it deletes a ledger. This document adds one clause to that ordering, as a named amendment to `15-F25` — **and the pointer is landed in `15-F25` itself, in the same change.** An amendment recorded only here is one a session routed to doc 15 by the `AGENTS.md` table never sees, which is how it opens the unamended ordering and revokes before draining.
  - **The clause:** step 1 is not satisfied until every reachable device in the org has **drained its outbox**. `22-F21` states plainly that until an event has been pushed and acked the device holds the **only copy** of it; `01-F42` sends a purge command to a revoked device on next contact. Revoking before draining therefore destroys events that `22-F16` has just promised the departing owner as *"the org's complete event log"*. The primitive already exists — `01-F47`'s push-only drain mode, which `01-F50` already requires before a training swap; this clause wires it into an ordering that was written without it.
  - **⚠ NEITHER THE ACT NOR ITS OBSERVABLE EXISTS, AND THE CLAUSE IS OWED BOTH RATHER THAN ASSUMING THEM.** `01-F47`'s drain mode is a state the **gateway grants** an expired-but-unrevoked device, and `01-F50` invokes it inside a **device-initiated** credential swap; neither is a step an operator can perform against a healthy till. And nothing reports that a device's outbox is empty — outbox depth is `15-F11`'s heartbeat dashboard, which is unbuilt. So as written the precondition cannot be *evaluated*, and §9.7's question — what to do when a device cannot be drained — presupposes being able to tell when one has. **Owed to doc 15 by name:** a declared, invokable step under `15-F27`'s discipline that puts a named device into drain mode, and `15-F11`'s outbox-depth read as the thing that says step 1 is satisfied. (The gateway already holds each origin's last acked position (`01-F8`), which is the fact those two would be built on; naming it here is an observation and not a substitute requirement.)
  - **⚠ STEP 1'S OWN EVENT IS UNBUILDABLE TOO, AND DRAFT 1 NAMED ONLY STEPS 2 AND 3's.** `22-F16` records the export as `governance.export_generated`; `packages/domain` declares **no `governance.*` family at all** (measured August 2026: zero occurrences in the registry), so under `01-F4` that emit throws exactly as `config.changed` and `device.revoked` do — the same defect `28-F14` names, one step earlier in the same procedure. **Owed: doc 22's to declare, doc 01's to absorb.** And step 1 has no vendor-side **actor**: `22-F16` is owner-triggered and *"owner-role only"* from doc 14's back office, while closure's actor is a platform operator whose only sanctioned route into a tenant surface is `15-F15`'s impersonation — which `28-F19` shows does not run. So closure's first step is blocked twice over, independently of the drain clause this FR adds.
  - **What is NOT decided:** what closure does when a device **cannot** be drained — offline, lost, or destroyed. Refusing to close leaves the tenant hostage to a missing tablet; closing anyway makes the export knowingly incomplete. Both are defensible and the choice is a founder's (§9.7). What is not defensible is doing either silently, so whichever is chosen, the export bundle must state which devices were not drained (`00 §5.7`).

- 28-F11 **NO TENANCY STATE DELETES A LEDGER, AND NO RETENTION PERIOD IS SET HERE.** Churn, non-payment, a lapsed pilot and a long suspension delete nothing and shorten nothing.
  - `22-F13` retains kernel events **forever**; `22 §7`'s never-configurable list forbids disabling backups for an org, shortening event retention, or any org-level switch that weakens `22-F1`/`22-F2`; `01-F1` has no delete path in any API; `00 §5.5` binds the vendor as tightly as the owner. A plan or entitlement that could switch any of these off is forbidden by name, and a "pilots are best-effort" posture is forbidden by `22 §1`, which makes nothing in doc 22 tier-dependent.
  - **`01-F51`'s droppability does not extend here, and the argument is why.** A training branch is droppable because it is *by construction not history* — it never fed a report, a tax filing or a payout. That premise is false for any pilot that rang a real sale, and `01-F69` already refuses the generalisation one level down.
  - **`22-F14` is not an offboarding mechanism.** It is customer-PII crypto-shredding that deliberately leaves every transactional fact standing and is refused under fiscal retention or legal hold. A departing tenant is not "erased".
  - **What a churned pilot's data costs, and for how long it is kept, is not decided here** (§9.9) — it is already `15 §9.6`'s open question with a founder named against it, and inventing "90 days after cancellation" would contradict a normative matrix and would be built.

### Self-serve signup

- 28-F12 **SELF-SERVE SIGNUP IS RULED IN, AND `15-F26` IS AMENDED BY NAME.** `15-F26` says *"There is no self-service signup path, and that is a decision"*; the founder ruling of August 2026 overrules that clause. Recording the overruling explicitly is the requirement — this corpus has already paid three weeks for a green artifact that went on defending an overruled rule because nobody carried the ruling back. **So the strikethrough and pointer are landed in `15-F26` and in `15 §9.7` in the same change**, per the corpus's own supersession rule: recording an amendment only in the amending document is the identical defect one layer up, and doc 28 is read at position 3 (see the status note) — a peer, whose amendment nothing points at unless it is written down where the routed reader lands.
  - **⚠ WHAT THE RULING OVERRULES BESIDES `15-F26`, NAMED SO THE REVERSAL IS NOT SILENT.** `plans/saas-pivot/plan-of-record.md` §0 lists *"vendor-operated onboarding rather than self-serve signup (R1)"* among the consequences it says *"follow automatically and are not separate decisions"*, and `plans/saas-pivot/reconciliation.md` FORK 4 recommends *"no self-service signup in v1; build the vendor console"* at **high** confidence. The ruling is the founder's and stands over both; what matters is that they are named, because FORK 4's three arguments are **overridden, not refuted**, and one of them is a live blocker rather than an opinion: *"`create-owner` mints a password and prints it once, which has no self-service analogue"* is precisely §9.21, unresolved.
  - **⚠ AND THE RULING ITSELF IS UNRECORDED — the one thing this FR cannot fix from inside doc 28.** A corpus-wide search for the ruling finds it **only in this document's §1**. So a reader arriving at the plan of record — the artifact that records the other sixteen rulings in a table — still reads the overruled consequence as current, and a document asserting a founder ruling nobody else records is exactly the state that let a green test defend an overruled rule for three weeks. **Owed: a citable row** (a plan-of-record §0 ruling row, or a `DECISIONS.md` row), and it is a founder act, not an editorial one (§9.20).
  - **Which of `15-F26`'s three reasons fall.** (i) *"§1 makes this module internal-only"* — falls, and it was never an argument against signup, only against signup living in doc 15: a public signup surface is not a platform-admin screen and doc 15 correctly does not own it. (ii) *"§4's New-org flow is a staffed sequence including a recipe-mapping session with the chef (`15-F9`)"* — falls **for the pilot path only**: the staffed sequence remains available and remains the better onboarding where a vendor session is possible; it stops being the *only* path. (iii) *"`restaurant-os.md` §7 sells done-for-you onboarding"* — is a commercial promise, not a technical bar, and a self-serve path is additive to it.
  - **Which of `15-F26`'s clauses SURVIVE, unchanged and binding on the new path.** The vendor never holds a restaurant's password. The org's first named owner is created in the same act as the org — no org exists that nobody can administer. `org_id` is minted once and never reused, so an abandoned or duplicate signup's id is **abandoned, never recycled** (`01-F68`). And `15-F27`'s writer discipline binds entirely: every record is created by a declared step, ordering is enforced at the writer because the schema carries no foreign key, re-runs are safe no-ops that say so, provisioning never renames and never resurrects, and a password is never an input.
  - **`15 §9.7` is closed on its signup half and stays open on its billing half.** The question *"should a self-service signup ever exist"* is answered: yes, for pilots. The paragraph's second half — billing, subscriptions, plans, quotas and metering-to-invoice deliberately not specified — is untouched (`28-F22`).

- 28-F13 **ONE SIGNUP ACT CREATES AN ORG AND ITS FIRST OWNER, AND IT REFUSES TO INVENT A BRANCH.** The act creates exactly two records: the org (`01-F68`, `display_name` as typed, status `active` per `15-F25`) and one user carrying the org-wide assignment `{ role: owner, branch_id: null }` (`01-F26`'s per-location assignment with a null location).
  - **The user record is `11-F20`'s required minimum inherited WHOLE, not restated in part.** Draft 1 listed a `display_name`, a credential and the assignment; that FR's minimum also carries `user_id`, `org_id` and **`01-F61`'s `grid_ordinal`**, which the shipping schema requires and which the staffed writer sets. A partial restatement of a field list is a list an implementer will follow into a row the database refuses, so this FR states no list of its own.
  - **The form collects exactly what those two records require and nothing more:** the org's `display_name`, the owner's `display_name`, the owner's email. **No branch, no tier, no plan, no channel** — a tier or plan collected at signup is `28-F2`'s refused lifecycle value and `28-F6`'s absent record arriving through a form instead, and a branch is the refusal below. Where the surface is *hosted* is not decided here (§9.26): the back office is a tenant-plane app whose every screen sits behind `14-F1`'s auth gate, so a public route inside it is a new posture rather than a new page.
  - **The email uniqueness check runs BEFORE the `org_id` is minted.** Email is unique case-folded and **globally** (§9.18), so a collision is foreseeable and ordinary; minting first would abandon an `org_id` permanently (`01-F68`, and the atomicity clause below) and manufacture one of `28-F15`'s permanent junk orgs on a keystroke a stranger cannot be blamed for. `15-F27`'s *"ordering is enforced at the writer"* is the discipline; this is one more instance of it. What the refusal may *say* is a surface decision and is not made here.
  - **It does not create a branch, and that is a refusal rather than an omission.** `01-F69` requires a branch to carry a non-empty `display_name`, a `type` and a `class` — three facts a signup form has not asked for. Minting a "Main Branch" is precisely the guess that `01-F65` and `01-F67` refuse elsewhere: a host that was not told which device it is refuses to start rather than defaulting. The first branch is the first step of `14-F26`'s wizard, made by an authenticated owner who knows the answers.
  - **The two records are one act.** If the owner cannot be created the org must not stand: `15-F26`'s *"no org exists that nobody can administer"* is the binding sentence, and a failure leaves the minted `org_id` abandoned. Atomicity is enforced at the writer, not by a foreign key — `01-F68` forbids one, permanently.
  - **The signup ordering is `15-F27`'s, inverted at exactly one point and no more.** Staffed provisioning runs org → branch → device → owner; self-serve runs org → owner, with branch and device deferred to the wizard. The writer's refusals do not change: a branch under an org with no record, a device under a branch with no record and an owner in an org with no record are each still refused **by name**, naming the step that was skipped.
  - **The credential is `15-F26`'s, and its unbuilt half is unchanged.** The step mints the secret itself and stores only an Argon2id hash at `01-F61`'s cost floor. `15-F27` already records that the single-use, expiring set-credential *link* has no redemption surface behind `14-F1` and that until it exists the minted secret is an ordinary password that does not expire — self-serve signup makes that the **first screen a tenant ever sees**, which raises its priority and changes nothing about its ownership (doc 14).
  - **⚠ AND NOTHING SAYS HOW THE SECRET REACHES THE STRANGER WHO ASKED FOR IT. THIS BLOCKS THE SURFACE (§9.21).** On the staffed path the answer is physical: `15-F27` has the step emit the secret once *"on its own stream, as the thing handed to the owner"*, and an operator reads it off a terminal. **Self-serve has no operator**, and the two obvious substitutes are each closed today: displaying it in the signup response is a decision nobody has made about an unverified email; and an emailed set-credential link needs both `15-F26`'s missing redemption surface **and an outbound-mail capability that no document in this corpus owns** — a corpus-wide search finds one scheduled-export delivery mention (`14-F25`, itself open at `14 §9.3`) and nothing else. `15-F27` also forbids the shortcut of collecting a password on the form (*"a password is never an input"*), and `28-F12` carries that clause forward unchanged. So the act as specified mints a credential that cannot be delivered, and the same absence removes **account recovery**: one owner, one password, no reset flow anywhere in the corpus, and `15-F15`'s vendor route unbuildable (`28-F19`) — a locked-out pilot is an unadministrable org whose `org_id` can never be reused. **Named, not solved:** this is one missing delivery channel behind one screen, and it is the founder/doc-14 decision at §9.21.
  - **⚠ THE PATH TERMINATES AT THE ORG AND ITS OWNER, AND BOTH THINGS IT HANDS OFF TO ARE UNBUILT.** The refusal above is right and its destination is not there: `14-F26`'s wizard does not exist in any form (the back office ships a workspace, a catalog screen, a price grid, a change history, a device list and an auth gate — no wizard, no branch form, no user CRUD, no pairing screen), and **`01-F25`'s back-office pairing code is explicitly still owed**, so a device is paired today only by a shell command on the service host. A self-onboarded tenant therefore signs up and stops: no branch, no staff, no till, without the vendor operator the staffed path was built around. **Owed with named owners, exactly as `28-F14` treats `config.changed`: `14-F26` to doc 14, `01-F25`'s pairing code to doc 01.** This document neither invents them nor pretends §4's flow is walkable without them.
  - **⚠ AND THE SUCCESSOR SURFACES HAVE NO PERMISSION ACTION TO GATE AGAINST.** This FR says the first branch is made by *"an authenticated owner"* and step 4 adds staff — but `PERMISSION_ACTIONS` ships **25 actions and none for a branch, a user or an org**, `services/api` refuses at boot to host a procedure that names none, and the device-plane authorizer's fail-closed default denies any request for an action with no row. So the wizard's first procedure cannot be built *or* booted. **Owed to doc 14 by name**, on the corpus's own precedent and not decided here: `14-F30` (`device.manage`), `02-F46` (`availability.toggle`) and `02-F47` (`customer.record`) each landed the missing action **in the FR that owns the surface**, and doc 14 owns both surfaces here (`14-F14` user CRUD, `14-F26` the wizard). Deciding them in this document would put the action in the wrong doc and re-open `14-F30`'s owner-only reasoning somewhere no reader of the surface will look.
  - **Signup does not extend the shell command's life, and `15-F27` already ruled that.** The self-serve act is a **third** writer of these same two records beside `15-F27`'s declared steps and `15-F1`'s console; two writers of one fact disagreeing silently is this corpus's most-repeated defect, so it is worth stating that nothing here re-opens the question — `15-F27` says in terms that *"this FR is satisfied by the console when it lands, and the command retires then"*, and this document proposes no amendment to that.

- 28-F14 **THE SIGNUP ACT EMITS NO EVENT, FOR `15-F27`'s REASON UNCHANGED, AND THIS DOCUMENT INTRODUCES NO EVENT TYPE.** No `subscription`, `entitlement`, `plan` or `tenant` family type is declared here, and none may be invented downstream.
  - **Why no new type:** `01-F4` makes producing an unknown type a build-time *and* runtime error; the `01 §4` catalog is extended only by a spec PR to the owning doc plus that list; and `01-F62` fixes the **org-scoped** set at five types on the test of who may legitimately emit — so any cloud-plane tenancy type is simultaneously a `01 §4` absorption, a `01-F62` amendment and a payload schema in `packages/domain`. `15-F25` already showed the corpus's answer: lifecycle transitions ride `config.changed` and introduce no type.
  - **Why the signup act itself emits nothing.** At the instant the org is created the signer-up is not yet a user of any org — the user record is an *output* of the act, not an input — so `OrgEvent.actor_user_id` could only be `null`, permanently, in an append-only store. `15-F27` refused exactly that for the shell commands, on the ground that an unattributed provisioning record is worse than none because it reads like one, and left `15-F4`'s ledger half **owed to a surface that has an actor**. Self-serve does not change the reasoning; it changes who the eventual actor is.
  - **⚠ "EMITS NOTHING NEW" IS TRUE OF THE CATALOG AND FALSE OF BUILDABILITY — DO NOT READ THEM AS ONE CLAIM.** `config.changed` has its `01 §4` entry and **no payload schema in `packages/domain`**: measured August 2026 the registry declares 41 event types and `catalog.changed` is the only admin-family member among them. So under `01-F4` every transition this document routes through it — `28-F2`'s lifecycle moves, `15-F25`'s, `15-F5`'s flag changes, §5's Data line, the suspension flow — **throws at emit today**. A platform-admin suspending a pilot would gate the org cloud-side with no ledger record and no attribution, permanently, in an append-only store (`01-F1`). This is `28-F19` (i)'s defect one FR over and `05-F7`'s exactly: a catalog entry with no schema makes a path *unbuildable* rather than merely unbuilt. **Owed, with named owners: the payload is doc 15's to declare** — it owns both writers (`15-F5`, `15-F25`) — **and doc 01's to absorb.** `15 §2`'s `device.revoked` is in the same state and is doc 15's too (`14-F13` already records its actor problem), and so is `22-F16`'s `governance.export_generated`, which doc 22 must declare and doc 01 absorb — that one is closure's **first** step (`28-F10`), so all three steps of `15-F25`'s procedure are unbuildable for this one reason and Draft 1 named two of the three. This document introduces no type and does not declare theirs.
  - **What it costs:** an org's ledger begins with no record of its own creation. The `created_at` on `01-F68`'s record is the fact, and it is a directory fact rather than a ledger one.
  - **Not decided here:** whether the owner the act creates may be stamped as the actor of their own signup — ids are client-minted UUIDv7 (`00 §6`), so the id *can* exist before the write, and the human did perform the act. It is cheap, it is arguable in both directions, and `01-F1` makes it permanent (§9.5).

- 28-F15 **A PUBLIC SIGNUP SURFACE DOES NOT SHIP WITHOUT A NAMED ADMISSION CONTROL, AND THIS DOCUMENT DOES NOT PICK ONE.** The requirement is that one exists and is named in the spec before the surface exists; the choice is a founder decision (§9.6).
  - **Why a requirement rather than a preference.** Today the corpus has exactly one unauthenticated procedure (login) and no verification, invite or reset flow. Signup would be the second, and it mints an `org_id` that `01-F68` says can never be reused, in a pooled deployment that has no quota of any kind (`28-F6`) and, per `28-F9`, no automatic suspension lever. **Every junk org is therefore permanent**, and it shares a database, a Redis and the serving processes with real tenants. `15-F26` notes that provisioning is not destructive, so `15-F2`'s typed confirmation does not apply — which removes the only friction the corpus has.
  - **What may NOT be used as the control:** anything that gates the *till*. Admission control belongs at signup, before a tenant exists; once an org has a device it is `01-F17` territory and nothing commercial reaches it (`28-F8`).
  - **The candidates, listed without a choice being made:** an invite code issued by the vendor (closest to `15-F26`'s staffed path, and it survives a public form); email verification before the org is created; a vendor approval step between form and creation; a rate limit on creation per source. Each has a different failure mode and one of them must be chosen before the surface is built, not after.

### Vendor identity

- 28-F16 **A PLATFORM OPERATOR IS NOT A TENANT ROLE.** `ROLES` is not extended, `15-F1`'s four internal roles (support / onboarding / fleet-ops / platform-admin) are not columns in the permission matrix, and no vendor staff account holds an owner role inside a tenant.
  - **`15 §8` already ruled the structure** — internal tRPC router split from tenant routers at the gateway, internal tokens never valid on tenant APIs and vice versa, separate auth domains — and this FR states the identity consequence that clause implies and never says.
  - **Adding a fifth column is worse than it looks.** The verdict table is exhaustive: a new role forces a cell in every row in a single edit, so 24-plus policy decisions would be invented at once under type-checker pressure, and a vendor would then be assignable to a tenant *branch* through an ordinary per-location assignment.
  - **The alternative that must also be refused:** giving vendor staff an owner account in each tenant. That is the shared-credential path `15-F26` and `15-F16` exist to forbid — `15-F3`'s audit cannot separate a shared secret from the owner's own later acts.
  - **The unresolved shape this leaves, and it is real:** `14 §1` says the back office is used by *"the vendor onboarding team (acting as scoped org users)"*, `15-F9` says its output is *"attributed to the onboarding actor"*, and Appendix A's recipe row reads *"✔ (or vendor onboarding team)"* — the corpus asks for a vendor identity inside a tenant in three places and supplies no value for it. Under this FR the answer is `15-F15`'s consent-scoped impersonation and nothing else (`28-F19`), which is why `28-F19`'s gap is blocking rather than cosmetic.

- 28-F17 **THE INTERNAL PLANE OWES THE BOOT-ASSERTED GATE THE TENANT PLANE ALREADY HAS.** On the tenant plane every procedure is built with an authorization gate and the server refuses at boot to host one that is not. The internal plane has no equivalent, so an ungated internal procedure is a code-review question rather than a build failure — on the plane whose subjects can see more than one tenant.
  - **The requirement is the discipline, not the vocabulary.** The internal action set and its role mapping belong to doc 15 (`15-F1`'s four roles, `15-F2`'s platform-admin-only destructive acts); what this document requires is that whatever they are, an internal procedure that names none of them cannot be served.
  - **⚠ WHICH MAKES THIS FR UNBUILDABLE TODAY, AND IT IS SAID HERE RATHER THAN DISCOVERED AT THE KEYBOARD.** Doc 15 has four **roles** (`15-F1`) and one destructive-act rule (`15-F2`) and **no action vocabulary of any kind** — there is nothing for an internal procedure to name. So an implementer either invents the action names, which is commandment 2 at exactly the scale the bullet below refuses for the verdict matrix, or ships nothing and leaves this FR satisfied by a comment. **Owed to doc 15 by name**, on the same terms as `28-F14`'s payloads and `28-F19`'s schemas: *a catalog entry with no schema makes a path unbuildable rather than merely unbuilt*, and an assertion with no vocabulary is that sentence one layer up.
  - **It is not the tenant matrix.** Reusing `PERMISSION_ACTIONS` for internal roles would breach `15 §8`'s domain separation and would collide with `28-F16`. Two vocabularies, two planes, one discipline.

- 28-F18 **CROSS-TENANT REACH HAS EXACTLY THREE SANCTIONED PATHS, AND EACH IS OWED A `01-F71` CLAUSE.** `01-F71` states the property absolutely — a subject authenticated in one org must never read, write, cause a write in, or be fanned out data belonging to another, on either plane, through any surface, in any degraded state — and it contains **no carve-out**, while doc 15 specifies two surfaces that are cross-tenant by construction and the deployment already runs a third.
  - **(a) Fleet-health facts** (`15-F11`/`15-F12`/`15-F13`): version, printer status, sync lag, storage, battery, clock skew, last-seen, every value carrying its age. These are *operational facts about devices*, not an org's business data, and a vendor operator reads them across the fleet by design.
  - **(b) An org's own data**, reachable only through `15-F15`/`15-F16`: consent-scoped, time-boxed (≤ 4 h), dual-identity impersonation, bracketed by audit events in **that org's** ledger, with no break-glass. There is no lighter path, and `15-F18`'s diagnostics bundle is not one — that FR constrains the bundle's *content* (`15-N4`: no customer PII, redaction-tested) and says nothing about the authority to pull it, which is a gap doc 15 owns (§9.12).
  - **(c) The `services/api` → gateway `/internal` hop, which is the only one of the three that actually SHIPS.** Draft 1 said *"exactly two"* and `28-F5` (b′) documented this hop in the same document as something that *"must"* exist and pointed at this register to constrain it — so the register did not contain the path it was cited as constraining, which is the precise failure `01-F71`'s own governance sentence describes. Measured August 2026: the API reaches `/internal/tenancy`, `/internal/devices`, `/internal/org-events` and `/internal/catalog/published` with `org_id` as a query parameter, and every `/internal` route sits behind **one shared bearer token with no role, no action and no per-org scope** (absent, the routes fail closed). For 5–10 tenants that hop carries every org name, branch list, device list and catalog history in the deployment. Its constraint is `28-F17`'s owed boot-asserted internal gate; its clause in `01-F71` is owed on the same terms as (a) and (b), and it is the one to land first because it is the one with traffic on it.
  - **The governance clause, and it is the whole point of naming them:** each is an enforcement point, `01-F71` says in terms that *adding an enforcement point adds a clause here — the list is the register, and an unlisted check is one no test is aimed at*, and neither is in that register. So each is owed a clause in `01-F71` plus a test that fails when **that point alone** is removed. Until then the fleet dashboard is a cross-tenant read with no named enforcement point, which is the state `01-F71` was written to end. This document deliberately does **not** open a second isolation register.
  - **A fourth cross-tenant path exists and is not a session at all:** scheduled jobs enumerate every org with no authenticated subject anywhere in the path (the Auditor is the shipping example). Whether a job is a subject of `01-F71`, and what constrains one if it is not, is **not decided here** (§9.11).

- 28-F19 **THE ONLY SANCTIONED CROSS-TENANT DATA PATH DOES NOT RUN, AND THIS DOCUMENT ROUTES THE GAP RATHER THAN FILLING IT.** `15-F15`'s impersonation is unbuildable today, for two independent reasons, and a document that assumes it works would be assuming its way past the corpus's own recurring defect.
  - **(i) No payload schema.** `15 §2` calls the two impersonation events *"an extension to `01 §4`"* and the catalog carries only the `audit.*` wildcard; `packages/domain` ships a closed set of audit subtypes with neither member in it. Under `01-F4` both emits are a runtime error. This is exactly the shape `05-F7`'s approval family had — a catalog entry with no schema makes a path *unbuildable* rather than merely unbuilt — and the fix shape is the same: declare the payloads in the deciding FR.
  - **(ii) No second identity.** `15-F15` requires every action in the session to carry **both** identities, and the envelope has one nullable actor field, with `01-F63`/`11-F20` pushing attribution onto the envelope and refusing an actor field inside a payload. The corpus's own answer to *two people, one event* is `05-F7`'s `approval.granted`, which carries an approver and a requester as two separately-required payload fields so `02-F41`'s two-identity property survives.
  - **Ownership:** the schemas are doc 15's to declare and doc 01's to absorb. This document records the dependency because `28-F16` and `28-F18` both terminate on it — a vendor's only legal route into a tenant's data is a path that throws on its first emit.

### Tenant isolation at the serving layer

- 28-F20 **THE API'S PER-PROCESS ORG CONFIGURATION IS THE MEASURED GAP, AND CLOSING IT MOVES CHECKS RATHER THAN DELETING THEM.** `01-F71` names four enforcement points on the kernel and the gateway and none on the serving layer, because the serving layer does not currently have a tenant axis to enforce: `services/api` and `apps/backoffice` resolve one org and one enabled `(branch, channel)` set **per process**, from boot configuration. Isolation there rests on there being only one tenant, which stops being true on the first pilot.
  - **The requirement, in three parts.** (i) Every serving-layer request resolves its org from the authenticated subject (`01-F71` (b)) — the process holds no default org and no bootstrap org. **What replaces the bootstrap seed is named, because this FR's own next bullet is a warning about deletions that look like moves:** the seed exists as the documented quickstart and so that a laptop with no Postgres can still open the back office, and its replacement is `15-F27`'s declared owner-creation step run against a local database, with the runbook and the env example edited **in the same change**. Dropping the seed without moving the quickstart is not this requirement being met; it is a developer who can no longer log in. (ii) The org-scoped data context is bound once per request, so a port or repository cannot be called without one; a `where org_id = …` at a call site is how one query implements isolation and is explicitly **not** what satisfies `01-F71`. (iii) The enabled `(branch, channel)` set is per-org **layer-2** data resolved from one declaration — the same one `01-F60`'s writer refuses against and `14-F29`'s grid is drawn from — one authority, no fallback. It is **not** `28-F6`'s entitlement record and must not be built as it (`28-F6`). **Which layer owns it is ruled — layer 2, per `01-F60`'s own source clause and `00 §7`** (`28-F6`) — so (iii) is not blocked on a founder decision, and Draft 1's *"owed before (iii) is built"* marker is withdrawn as an error rather than satisfied. What is still open (§9.15) is the composition residual, which does not gate this requirement: a layer-1 flag that subtracts from the layer-2 set changes which columns the set may contain, never who declares it.
  - **⚠ The deletion must MOVE the check, not drop it.** When the back office's environment module was deleted, `02-F42`'s closed-channel check was nearly deleted with it, because moving the authority and removing the file look identical in a diff and no rail can see the difference. The same hazard sits on every boot-configured tenant fact being removed here, and the evidence for how invisible it is: restoring the client-side fallback failed **0 of 95** pre-existing tests with `pnpm verify` and `pnpm seams:check` clean.
  - **Requirement (ii) IS an enforcement point the moment it is built, so its `01-F71` clause is owed UNCONDITIONALLY.** `01-F71` states it without a condition — *"adding an enforcement point adds a clause here — the list is the register, and an unlisted check is one no test is aimed at"* — and a conditional is exactly how a check ends up unlisted, aimed at by no test, and collapsed back to a `where org_id = …` at call sites by a later refactor with every rail green. Draft 1 wrote *"if this becomes"*; it is not conditional. So the clause plus its two-tenant single-point mutation test (`28-N3`) are owed to doc 01 **in the change that builds the binding**, not after it — and not as a second register in this document.
  - **One join key with three ends survives regardless, and it has no error message:** the API's org must equal the device's configured org, and the enabled branch set must contain the device's branch, or all processes report success and no till ever sees a menu. Nothing checks the second agreement today.

- 28-F21 **A DATABASE-LAYER GATE IS NOT DECIDED HERE, AND `01-F68`'s FOREIGN-KEY BAN IS NOT A BAN ON ONE.** Whether the pooled deployment adds row-level security beneath the application scoping is a founder decision (§9.8). What is decided is what such a gate must and must not be if it lands.
  - **⚠ THIS IS A DELIBERATE REFUSAL TO RULE, NOT AN OVERSIGHT, AND THE PLAN ASKED FOR A RULING.** `plans/saas-pivot/reconciliation.md` assigns *"a ruling on RLS"* to this document and FORK 2 prices *"RLS (a migration + `SET LOCAL` + a second role)"* as one of five named pooling blockers; `plans/saas-pivot/plan-of-record.md` W4 schedules **Postgres RLS** as build work gated on this document existing. So *"the corpus is silent"* is true of the FRs and **false of the plan**, and §9.8 says so now. The reason the ruling is still owed to the founder is the measurement in the next bullet, which did not exist when FORK 2 priced it: a policy landing on the ingest path wedges a device's outbox permanently, which is not a migration cost but a `01-F17` hazard, and it changes what is being agreed to. What this FR does is remove everything from that decision except the yes/no — scope, keying rule, forbidden paths and the owed `01-F71` clause are all fixed below.
  - **The two are one keystroke apart in English and nothing alike in code.** `01-F68` forbids a foreign key from any ledger table to the org record, **ever**, because a referential constraint refuses ingest for an org that has events and no directory row — refusing a sale a till already rang. A row policy is a different mechanism: it consults no directory. Reading the ban as covering both would refuse a real defence; reading it as covering neither would reintroduce the ban's own failure through the back door — **and a row policy on the ingest path is exactly that back door**, which is why the scope below is binding rather than advisory.
  - **⚠ IT BINDS THE TENANT-SERVING PLANE ONLY. IT IS FORBIDDEN ON THE INGEST/MERGE PATH AND ON SUBJECT-LESS SCHEDULED WORK.** Draft 1 said a per-connection policy *"does not touch ingest"*; that is an assumption about the mechanism, not a property of the shipping host, and it is stated here rather than left to `28-F8`'s general ban because `28-F21` is the FR someone building row-level security will read. Measured August 2026: the gateway authenticates a **device token** and reads its registry row — there is no resolved *subject* anywhere on that path — and then performs the whole push inside one transaction on one shared connection handle, inserting the kernel `events` table, the quarantine and its notices with no per-connection tenant variable; and `services/jobs` enumerates every org with no authenticated subject at all (`28-F18`'s third path, §9.11). A policy landing on the kernel `events` table there refuses the INSERT as a **database error rather than an `01-F37` quarantine**, so it fills **no lamport slot**, `push_ack` never advances (`01-F8`), and that device's outbox wedges permanently — while `22-F21` says the device holds the **only copy** of every sale in it. The Auditor, meanwhile, reads nothing and reports every org clean. **`28-F8`'s second bullet is carried here as a constraint on the policy itself:** if a refusal is ever specified at the gateway for any reason, it fills its lamport slot.
  - **Therefore, if it lands (serving plane):** the policy keys on a value set per connection from the request's already-resolved subject, and **never joins the org registry**; and it is added as a clause on `01-F71` with a test that fails when that point alone is removed. A defence-in-depth layer with no clause is a security mechanism nobody can point at, which a refactor removes silently — the precise state `01-F71` exists to end.
  - **What it does not license:** per-tenant kernel behaviour of any kind. `01 §1` runs the identical kernel for every tier and profile, `15 §7` forbids per-org kernel behaviour differences, and `01-F69` refuses a per-branch timezone by name. A tenancy mechanism may change *who sees what*; it may never change *what the kernel does*.

## 4. Key flows

**Self-serve signup → first branch → go-live**
**⚠ THIS WALK IS THE INTENDED SHAPE AND IT IS NOT WALKABLE TODAY — steps 3 and 4 both terminate on unbuilt surfaces. Read it with `28-F13`'s two owed clauses, not as a build sequence.**
1. A prospect completes the signup form, past whatever admission control §9.6 selects (`28-F15`).
2. One act creates the org (`active`) and its first owner (`28-F13`). No branch, no device, no event (`28-F14`). A failure at either record abandons the `org_id`.
3. The owner sets their credential and signs in to the back office (`14-F1`); the wizard (`14-F26`) collects the first branch, users, devices and printers. **⚠ Blocked twice: the credential has no delivery channel (§9.21) and the wizard does not exist, nor does `01-F25`'s pairing code — both owed, `28-F13`.**
4. The go-live checklist (`14-F27`) gates going live, on the branch's **declared** capabilities (`15-F10` as amended by `DEC-HW-001`) — it never requires hardware the restaurant does not have. **⚠ Blocked: `15-F10`'s runbook, which feeds those items, is a vendor-staffed instrument, so a self-onboarded tenant cannot complete the checklist and no self-serve pilot goes live until §9.14 is answered.**

**A capability refused for want of entitlement**
1. A cloud request arrives; the subject resolves, carrying its org (`01-F71` (b)).
2. `can()` decides the subject may perform the action.
3. `entitled(org, capability)` is resolved from per-org data (`28-F5`) and returns no.
4. The surface says so honestly and names the reason (`00 §5.7`, `14-F37` — a disabled control explains nothing), rather than hiding the control.
5. *If the entitlement state cannot be read at all*, the cloud capability is refused as unreadable (`28-F8`) — a different answer from "not entitled", and the surface says which.
6. **Nothing in this flow can occur in a branch** (`28-F7`).

**Suspension and reactivation** — unchanged from `15-F7`/`15 §4`: an administrative act under `15-F2`'s typed confirmation, `config.changed` in the org's own ledger, cloud services gated with an honest notice, sync still accepted, in-branch billing untouched, reversal effective within `15-N2`'s cloud-side bound. No entitlement or plan state can initiate it (`28-F9`). **⚠ WHICH CLOUD SERVICES, MEASURED RATHER THAN ASSUMED:** `15-F7`'s two enumerated effects are *storefront down* and *new cloud-originated orders blocked*, and both are **inert today** — the storefront is a two-line stub. The cloud surfaces that do exist are the catalog save/enabled/history procedures, the device list and revoke, the change history and the nightly summary, and **no FR in doc 15 or this document says whether any of them is a "cloud service" for `15-F7`'s purposes** — so today a suspended tenant's owner can still edit a price and revoke a stolen till, or cannot, depending on which procedure author decides. That is §9.23. Note what is *not* in doubt: the till keeps selling (`28-F8`), which is the half a Friday evening turns on.

**Closing a pilot**
1. Offer and generate the owner's export (`22-F16`) — **and drain every reachable device's outbox first** (`28-F10`), recording any device that could not be drained.
2. Revoke every device (`14-F13`, `01-F42`, evicted within `01-F48`'s bound where a path reaches them).
3. Suspend with the reason recorded (`15-F7`). The ledger stays (`28-F11`); the org stays `active`-or-`suspended` and never becomes `closed` (`15-F25`).

## 6. Non-functional requirements (module-specific)

- 28-N1 An entitlement decision is server-side and per-operation (`01-F27`) and adds **no network hop**: the subject is already resolved and carries its org, and there is no per-device or per-branch resolution to wait on (`28-F7`).
- 28-N2 **`15-N2` IS INHERITED VERBATIM AND NOTHING IS RE-SIZED HERE.** `15-N2` reads *"Flag/kill-switch propagation ≤ 5 min **to online devices**; suspension/reactivation effective **cloud-side** ≤ 5 min"*, and Draft 1 inherited it *"in two halves"* that were **its two halves swapped** — it gave the device leg to suspension, which `15-N2` bounds cloud-side only, and took it away from flags, which is where `15-N2` and `15-F22` both put it. Corrected:
  - **Entitlement changes are cloud-side ≤ 5 min, which is `15-N2`'s suspension bound reused for a cloud-side fact, and they have no device leg** — there is no entitlement cache, no admission-path payload and nothing to propagate (`28-F7`).
  - **Whether that contradicts `15-N2`'s first half depends on which FR that half sizes, and the corpus does not say.** `15-N2` says *"flag/kill-switch"*; `15-F22` — *"kill-switch/feature flags … effective ≤ 5 min for online devices"* — is the natural referent and is an **operational kill switch**, not `15-F5`'s enablement, and this document owns neither. **Read narrowly, nothing here touches `15-N2`.** Read as covering `15-F5`'s flags too, `28-F7` amends it — and that amendment is then **owed to doc 15 by name**, not performed by an NFR quietly widening its own scope.
  - **The suspension banner gets NO number here**, because `15-N2` gives suspension only a cloud-side bound, `15-F7` says only *"within minutes"*, and there is no field on any wire that carries it (`28-F7`'s ⚠ bullet: no producer, no field, no consumer). **A bound sized against a path that does not exist is a number nothing can be measured against**, which is why Draft 1's ≤ 5 min device leg is withdrawn rather than kept as an aspiration.
- 28-N3 Every cross-tenant assertion in this document's area runs **two tenants** and is mutation-proved per `01-F71`: a suite exercising one tenant passes with the enforcement deleted, so a green single-tenant suite is not evidence of anything here. **The register that names each such point is `01-F71`'s, not this section's** — an NFR is a property, not a list, and a check recorded only here is one nothing enumerates.
- **Numbers deliberately absent, each because inventing it is the failure this document exists to prevent:** any branch, device, user, storage or event-volume quota; a signup rate limit; a trial length; a grace period; an entitlement cache TTL (there is no cache — `28-F7`); a retention period for a churned tenant.

## 7. Customizability

Entitlement is **layer 1** (`00 §7`: provisioning, feature flags and tier enablement are the vendor's), and a lower layer cannot override it. Layer 2 configures *within* what layer 1 has enabled — `14-F19`'s channel configuration is already gated by layer-1 channel flags. *`01-F60`'s enabled `(branch, channel)` set is **layer-2** data and not an entitlement (`01-F60` names `00 §7` layer 2 as its source; `00 §7` lists "channels enabled" under layer 2 and nowhere else). The open residual is composition, not ownership: §9.15.*

- **A tenant configures nothing about its own entitlement.** No self-service plan change, no self-granted flag, no quota adjustment.
- **Deliberately not configurable, ever:** any lever by which a commercial state reaches a sale (`28-F8`); any per-org kernel behaviour difference (`01 §1`, `15 §7`); anything on `22 §7`'s never-configurable list (disabling backups, shortening event retention, weakening `22-F1`/`22-F2`); a third lifecycle state (`28-F2`); a tenant-supplied org identifier on any request (`28-F5` (b)).
- **Not free-form.** `00 §7`'s *presets, not knobs* binds this module: the flag set is `15-F5`'s enumeration resolved per org, not an open key–value bag.

## 8. Tech notes

- **Two planes, two auth domains, two vocabularies** (`18 §6`, `15 §8`): internal routers split from tenant routers at the gateway; internal tokens never valid on tenant APIs and vice versa; the tenant permission matrix is not extended with vendor roles (`28-F16`).
- **The gate composes at existing choke points.** `can()` then `entitled()`, both server-side (`18 §5`, commandment 8). ⚠ *What boot asserts is a **declaration**, never an entitlement* — `28-F4` corrects Draft 1's *"an ungated or unentitled procedure is a boot failure"* in terms, and this line said it too. Entitlement is a per-org runtime fact and boot cannot see one. The internal plane's equivalent assertion is `28-F17` and is **owed a vocabulary from doc 15** before it can exist at all.
- **No foreign key to the org record, ever** (`01-F68`), including from any table this document introduces — atomicity and ordering live at the writer (`15-F27`).
- **Structured tenancy keys only** — `(org, branch)` as a pair, never a concatenated string; `("ab","c")` and `("a","bc")` are different tenants (`01-F71` (d)).
- **The seam this document is most likely to lose:** an entitlement port supplied with a permissive stub reads exactly like a supplied port to `pnpm seams:check` — Rule B asks whether an optional member is supplied, never whether what was supplied is real. The assertion that the shipping construction passes the **real** resolver has to be written by hand.

4. **Where does the RESOLVED entitlement read model durably live** — derived from the org's own ledger, or held in platform tables outside org ledgers (`15 §2`/`15 §5`, where staff accounts, meters and the platform audit log sit) and reconciled? ⚠ *Draft 1 posed this as ledger-**or**-platform-tables, which invites an implementation that emits nothing: the ledger event is **not** optional — `15-F5` requires a `config.changed` with actor per flag change and `15-F25` says the same for lifecycle, and §2/§5 of this document state it as settled.* So the open part is only where the value the **gate reads** lives.
