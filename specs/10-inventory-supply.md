## 1. Purpose & scope

The supply plane: theoretical stock maintained by recipe-chain deduction from the sales exhaust, purchasing with supplier ledger, production of prepared items, inter-location transfers, wastage logging, guided physical counts with PKR-valued variance, demand-driven prep planning, and a simple explainable forecasting service.

- **Who uses it:** storekeeper/purchaser (photo invoices, counts, transfers), chef/prep staff (prep suggestions, production entry), branch manager (alerts, discrepancies), owner (variance/purchase/wastage views via doc 12). Recipes and par levels are set up ~~by the vendor onboarding team via doc 15 tooling — **owners never do recipe data entry**~~ **by the OWNER in the back office (14-F9), and the RestOS team uses the same editor on a pilot's behalf** — founder decision 2, August 2026. Doc 14 was already right (14-F9: *"editable by the vendor onboarding team **and permitted org users only**"*) and the recipe-edit permission action is already owner-only in the shipped matrix, so this costs nothing in code; 15-F9's workbench survives unchanged as *the same editor with a different actor*. **10-F31's completeness ramp depends on this ruling** — it converges only if an owner can close a cost gap without booking a vendor session. The real cost is support, not build: a wrong recipe silently mis-costs every dish, which is what 10-F31's dish gate and blocking-item list exist to make loud.
- **Runs on:** cloud service (deduction, variance, forecasting) + back office UI (doc 14) + mobile flows on branch devices (docs 02/05 host the count, invoice, wastage, production surfaces).
- **Tiers/profiles:** all tiers. Value is gated by tracked-item onboarding, not hardware tier. Multi-branch orgs additionally get transfers between branch/prep_kitchen/storage locations.
- **Discipline (`restaurant-os.md` Appendix D, binding — ⚠ AMENDED here August 2026 under this doc's own header licence, *"carried over wholesale unless amended here"*; Appendix D carries a pointer so the seed stays readable on its own):** ~~track only the top 10–20 high-cost ingredients (~70% of food cost)~~ **COUNT only the top 10–20 high-cost ingredients; COST everything (10-F31).** The struck sentence bound both scopes to one flag, and under it a fully complete recipe still costs ~70% of a dish — so a food-cost figure would understate by ~30% permanently, by design, which is larger than most of the gaps this module exists to find. Staff gain **at most two new habits** and that is unchanged: photographing purchase invoices and the periodic guided count. The split moves an estimated 20–40 rows from a recurring workload to a **one-time** onboarding one; nothing recurring grows. Everything else is a side-effect or derived.

## 3. Functional requirements

**Stock model & automatic deduction**
- 10-F1 Stock always exists at a location (branch | prep_kitchen | storage — 01-F25 types). Item types: raw | prepared. Unit conversions purchase unit → stock unit (e.g. "bag of 10 kg" → kg); quantities are integer mg/ml/units (00 §6).
- 10-F2 ~~Only items with `is_tracked` participate in deduction, counts, variance, and alerts. Untracked items exist in the catalog but generate zero inventory workload.~~ **SUPERSEDED August 2026 by 10-F31** (founder decision 3), which splits the single flag into `is_counted` and `is_costed` because its four consequences do not follow the same discipline: three of them spend `10-N2`'s count budget and one does not. The ID is kept and never renumbered (`00 §8`); the rule is 10-F31's.
- 10-F3 Every sale on every channel deducts theoretical stock through the recipe chain (menu recipe → raw + prepared; prepared → prep recipe) at the selling location. **Single canonical trigger, channel-agnostic:** ~~a line belongs to deduction iff it is part of a **confirmed** order (`order.confirmed`, or `line_added` after confirm) and was not removed pre-confirm~~ **AMENDED August 2026 — both struck clauses are ORDERING predicates and neither is computable on either plane.** `01-F34` gives a fold no ordering metadata at all, and that FR's superseded clause withdrew `global_seq` as a cloud-side business arbiter, so *"after confirm"* has no legal source anywhere; `03-F55` confirms post-confirm additions are contemplated, so this is not hypothetical. **The order-free restatement, which is what is built:** the deduction set is `{ lines named by order.line_added } − { lines named by order.line_removed }`, for every order for which an `order.confirmed` exists. A set difference over two grow-only sets is convergent, relabel-invariant and clock-free (`26 §7`'s first merge rule), so it needs no exemption — and it is built to `01-F34` **as if it were a device fold even though it runs in the cloud**, which keeps the option of moving it device-side. **What it loses, stated rather than discovered later:** a line removed *after* confirm exempts itself, where the struck clause says it should not. The mitigation already ships and is not in the fold — `01 §4`'s dagger makes post-KOT removal a `void.recorded`, and the matrix separates `order.line_removed` (cashier allow) from `void.recorded` (cashier deny, escalate) — so a cashier taking the cheap path is a **permission-gate** finding, not a deduction defect, and the fix belongs at the void gate. KOT printing and channel of origin remain irrelevant to the invariant. Idempotency key per derived movement row: `(order_line_id, recipe_version)` — one deduction per line, recomputable on recipe correction (10-F4), never doubled by retries or duplicate events. *(Automation law: side-effect of billing.)*
- 10-F4 Physical actions (purchase, transfer, production, wastage, count adjustment) are kernel events and are never recomputed. Sale deductions are **derived** movement rows in the read model, each citing order line id + recipe version — recomputable when a recipe mapping is corrected. The order stream is the fact; deduction is math.
- 10-F5 Theoretical stock may go negative (offline oversell, coverage gaps) — allowed and flagged, never blocks a sale (01-F17); reconciled at next count.
- 10-F6 Moving-average cost per item per location, ~~integer paisas per base unit, updated on each purchase receipt~~ **AMENDED August 2026 by 10-F28 — the struck clause is ORDER-DEPENDENT and therefore illegal under `01-F34`.** A running average interleaved with issues values those issues differently depending on the order receipts and issues arrive, so delivery order decided a money outcome — the exact failure `26 §2` exists to remove. It is now the **period-weighted average** of opening value plus receipts, per (item, location, period), held as the **pair** `(value_paisa, qty_base)` and never as a stored unit rate: a cost per base unit is a rate and will not be an integer. All PKR valuations in this module use it.
- 10-F7 Post-KOT voids and comps still consume stock (the food was made); pre-KOT line removals do not. Variance attribution (10-F19) relies on this distinction.
- 10-F8 Sold items with no recipe mapping are listed as coverage gaps; their deduction is skipped and the variance report states recipe-coverage % of ~~sales~~ **REVENUE (amended August 2026 — 13-F5, 14-F10 and 15-F9 all say revenue and this doc said "sales", so one number had two denominators), counting a COSTABLE recipe rather than a merely mapped one**: a dish whose recipe points at an unpriced ingredient is *covered* under the struck reading and cannot be costed, which is the gap 10-F31 exists to make loud. So gaps are never misread as theft.

**Guided count & variance**
- 10-F17 Guided count on a phone/tablet **(amended August 2026: the DEVICE is a layer-3 choice — §7 already places *"which station device hosts the count flow"* there — so a till surface is in contract and a phone port is a port, not a precondition; founder decision 4, *"which device doesn't matter"*)**: `is_counted` items only (10-F31), presented in ~~per-location storage-layout order~~ **per-AREA storage-layout order with a line per `(item, area)` (10-F30)**, tap-to-enter quantities **at the partial tier the item declares, with an explicit *not counted* that is not a zero (10-F29)**; target ≤ 15 min; resumable within the same business day → `stock.count_recorded`. **The count is BLIND — it shows no expected quantity** (a device cannot legally hold one; see §4 Flow A step 2 — and blind counting is the industry's own best practice because it prevents anchoring, so this is got for free rather than chosen). *(Scheduled verified ritual.)*
- 10-F18 Variance per item for the period since last count **(the period is 10-F28's, and a closed one is immutable)**: opening + purchases + transfers-in − theoretical consumption − wastage − transfers-out = expected closing; vs counted. Gap valued in PKR at ~~moving-average~~ **period (10-F6/10-F28)** cost. **An item that is *not counted* (10-F29) carries NO gap in either unit and is rendered as *not counted*, never as zero variance; the report's PKR total is then a FLOOR and says so** — `00 §5.7` prefers a stated absence to a confident smaller number. The row carries the count's **basis** (10-F29), and a gap inside its own measurement error is not shown as a gap at all (10-F33). The quantity column needs no cost and is never gated; the money column is complete by construction because 10-F31's `is_counted ⇒ is_costed` invariant is enforced at the writer.
- 10-F19 Attribution hints, never accusation: "gap concentrated on days X, Y", ~~"gap exceeds all voids+wastage logged"~~ **AMENDED August 2026 — that clause compares a COST with a SELLING PRICE.** The gap is valued at cost (10-F18) and `void.recorded.amount_paisa` is a selling price, so the void side is overstated by the gross margin — at a 70% food-cost target a factor of ~3, which makes the hint fire almost never and mislead when it does. And because a void names no line (10-F3), the void side **cannot** be restated in stock units without a `line_id` on `void.recorded`, which is a protected-path schema change on the money ledger and is not worth it for a hint. **The hint compares like with like — gap value at period cost against WASTAGE value at period cost, wastage being the sink that names its item and quantity (10-F32) — and voids enter as a separate, LABELLED COUNT, never summed into the same number.** Transfer-discrepancy correlation, steady-small-gap over-portioning signature. **Every hint is gated by 10-F33**: none fires on a single period, none fires on a gap inside the item's noise floor, and no hint may name a person or a role. The count writes an adjustment movement referencing the count event, resetting the theoretical baseline.
- 10-F20 Count schedule per org (2–3×/week presets). An overdue count raises `stock.count_overdue_flagged` to manager/owner — the count-skipped nag backing risk §9.4 (`restaurant-os.md`).

**The count period, the count line, and what a number is allowed to claim (August 2026 — founder decisions 3 and 4, rulings R74–R77)**

- 10-F28 **THE COUNT PERIOD.** A count period per **location** is opened by the previous `stock.count_recorded` and closed by the next; a location's first period has no opening and its report says so rather than assuming zero. **A closed period's derived movements, valuation and variance report are IMMUTABLE**; a recipe correction (10-F4) re-derives **only the open period** and applies forward. **Period cost is the weighted average of opening value plus receipts — `(opening_value + purchases_value) / (opening_qty + purchases_qty)` per (item, location, period) — held as the PAIR `(value_paisa, qty_base)` and never as a stored unit rate.** A quantity is valued by one exact multiply-then-round, `round(qty × value_paisa / qty_base)`, accumulated in **BigInt** (`00 §6`, law 3); §8's *"no cumulative drift vs exact rational computation"* is then satisfied **by construction**, because no running accumulation is left to drift. **It fixes three defects at once, which is why it is the first thing built:** 10-F4's recompute had nothing to bound it, so a correction could re-derive a window containing a count adjustment computed against the *old* derivation, and 10-F19 writes that adjustment as a kernel event which `01-F1` forbids fixing; 10-F6's running average was order-dependent; and *"the period since last count"* (10-F18) named an entity that existed nowhere in this doc. Amends 10-F6, 10-F18 and §8's moving-average note.
- 10-F29 **COUNT UNITS, THE PARTIAL TIER, THE LINE BASIS — AND `counted: false` IS A DISTINCT VALUE FROM `qty: 0`.** An item declares `count_units`: a `primary` whole-container unit, and at most **one** `partial` tier, `kind: none | fraction | weight`, **fixed per item at onboarding rather than chosen at count time** (the guidance every vendor publishes — *each item counted in the same unit every time* — turned into a schema field instead of a memo). `fraction` is an integer 0–9 **tenths, never a float**: `qty_base = containers × size + tenths × size / 10`, one exact multiply-then-round in BigInt, because a float tenth is how delivery order gets to decide a quantity. `weight` is legal **only where the partial unit and the base unit share a dimension** — weighing a bottle held in `ml` needs a density, and assuming 1 L = 1 kg is a fudge this module refuses, so an item is either held in mass or counted by tenths and never both. **No container tare weight is stored anywhere**: variance is a *difference* of two counts, so an unknown-but-constant tare cancels between the ends, while a wrong tare produces a number that looks like a fact — and a scale out of calibration does not announce itself. Two tiers is the cap; a third breaks 10-N2's ≤3 taps. **A count line is `{item_id, area_id, counted, qty_base?, basis}` with `basis: exact | weighed | estimated`, and the basis TRAVELS to the variance row** (`00 §7 (e)`'s rule that a resolved source travels with its value, one domain over). **`counted: false` carries NO `qty_base` at all**, so no arithmetic can consume it by accident; `counted: true, qty_base: 0` means *I looked and there is none*, which is a measurement and a large, real variance. **An item is counted iff EVERY one of its area lines is counted** (10-F30); otherwise 10-F18 renders it *not counted*. A blank is not a zero — the mainstream treats one as zero and then reports an untouched item as *variance is, by definition, zero*, so an uncounted item is indistinguishable from a perfect count on the page the owner reads. §4 Flow E's *"an abandoned count writes nothing"* is unchanged and is a **different case**: it covers the count never submitted; this covers the count **submitted with holes**, which is the more dangerous one because it produces a document. *Saved is not an event* — 10-F17's same-day resume is device-local partial state.
- 10-F30 **AN ITEM IS COUNTED IN ONE OR MORE AREAS; THE BALANCE STAYS AT `(item, location)`.** A storage area partitions the count **sheet**, never the **stock**. Area membership is reference data keyed `(item_id, location_id, area_id) → sort`; the sheet carries a line per row; the item's counted quantity is the **sum** of its area lines. No intra-branch transfer, no per-area balance, no per-area variance, no per-area cost. An org that declares no areas has exactly one implicit area and a sheet identical to a single-area one, so the default costs an existing pilot nothing. Amends 10-F17's singular *"per-location storage-layout order"*. **There is deliberately no mid-count area-creation flow:** a counter who finds an item in a room it is not declared in counts it into an existing area, and the owner fixes the reference data after. **Reopen trigger:** a bar or prep kitchen that reconciles *separately* — a separate balance, not a separate sheet — wants a `01-F25` **location**, which already exists; it does not want areas to grow into one.
- 10-F31 **WHAT IS COUNTED AND WHAT IS COSTED ARE TWO SCOPES, AND A COST FIGURE IS REFUSED UNLESS IT IS COMPLETE.** Supersedes 10-F2. **`is_counted`** carries counts (10-F17), variance (10-F18) and par alerts (10-F21): this is where Appendix D's 15 minutes go and its top-10–20 discipline is unchanged. **`is_costed`** carries deduction's derived movement rows for costing — math on events that already exist, costing no habit and no minute. **Why the split is forced:** a recipe 100% complete under any coverage rule you can write still costs only the tracked ~70% of a dish, so a rendered *"food cost 22%"* against a true ~31% understates by ~30% permanently and by construction, and a gate at 100% coverage does not touch it. **Two invariants, both enforced at the WRITER** (14-F29/01-F60's precedent — completeness is met where the owner types, never where the report is read): **`is_counted ⇒ is_costed`**, which is what makes 10-F18's PKR column complete by construction; and **every leaf item of every published recipe is `is_costed`**, which is the reachable form of *"every item is accounted for"*. **A cost basis per (item, location, period) resolves to exactly one of `receipted | reference | none`.** `receipted` is 10-F28's `(value, qty)` pair when `opening_qty + purchase_qty > 0`. `reference` is a back-office unit cost typed once on the item, carrying no receipt, no khata entry and no supplier — **a legitimate first answer, not a placeholder**, without which the onboarding ramp cannot terminate because salt bought quarterly never acquires a basis in a weekly period. `none` is neither, and every figure that would contain it is refused. A receipt line with **non-positive quantity does not enter the valuation** but still enters 10-F14's khata — money spent is money spent, and the two ledgers answer different questions. **An explicit `0` is a cost; an absent field is not** (01-F60's free-modifier argument, one domain over). **Three units of completeness, and they fail differently:** *item* — costable iff basis ≠ `none`; *dish* — **all-or-nothing per sellable**, requiring a menu recipe, an explosion that terminates (cycles are refused at the writer), and every leaf item costed, so complete → the plate cost with its basis mix and incomplete → **nothing**, plus the blocking item names; *window* — per (location, window), `costed_revenue_share` = billed revenue of lines whose sellable is costable ÷ billed revenue of all lines, on `01-F63`'s attested `billed_paisa` and never a second derivation of it, COMPLETE iff that share is exactly 1, no sold sellable lacks a recipe, and no consumption resolved to basis `none`. The dish gate fails **locally and repairably** and is enforced hard; the window gate fails **globally** and re-breaks on every menu change, which is why R75 refuses the publish that would break it. **THE RULE: a cost figure may be rendered iff every quantity in it resolves to a cost basis at the unit of the figure, and the figure states its unit and its basis.** **R1** an unqualified ratio (*food cost %*, *gross margin %*) requires COMPLETE for the window it covers; otherwise it is **omitted**, and the omission is rendered **as data** carrying what is missing and what would close it. **R2** a per-dish cost is all-or-nothing per dish. **R3** an absolute money figure may be shown at any coverage as a **labelled floor**, with `costed_revenue_share` in the same sentence, and never converted to a percentage of sales. **R4** a **scoped** ratio below COMPLETE is **not** shown (R76: a label beside a number is dropped by the reader, and this corpus has two recorded instances of exactly that on a shipped screen). **R5 — never:** a partial plate cost; a zero standing in for an unknown cost; a grossed-up estimate of an untracked residual; a percentage of sales below COMPLETE. **The gate belongs in 13-F5's metric registry, not in each surface** — implementing it per screen is how 01-F60's two declarations of one set happened, and it cost a whole session to unify. **Stated cost, because it is a trade and not a free lunch:** Appendix D's discipline survives on the **count** and is lifted off the **cost**, moving an estimated 20–40 rows from a recurring workload to a one-time onboarding one; no ongoing ritual grows, and that one-time cost is precisely where Appendix D said competitors die.
- 10-F32 **THREE SHRINK SINKS, AND THE FOURTH IS REFUSED.** Trim and prep loss (peel, stem, bone, the water a marinade drives off) → the **prep recipe's yield**, captured as *actual* yield on the production entry (10-F9, 10-F10). Spoilage someone finds and throws away → the **wastage log** (10-F16). Everything nobody logged — dehydration, unrecorded spoilage, over-portioning → the **count**, as variance (10-F18, 10-F19). **These are the only three.** **No automatic shrink or yield percentage on the raw item, at any configuration layer:** loss on a marinade is a property of the process on the night and not of the goat, and a shrink percentage is a guess that enters a ledger and comes out looking like a measurement — the same failure shape as a wrong tare (10-F29) and as a plate cost with a missing ingredient (10-F31), which is three instances of one shape inside one module. 10-F19's social licence does not survive a variance report whose baseline was quietly adjusted by an assumption nobody typed. **The cost, stated because it is real:** a restaurant that never logs wastage sees all three losses arrive as one undifferentiated gap and cannot tell rot from theft. That is 10-F16's own backstop working as written, and it is why the wastage log ships **with** the count rather than after it.
- 10-F33 **A GAP INSIDE ITS OWN MEASUREMENT ERROR IS NOT SHOWN AS A GAP, AND NO HINT FIRES ON ONE PERIOD.** *(R77. The governing constraint is the founder's: entry effort must not increase, or staff enter random values; and the system must still be accurate. The resolution is that effort stays flat and the system knows how precise each entry is — and the second-order effect matters as much, because **fabrication is driven by fear of the report**: a noise floor that makes an in-band gap unaccusable removes the incentive to round toward theory.)* **(a) A computed per-item noise floor**, from inputs this product already holds together and no surveyed competitor does — the line `basis` (10-F29), the container size, and theoretical consumption for the period: `floor ≈ k × basis_error × container_size × √2`, expressed as a share of period consumption. Inside it the row reads **"no reading this period"** — never `0`, never a small gap — which extends 10-F18's *not counted* treatment from *not counted* to *counted but not resolvable*. ⚠ **`k` is DELIBERATELY UNPINNED:** it is the multiple of the basis error at which a reading becomes reportable, it needs a pilot's data, and pinning it in a spec would repeat `DEFAULT_STATION`'s recorded mistake. An implementation declares it as **one named constant carrying that reason**, never as a literal at a use site. **(b) Rank and alert in PKR, never in percent** — 10-F18 already values the gap at period cost, so money is the sort key and the only alert unit; percent survives as a diagnostic *after* selection, never as a trigger. **(c) A hint fires only on a sustained SAME-SIGNED run** — about three consecutive periods above the item's floor with the same sign, ~1 week at 10-F20's cadence. **Sign is the discriminator: measurement error is zero-mean and flips, while theft, over-portioning and unlogged waste are one-signed.** This promotes 10-F19's steady-small-gap hint from *one hint* to the **gate on every hint**. **(d) Recount inside the count session:** the one or two biggest-money gaps are flagged **before the period closes and before anything reaches an owner**. A recount is a count line while the period is open — **no new event type**. **(e) No settable percentage tolerance ships**, and the reason is recorded so a later session does not add the missing setting: every vendor threshold is per category or per site and is a number a human guesses once — wrong in **unit** (percent, when the risk is money), wrong in **grain** (category, when the noise is per item) and wrong in **basis** (a guess, when the error is computable). (a) replaces its filtering, (b) its prioritisation, (c) its alerting. If a control is ever wanted, make it **currency**. **(f) Vocabulary is part of this FR, because this is a social problem before it is a technical one.** Use **"unexplained usage"** and the row form *"expected 4.2 kg, counted 3.6 kg"*. **BANNED: `shrinkage`, `loss`, `theft`, `missing`, and the euphemism `growth`.** 10-F19's causes-not-people becomes a **checkable invariant: no hint may name a person or a role.** **(g) The investigation ladder is data-first and theft is LAST:** (i) not counted, or an estimated basis; (ii) a receiving discrepancy this period (10-F12); (iii) a recipe or cost changed mid-period; (iv) **zero wastage logged on an item with a sustained gap — presume unlogged waste**, because published waste is 4–10% of purchases and the remedy is the waste button, not the staff; (v) a gap proportional to volume, the portioning signature. **(h) Aggregate only as a trend:** independent per-item errors shrink relatively by ≈√n, so a branch PKR total may be shown where an item row is refused — but that holds only for zero-mean error, and eyeball optimism is not zero-mean, so the branch total is shown **period-over-period**, where a constant bias cancels, and **never as a standalone absolute**. ⚠ **What this FR does NOT close:** `k`; the error figures behind `basis_error`, which rest on one ten-bottle head-to-head rather than a study and must say so **where they are declared**; and (h)'s independence assumption, which a single distracted counter violates. **Sequencing consequence, which is part of the ruling:** the **wastage log is built before the variance report is polished** — it is the largest measured non-noise term and its named failure is capture at the point of discard.

**Automation-law register (00 §5.8)** — every capture in this module, classified:

## 4. Key flows

**Flow A — Sale → deduction (fully automatic)**
1. Order line reaches kitchen commitment on any channel (KOT print / ingestion-confirm).
2. Event replicates to cloud (doc 01); the inventory fold ~~resolves the recipe version effective at the event time~~ **computes with the CURRENTLY PUBLISHED recipe version and records the version it was computed WITH — amended August 2026.** *"Effective at the event time"* is an ordering read and would need a per-event recipe lookup besides; `01-F53`'s precedent (snapshot the price at line-add) does not transfer, because the till does not hold the recipe and must not. A recipe correction re-derives the whole **open** period at the new version, replacing rows keyed by the old one (10-F4, 10-N6), and 10-F28's close freezes it — which is exactly 10-F3's `(order_line_id, recipe_version)` key already says. **Consequence, and it is a feature:** a device cannot hold a correct expected-stock number, so the count is **blind** by construction (10-F17).
3. Derived movement rows written (menu recipe → raw + prepared components; prepared components resolve through prep recipes for costing only — prepared stock itself moves on production, not sale).
4. Stock level updated at the selling location; par check runs; `stock.low_level_flagged` if breached and not already flagged today.
5. *Failure — no recipe:* item lands on the coverage-gap list; no movement written; variance report shows coverage %, so the gap is never misread as theft.
6. *Failure — WAN down for days:* nothing is lost; folds catch up on reconnect; device stock views show last-synced age (00 §5.7).

**Flow B — Purchase**
1. Storekeeper taps "purchase", photographs the invoice (offline OK; photo queued).
2. Smart-default form opens: last-used supplier preselected, that supplier's recent items with last prices prefilled.
3. Storekeeper confirms/edits item, qty (purchase units, converted), price; submits → `stock.purchase_recorded` with photo ref.
4. Moving-average cost updates; price-spike check runs (`stock.price_spike_flagged` if tripped); supplier khata balance updates.
5. *Failure — upload pending:* the record stands and deducts into ledgers immediately; the photo badge shows "uploading" until done.

**Flow C — Evening prep (suggestion → production)**
1. Nightly job publishes prep suggestions per prepared item per location, each with its evidence line.
2. Chef opens the prep list on the station device: "last 4 Fridays sold 43 karahis → marinate 25 kg tonight".
3. Chef confirms 25 kg or edits the quantity — this confirmation IS the production entry (10-F23).
4. `stock.production_recorded` (suggestion ref attached): raw consumed, prepared produced, actual yield captured.
5. *Failure — no confirmation:* the suggestion expires at day close; no stock fact is ever created from an unconfirmed suggestion.

**Flow D — Transfer with discrepancy**
1. Sender records items/quantities → `stock.transfer_sent`; stock moves to in-transit.
2. Receiver opens pending transfers, confirms received quantities → `stock.transfer_received`.
3. Received ≠ sent → discrepancy on the receive event → manager alert (doc 05); both locations' variance windows annotated.
4. *Failure — never received:* transfer stays in-transit and is flagged after a configured staleness window; in-transit stock belongs to neither location's count.

**Flow E — Guided count → variance**
1. Storekeeper/manager starts the count; items appear in storage-layout order, tracked items only.
2. Tap-to-enter each quantity (≤ 3 taps per item); resumable within the business day.
3. Submit → `stock.count_recorded` → variance report computed (< 30 s, 10-N3): expected vs counted per item, PKR-valued.
4. Attribution hints attached; owner alerted if the gap exceeds the org threshold; adjustment movement resets the baseline.
5. *Failure — count abandoned:* partial entries persist for same-day resume; an abandoned count writes nothing and the overdue clock keeps running.

## 8. Tech notes

- Lives as the `inventory` module inside the modular Node backend (00 §3 — no microservices); read models in Postgres via Drizzle; `stock_movements` partitioned org+month like the event table.
- Deduction is a deterministic fold keyed by (order line id, recipe version) — idempotent, replayable, property-tested alongside 01-N1.
- ~~Moving-average cost arithmetic: integer paisas, round half-up at movement granularity; property test proves no cumulative drift vs exact rational computation.~~ **AMENDED by 10-F28:** period-weighted cost held as the pair `(value_paisa, qty_base)`, accumulated in BigInt, valuing a quantity by one exact multiply-then-round. The drift property is then satisfied **by construction** rather than by a property test — there is no running accumulation left to drift — and the property test that remains is the useful one: **bijective id-relabel and clock-injection invariance** on every projected value (`01-F34`, law 1), which plain convergence testing does not catch.
- Statistics are pure TS (no ML dependencies): trailing means + same-weekday seasonality; every suggestion/forecast stores its input points as JSON for UI evidence and doc 13 citations.
- OCR for invoices deliberately deferred (see §9); the prefill + fast-confirm form is the shipped baseline (`restaurant-os.md` Appendix D).
- Count and invoice flows get Maestro tests; the rush-simulation replay (00 §4) is extended with an inventory-fold determinism assertion.
