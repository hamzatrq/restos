# 01 — Kernel: Event Ledger, Sync Mesh, Catalog, Customer File, Auth

**Module spec — Draft 1, July 2026** · Parent: `00-platform-overview.md` (conventions §5–§7 inherited). This is the foundation module — Wave 0. Every other module consumes it; it depends on nothing else.

## 1. Purpose & scope

The kernel is four things: (a) the **append-only event ledger** — the single source of truth for everything that happens in a restaurant; (b) the **sync mesh** — replication of that ledger between devices, branch LAN, and cloud; (c) the **shared reference data** — catalog (menu/recipes) and customer file; (d) **identity** — orgs, branches, devices, users, roles, sessions. It has no UI of its own; it ships as `packages/domain`, `packages/sync-client`, the cloud `sync-gateway`/`api-gateway` services, and the schemas under them.

All tiers and profiles run the identical kernel. A T1 single-terminal restaurant and a 5-branch fast-food org differ only in topology records, never in kernel behavior.

## 2. Position in platform

- **Consumed by:** every app and service (docs 02–17).
- **Depends on:** nothing internal. External: Postgres, Redis, object storage.
- **Emits/owns:** the event store itself; catalog and customer read models; auth/session/device registry.

## 3. Functional requirements

**Ledger**
- 01-F1 Append-only event log per org, following the canonical envelope (00 §6). No update/delete paths exist in any API. Corrections are new events referencing the corrected event id.
- 01-F2 Every device persists events locally (SQLite, WAL) before acknowledging the action to the UI. A confirmed action is a persisted event (plug-pull safe).
- 01-F3 Events carry `lamport_seq` per device (monotonic, persisted, gap-free). The cloud assigns `server_received_at` and a global org sequence on merge.
- 01-F4 The event-type catalog and payload schemas live in `packages/domain` (Zod). Producing an unknown/invalid event type is a build-time and runtime error.
- 01-F5 Audit events are ordinary kernel events, hash-chained per device: each carries the hash of the device's previous audit event. Concrete scheme (DEC-AUDIT-001, accepted): the `audit.*` family has **seven** subtypes — `audit.login`, `audit.drawer_opened`, `audit.reprint`, `audit.threshold_override`, `audit.settings_changed`, **`audit.print_acknowledged`** (added August 2026: `03-F5` requires that acknowledging a print-failure alert is "logged (`audit.*`)" and none of the original five fits, so the FR mandated an event the catalog could not express — found when K-7 wired the alert and had nowhere to record the ack. It belongs in this family rather than beside `kot.*` for the reason `audit.drawer_opened` does: silently dismissing the band **loses a kitchen ticket with nobody accountable**, and the hash chain is what makes a quiet dismissal detectable), and **`audit.alarm_acknowledged`** (added August 2026 for the same reason one subtype later, and the repeat is the point: `05-F2` requires that a manager's acknowledgment of an alarm is "logged (`audit.*`, hash-chained per 01-F5)", and **none of the other six fits** — so `01-F4` refused the emit and *every alarm on the manager console was permanent*, which `apps/manager/src/alarms.ts` had recorded as unbuildable rather than guessed at. **The near miss, stated because a later session will reach for it:** `audit.print_acknowledged` is `03-F5`'s TILL band, whose subject is a print JOB the spooler minted an id for. Recording a LATE-ORDER alarm ack under it would assert in an append-only ledger (`01-F1`) that a print was acknowledged when nothing printed and no printer was involved — the same permanent falsehood `printing.ts` already refuses when it declines to write a shift id into a field called `order_id`. Reuse would also collide two id spaces in one field name, which is `03-F40`'s named defect. The two acks stay separate types because they are two acts, on two surfaces, by two people; `05-F30` declares the payload and is the only FR that may widen it); each payload carries `prev_audit_hash: string | null` (`null` only for a device's first audit event); the hash is SHA-256-hex over the canonical-JSON serialization (UTF-16 code-unit key sort at every depth) of the envelope **with `server_received_at` omitted** — so a device-local event (`server_received_at` null) and its cloud-merged form hash identically. The chain is store-owned (the device stamps `prev_audit_hash` inside the append transaction; a caller-supplied value is rejected). The bare chain binds each event to its predecessor; **tail-truncation and last-event forgery are detected by the Auditor (20 §4.2) cross-checking each device's chain against the merged cloud log**, not by `verifyAuditChain` alone. Hashing is platform law (§7), not configurable.

**Materialization**
- 01-F6 Devices maintain materialized state tables (open orders, table map, availability, current shift) by folding events; folds are deterministic and replayable from the log.
- 01-F7 The cloud maintains per-module read models (Postgres) fed by the merged log; read models are disposable/rebuildable projections, never sources of truth.

**Sync — device ↔ cloud**
- 01-F8 Push: a device uploads its own events in `lamport_seq` order; the server acks the high-water mark; retries are idempotent (event `id` dedupes).
- 01-F9 Pull: a device subscribes to its branch's merged stream ~~(plus org-scope reference data)~~ **(plus reference data — AMENDED August 2026 by `01-F76`: the scope belongs to the ARTIFACT, not to the class.** `01-F76` keys every artifact by `(resource, scope)`; the catalog stays **org**-scoped, so `01-F52`'s quotation of the struck phrase remains true of the thing it describes, and the staff roster is **branch**-scoped (`plans/saas-pivot/plan-of-record.md` R25). "Org-scope" here described the only reference data that existed when this line was written, and reading it as a property of the class is what would have made a branch-scoped roster illegal by accident.**)** over WebSocket; catch-up after offline is a range fetch from its last received global sequence.
- 01-F10 Devices tolerate out-of-order arrival of soft references (00 §6) — folds park events awaiting a parent for late resolution, never crash or drop. **Parking is by key-presence (July 2026, `26`):** an event carrying its full projection keys never parks — payments/refunds carry `order_id`, line edges carry `line_context` — so parking remains only for genuinely key-underivable references (e.g. an orphan `order.confirmed` ahead of its order). The parked list is indexed by `waiting_for`; drain touches only events awaiting the newly-arrived reference.
- 01-F11 Sync status (last push ack, last pull position, queue depth) is queryable by the host app for the honesty UI (00 §5.7).

**Sync — branch LAN mesh**
- 01-F12 Devices in a branch discover each other on the LAN (mDNS; manual IP fallback) and exchange events directly while WAN is down.
- 01-F13 One device acts as **branch hub** (deterministic election among the hub-eligible classes of 01-F39: `counter_electron` > `counter_rn` > `kitchen`; ties broken by lowest device id, compared lexicographically; re-election on hub loss < 10 s). Non-hub devices connect to the hub (star); the hub relays events branch-wide **and is the branch's cloud uplink for any device that has no WAN of its own** (DEC-SYNC-009, accepted — this supersedes the per-device-only reading in DEC-SYNC-004). A device that *has* WAN still runs its own cloud session (per-device sessions remain the default); a LAN-only device — the normal case when only the counter terminal is given internet — has its events relayed upward by the hub on its behalf, so no device's events can be stranded outside the cloud log. Relayed events are attested by the hub, never re-authored: origin `device_id`, `lamport_seq` and payload are carried verbatim (01-F1), and the cloud tracks lamport contiguity per origin device.
- 01-F14 Every **hub-eligible** in-branch device (the hub-eligible classes of 01-F39) retains the full branch event stream for the rolling operational window (current business day + configurable N days); any device can therefore become hub or serve a cold-started peer.
- 01-F15 LAN propagation is fast-path: an event reaches all connected branch devices < 1 s p95 (00 §5.3). Availability toggles and order state changes ride this path.

**Conflict rules (explicit, closed list)**
- 01-F16 Two devices adding lines to the same order → merge (both valid).
- 01-F17 Stock going negative from offline oversell → allowed, flagged; reconciled at next count. A sale is never blocked by inventory math.
- 01-F18 Catalog/price edits → last-writer-wins by `server_received_at`, with full audit trail; the price on an order line is snapshotted at line-add and never re-derived.
- 01-F19 Same physical table opened on two devices while partitioned → both orders stand on merge; the table shows a conflict badge for staff to merge or reassign (a new event). Nothing is auto-discarded.
- 01-F20 Any conflict class not in this list must be designed as append-and-merge before a module may emit the event type. New LWW entities require a spec change here.

**Catalog**
- 01-F21 Catalog entities: Category → MenuItem → Variant → ModifierGroup/Modifier; MenuItem/Variant ↔ Recipe; InventoryItem (raw|prepared, base unit, ~~conversions, `is_tracked`~~ **`is_counted` + `is_costed` (`10-F31` splits the struck single flag), count units and the per-item partial tier (`10-F29`), an optional reference unit cost (`10-F31`)**, par levels per location); **SupplierItem (`brand` — a free string, not an entity — the supplier's own code, and the PACK TRIPLE `pack × size × unit` that computes the ONE integer conversion `10-F1` calls "purchase unit → stock unit"): ⚠ conversions moved OFF InventoryItem here in August 2026, because a conversion is a property of how THIS SUPPLIER packs the thing and not of the thing — one item, many supplier items, many packs;** PrepRecipe with yield %; Supplier + price history. **Area membership `(item, location, area) → sort` (`10-F30`) rides this set too; the stock BALANCE stays at `(item, location)`.** Edited only via back office (doc 14); versioned; distributed to devices as reference-data snapshots + deltas over the same sync channel.
- 01-F22 Item availability ("karahi finished") is an operational event (not a catalog edit), toggleable from POS/pass/manager surfaces, propagated fast-path to every device and channel driver (storefront hides it, foodpanda availability push, doc 08).

**Customer file**
- 01-F23 One customer identity per org, keyed by normalized phone number (E.164); channels attach names/addresses to it. Merging two identities is an event; history is preserved.
- 01-F24 Customer data is org-scoped absolutely (00 §5.4). Cross-branch within an org: shared.

**Identity & auth**
- 01-F25 Org → Branch (type: branch | prep_kitchen | storage) → Device (registered, class-typed, revocable token). Registration is a one-time pairing via back office code; a revoked device loses cloud+LAN participation on next contact and is flagged branch-wide.
- 01-F26 User × Role × per-location assignment; permission overrides per user; PIN (Argon2id) unlock on shared devices; idle auto-lock (device-layer setting). The permission matrix from `restaurant-os.md` Appendix A is the seed; roles are permission sets, not apps.
- 01-F27 Server-side authorization on every API/sync operation; device tokens carry device identity only — user identity comes from the PIN session; both are validated server-side (and hub-side on LAN, with cloud reconciliation).
- 01-F28 Offline auth: PIN verification works on-device against synced credential hashes; role changes propagate as reference data.

**Money contract (canonical — every payment-touching module conforms)**
- 01-F29 `payment.refunded`: carries `order_id`, its **own** `settlement_attempt_id` (01-F31), and references its parent payment by **`payment_attempt_id`** — the parent's attempt key; two fields, never one (a shared field would UKS-collapse two genuine partial refunds) (envelope-id parent refs superseded — one intent may legitimately exist under two envelope ids, which fragments any id-keyed cap, `26 §8`); the cap `Σ refunds ≤ un-refunded remainder` is a fold-evaluated **set** predicate whose violation surfaces as a monotone `violated` exception state gating the order's money rendering — never blocking a sale (01-F17); naming *which* refund busted the cap is definitionally sequence-dependent and is the **gateway's** job at merge (DEC-SYNC-007), quarantining per 01-F37; **when the parent attempt key is itself DISPUTED (divergent members per 01-F31) the cap is UNPROVABLE and the refund passes through with the anomaly flagged** (ratified July 2026) — the gateway previously resolved such a parent by first-merged `global_seq`, which let *delivery order decide a money outcome*, the exact failure `26 §2` exists to remove; the Auditor's refold owns the rest, and both planes now agree that a disputed key contributes nothing; method `cash_out | raast_reversal_ref | khata_credit`; reason; actor + approver — **refunds always require manager approval** (they are a leakage vector). Partial refunds by amount or by listed line ids; a food-return refund links its `void.recorded`/`comp.recorded`.
- 01-F30 Conservation invariants, executable in `packages/domain` and enforced by the Auditor (20 §4.2) and property tests: per order, `Σ tendering payments (purpose: settles_order) − Σ refunds = billed_total − void_value − comp_value − discounts` once settled; khata receivable = billed − Σ tendering payments, decremented by `purpose: repays_receivable` payments (DEC-MONEY-007); split bills: Σ(child billed) = parent billed at split time (`01-F86`: a sub-bill IS that child order); a fully-voided order nets to zero. **`billed_total` INCLUDES TAX — amended August 2026 by `01-F82` (founder ruling R54). It is no longer *"the sum of line prices"*: it is `16-F5`'s snapshot total, so under `16-F2`'s `exclusive` posture it is larger than the delivered lines' billed cells by exactly the tax. The equation above is unchanged and every term in it now means the tax-inclusive number; a reader that means the old one is wrong rather than merely stale.** **AND IT IS ROUNDED — amended again August 2026 by `02-F63` (founder ruling R70): `billed_total` is `16-F5`'s snapshot total rounded to the org's `charge_rounding_paisa`. The equation is again unchanged and needs no new term, because the rounding is INSIDE the number the customer tenders; `02-F63` (b) is why a stored rounding adjustment was refused. ⚠ The split-bill clause takes a second, independent hit — see `02-F63`.**
- 01-F31 Payment/refund idempotency: every emission carries a UI-layer `settlement_attempt_id` — double-taps and retries can never double-record; event-id dedupe (01-F8) covers transport duplicates. **Uniqueness law (ratified):** the token is **org-globally unique, UI-minted, UUID-class** — never a per-device counter (a colliding counter collapses two genuine payments into one key and cash vanishes silently, converged everywhere). Folds dedupe by attempt key: unique-keyed maps whose Σ skips disputed keys. **The payload minus its key is the immutable intent** — members diverging in *any* field (amount, method, purpose, parent ref) mark the key disputed, contribute **zero**, raise an anomaly, and are all retained; a fold never picks a winner. **AMENDED August 2026 by `01-F83` (founder ruling R56): this law is not payment-only.** Every corrective carrying an amount mints an `adjustment_attempt_id` in the same org-global, UI-minted, UUID-class namespace, deduped by the same keyed sum — a different field name because it sits on the other side of `01-F30`'s equation. Cross-**order** attempt-id collision is fold-undetectable in principle — enforcement is mint-time + gateway. **Gateway enforcement posture, ratified July 2026: DETECT AND ALARM, NEVER REJECT.** The gateway checks org-global uniqueness and raises a loud anomaly to fleet health (doc 15) and the Auditor (20 §4.2) on collision, but still **merges** the event. Rejecting would be the stronger algebraic guarantee and is refused deliberately: a device running a bad build would have real, rung-up sales quarantined, which breaks 01-F17. The failure this closes is that a colliding key makes cash vanish *silently and identically on every device* — a loud wrong number gets fixed, a silent one does not, so converting silence into an alarm is the whole win.
- 01-F32 Channel closure: aggregator-collected orders settle as `payment.recorded { method: aggregator_receivable }` (doc 08 reconciles against payouts); khata repayments are `payment.recorded { purpose: repays_receivable }` referencing original orders (02-F14) — excluded from `pay_total` by 01-F31's keyed sum, so a repaid tab can never read as overpaid (DEC-MONEY-007). No order reaches settled state with conservation violated. **`method` is no longer a fixed enum — amended August 2026 by `01-F85` (founder ruling R55): the set is a seed the owner extends, and `aggregator_receivable` and `khata_credit` are RESERVED ids whose kernel meaning is this clause's and which no owner may mint a second of.**
- 01-F33 Settlement is an **act, not a derivation**: `order.settlement_closed` (cashier-emitted, offline-legal) closes the money side as a monotone fact — nothing arithmetic settles or un-settles an order, and a late line-add raises `uncovered_addition` rather than reopening (a derived predicate over an append-only log cannot be both monotone and a pure function of the set, `26 §7`). Post-settlement corrections are always linked event pairs (refund + void/comp; fiscal credit note via doc 16 when active). Order "reopening" does not exist. ⚠ **THE CEILING IS `billed_effective_paisa`, A SECOND ATTESTED NUMBER, AND NOT `billed_paisa` (amended August 2026; measured on shipping code, wrong in BOTH directions).** `01-F82`/`02-F63` made `billed_paisa` the ROUNDED, TAX-INCLUSIVE charge while the fold's own accumulator stayed the raw, tax-blind, unrounded line sum, so the check straddled two quantities: a charge that rounded DOWN sits below its line sum, so `uncovered_addition` — which means *a line was added after the close* — fired on correctly settled orders nobody touched (posture `none`, step 1000, one Rs 404 line → `["uncovered_addition"]`), and under `exclusive` the charge sits ABOVE the line sum by the tax, so any post-close addition up to the tax was invisible (16 %, a genuine Rs 60 line added after the act → `[]`; that half predates `02-F63`). `01-F82`'s enumeration of the readers that move together named this ceiling, and it could not move: `01-F87`/`01-F52` ban configuration as a fold input, so no fold may ever compute a rate-and-step-dependent number — the enumeration is CORRECTED BY MEASUREMENT here, as `01-F83` corrected R56's list. So the closing act attests BOTH: `billed_paisa` stays `billed_total` (what the customer owes — `01-F30`'s equation and the owner's day sales read it, and nothing can recompute it once `01-F87`'s carrier is the only rate authority), and `billed_effective_paisa` carries `01-F63`'s literal words for the ceiling, *"the fold's `billed_effective` at the moment of closing"*. The ratified snapshot semantics are UNCHANGED and now bind the ceiling field: an absent snapshot asserts no ceiling, an attested `0` is a real ceiling, a non-integer or negative one raises `close_snapshot_invalid` while the act still settles — and a malformed `billed_paisa` raises it too, because `01-F63` calls the whole payload one snapshot.

**Convergence contract (formalizes 01-N1)**
- 01-F34 Fold **merge** law (rewritten July 2026 on DEC-PERF-001 ratification; formerly "Fold-ordering law"): every fold declares an explicit merge rule per projected field — grow-only set/map union, unique-keyed sum (01-F31 attempt keys), monotone fact, supersedes-DAG head-set, or an explicitly rendered contested set — per the normative matrix (`26 §7`, `plans/wave-0/merge-semantics-matrix.md`). Device folds read **no ordering metadata**: no `global_seq`, no `lamport_seq`, no device clock — property-tested by **bijective envelope-id relabeling** and sequence/clock-injection invariance (equal delivered set ⇒ byte-equal projection; plain convergence alone is insufficient — a min-id tiebreak passes it while smuggling wall clock through the UUIDv7 prefix). `global_seq` remains the delivery/catch-up cursor and compaction watermark (01-F3), never a business arbiter; the two legitimate gateway-side sequence uses are enumerated in `26 §7`. ~~For the closed LWW list (01-F18) and any genuinely order-sensitive read model, the cloud's global org sequence (01-F3) is the tiebreak; devices converge to cloud ordering on ack~~ — superseded: cloud-plane catalog LWW (01-F18, `server_received_at`) is unchanged; device-plane folds never tiebreak by sequence.
- 01-F35 Terminal-state monotonicity: an entity in a terminal state ignores later non-terminal transitions; the ignored event is retained and flagged as an anomaly — folds never regress. This, not 01-F16, is what makes duplicate "same action" events safe (e.g. `rider.delivered` from both the rider app and an on-behalf counter entry).
- 01-F36 Approval idempotency: `approval.granted / denied` applies only while its request is pending; duplicates and stale responses are logged no-ops.
- 01-F37 Rejection & quarantine: an event failing schema, authorization, or invariant validation at hub or cloud is quarantined — stored verbatim, excluded from folds, surfaced to fleet health (doc 15), originating device notified. **Notification target, amended July 2026 (founder ruling; code was right, this sentence was not):** for ordinary content-class rejections the *originating* device is notified as written. For **identity-failure** classes — where the claimed origin may be forged — the notified party is the device that actually **pushed** the event, not the device the envelope claims to be from. Otherwise anyone could forge envelopes naming an innocent terminal and flood it with rejection notices it cannot act on, turning the honesty UI (00 §5.7) into a spam channel. **Storage is per claimant:** the quarantine key is `(org, claimed_event_id, device_id)`, so a foreign pre-claim can never displace an honest origin's envelope — each claimant's bytes are preserved as its own evidence row. A row whose event is later legitimately merged is **marked superseded and retained**, never deleted (it drops out of live-quarantine counts and fleet-health surfaces, but the evidence survives — this table exists to preserve what a device tried to send). **Supersession is scoped by the STORED ENVELOPE's author, not by the row's attribution** (amended July 2026, adversarial review M2): a row is superseded only when the event that merged is the one that row holds. This covers the hub's pre-registration placeholder — a relay carries the origin's envelope verbatim, so the placeholder's stored bytes *are* the merged event even though the row is attributed to the hub — while a **forged** claim on the same id holds a different envelope and therefore stays live until an operator sees it. Someone impersonating a terminal is precisely what the live surface exists to show. Resolution is an explicit operator action producing correction events; where the origin device already folded the event locally, the correction event defines the reconciliation. A quarantined event is durably stored, so it **fills its lamport slot** for watermark/ack purposes: the push ack advances past it and the device outbox never wedges on a poison event (DEC-SYNC-005, accepted; the 01-F17 never-blocked spirit). The Auditor's lamport-gap check counts quarantine rows as slot-filling (20 §4.2).
- 01-F38 Split/merge races while partitioned: both results stand on merge (01-F19 pattern) with a conflict badge; staff resolve via new events; nothing auto-discards.

**Device classes & sync slices (formalizes scoped sync)**
- 01-F39 Device classes (canonical identifiers — the `DEVICE_CLASSES` vocabulary declared once in `packages/domain`) with fixed slice + hub rules: `counter_electron` (counter POS, Electron host — full branch window, hub-eligible), `counter_rn` (counter POS, React Native host — full branch window, hub-eligible), `kitchen` (pass screen / KDS station, doc 03 — full branch window, hub-eligible), `manager` (full slice, never hub — personal phone), `waiter` (scoped: own-table orders, availability, own events; LAN member, never hub), `rider` (cloud-only scoped: assigned orders + own events; never joins the branch LAN). Hub-eligible is exactly {`counter_electron`, `counter_rn`, `kitchen`}, listed here in 01-F13 election-priority order. 01-F14's full-window retention applies to hub-eligible classes.
- 01-F40 Slice predicates are enforced server-side and hub-side from device class + role — never client-declared. A scoped device requesting outside its slice is denied and flagged.
- 01-F41 Reassignment backfill: reassigning an entity (table to another waiter, order to another rider) triggers targeted backfill to the new device and halts delivery to the old one.
- 01-F42 Revocation & purge: a revoked device or role receives a local-purge command on next contact (cloud or LAN); scoped devices cold-start from slice backfill only (< 2 min on 4G).

**Time layer (DEC-TIME-001, accepted July 2026 — separate from the ordering layer, which reads no clock at all per 01-F34)**
- 01-F43 **Branch-consensus time.** The elected hub (01-F13) is the branch time authority. Every device holds a signed integer millisecond `branch_time_offset` against hub time, refreshed on hub contact, and computes *branch time* as `device_clock + branch_time_offset`. All **durations** — kitchen age, ETA, service intervals (doc 03) — are differences evaluated in branch time, so a uniform offset cancels and the shared clock need only be *consistent*, not correct. Because DEC-SYNC-009 makes the hub the branch's WAN uplink, the hub is normally the device that has real internet: branch time is genuinely correct in the common case and self-consistent when fully offline. Offset acquisition never blocks operation (01-F17) — a device with no hub contact yet uses offset 0 and marks its derived stamps provisional per 01-F44. **Branch time is CONTINUOUS across hub re-election** (amended July 2026 — the first draft was silent here, and silence meant a catastrophic discontinuity): a newly-elected hub (01-F13) **retains the branch time it already held**, keeping its measured offset rather than resetting to its own raw clock; only a device that has never acquired an offset starts at 0. Correspondingly the hub's heartbeat carries **branch** time, not its raw clock. Without this, a hub handover — a normal event on any counter reboot, re-elected within 10 s — would teleport branch time onto the new hub's untrusted clock, and every open order's age would jump by that clock's error (a kitchen display stuck years ahead would show every ticket as years old). Branch time is a property of the BRANCH, not of whichever device currently serves it; the hub serves the clock, it does not define it.
- 01-F44 **Absolute business timestamps are provisional until reconciled.** Two distinct markers, deliberately separated (amended July 2026 — the first draft conflated them, and a device cannot know server time at append):
  - **The envelope marker** is `time_basis: 'branch' | 'branch_provisional'` — a property of how the *device* stamped `branch_created_at`: `branch` once an offset has been measured against the hub (01-F43), `branch_provisional` when the device has had no hub contact and is running on offset 0. It is written once at append and **never rewritten** — the ledger is append-only (01-F1).
  - **The derived business stamp** — what tax and fiscal instants (doc 16), audit chronology (01-F5) and the day boundary actually read — resolves to `server_received_at` when the cloud has seen the event, and otherwise to the event's branch stamp carried forward with its provisional marker. Its basis is therefore `'server' | 'branch' | 'branch_provisional'`. Reconciliation is **observable**, never a silent promotion: the envelope marker stays as written and the resolved stamp changes basis when `server_received_at` lands beside it (16-N3 already assumes this shape). Which FR owns the resolver is deliberately unfixed — doc 16 declares it when fiscalization lands; Wave 0 writes and asserts the marker only. **A solo/hub device stamps `branch`, not `branch_provisional`** (ruled July 2026, review H2b): it *is* the branch, so there is no other clock its time could mean, and durations on a lone device are self-consistent by definition. Fiscal correctness is not weakened — the derived business stamp is provisional whenever `server_received_at` is absent, independently of this marker — and marking every stamp of an offline single-terminal restaurant provisional all day would drain the marker of meaning exactly where it needs to carry weight.
- 01-F45 **`device_created_at` is untrusted.** It is a display/forensic hint only. No fold, read model, invariant, or ordering key may derive a value from it — mechanically enforced alongside the 01-F34 ordering-metadata ban. Timing read models take branch time (01-F43); business stamps take 01-F44. This closes the live defect in which a device whose clock is years wrong wrote wrong `confirmed_at`/`kot_at`/`age_basis` values straight into the doc-03 timing models. **Basis precedence in value selection (amended July 2026, adversarial review H2):** where a fold selects among competing time-carrying members, members whose `time_basis` is `branch` are preferred over `branch_provisional` ones; a provisional stamp is used only when no `branch` member exists. Without this the ban is closed for `branch` events only — a `branch_provisional` stamp *is* the raw device clock (offset 0), so under an earliest-wins rule a device whose clock is behind always wins, and a tablet powered on before the counter would set an order's age years in the past on every screen. Precedence is a partition of the delivered set, so selection stays set-determined and order-independent (`01-F34`). **One exemption, named explicitly:** `01-N2` skew detection *must* read the raw device clock — measuring how wrong a clock is is impossible without it. Device health is neither a fold nor a read model, so this is a carve-out from the mechanical ban, not a contradiction of it; the raw field is retained for exactly this purpose.
- 01-F46 **Business-day boundary** is anchored to Asia/Karachi regardless of cloud region or device locale; the day-close boundary is a property of the business, never of where a server happens to run. **The day starts at a configurable cutover hour, default 05:00** (layer-2 org setting per 00 §7 — the first draft left the start hour unstated, which silently meant midnight). A business day therefore runs 05:00→05:00 local: a sale rung at 01:30 belongs to the night it was actually served, not to the calendar date. Midnight is the wrong default for this market — a restaurant open past midnight would otherwise have one night's takings split across two days' reports, and every daily total, shift report and cash reconciliation inherits the error. The cutover is adjustable within designed bounds (00 §7 presets-not-knobs); the *timezone* anchor is not configurable. **⚠ THIS FR IS NOT A SCHEDULER, and August 2026's R31 turns on that distinction, so it is stated here rather than left to be inferred.** The business day answers *which day does this sale belong to* — a reporting fact that daily totals, shift reports and cash reconciliation are all computed against. It has been read as also answering *when does a change take effect*, because `01-F61` and `14-F28` both once used this boundary as their default application time. R31 severs the two: a change now carries its own application time, and this cutover keeps only its own job. **Nothing about R31 reaches this FR** — the cutover hour stays configurable per org, the Asia/Karachi anchor stays a refusal rather than a deferral, and an org that moves its cutover to 04:00 has changed which day a 04:30 sale belongs to and has changed no schedule.

**Auth hardening (DEC-AUTH-001 / DEC-AUTH-002, accepted July 2026)**
- 01-F47 **Device token lifetime, binding, and renewal.** Every device token carries a mandatory expiry (`exp`, default 90 days) and is bound to its issuer and audience (`iss`/`aud`) so a token minted for one deployment is inert in another. Tokens are renewed silently on any authenticated cloud contact — including **hub-relayed** contact (01-F13), so a LAN-only device renews without ever holding WAN itself. **The device PERSISTS the renewal itself and presents it on every later connection** (amended July 2026, adversarial review B1 — emitting a renewal the device never applies makes expiry terminal rather than transient, and at TTL the whole fleet enters a reconnect loop simultaneously; a hub in that state strands its entire branch). Persistence belongs to `sync-client`, not to the host app: "silent" is the FR's own word, and any host that forgot to store it would brick its devices at TTL. The cloud's `token_expires_at` record is seeded at registration so a relayed origin is due for renewal from its first day — and the host app surfaces a warning once the remaining life falls below 25%. **Expiry never blocks a sale** (01-F17, 00 §5.1): an expired token withdraws cloud/LAN *admission* only, and the device continues to serve and persist locally. An expired-but-unrevoked device presenting itself is admitted for the sole purpose of relaying its backlog upward and receiving a renewed token. **That session's `hello_ack` MAY carry the renewal, and the session nonetheless stays push-only** (amended July 2026): "sole purpose" constrains what the session may *do* — reads refused, no fan-out — not which message the credential arrives on. Requiring the renewal to be *earned by a push* is a stronger rule than the clause needs and creates a permanent wedge: a device offline across its whole renewal window comes back with an empty outbox, so it has no push to make, no ack to carry a renewal, and reconnecting repeats it forever. Expiry would then block a device outright, which 01-F17 forbids. The renewal changes the device's *next* connection; drain mode remains observable on *this* one; an expired **and revoked** device is purged per 01-F42. Expiry is a backstop against indefinitely-valid credentials — revocation (01-F25) remains the operative kill switch.
- 01-F48 **Revocation eviction latency.** Revoking a device evicts it from the mesh within 30 s where any path (cloud or LAN) reaches it, rather than only at its next voluntary contact: the cloud drops live sessions and culls the device from fan-out on the revoking transaction, and the hub does the same on LAN. Eviction is fail-closed — if revocation state cannot be read, participation is refused, not granted, and refusal never carries a purge (an unreadable state is not proof of revocation, and a purge is destruction, not refusal). Revocation blocks **reads as well as writes**: a revoked device receives no further events on any plane. **LAN scope (July 2026):** the hub evicts a peer the cloud has refused as `origin_revoked` — at hello and on every heartbeat, so a mid-session revocation still lands inside the bound — and drops any credential it was holding for it. This covers every revoked device the hub can *observe*; a revoked device that only reads and never pushes produces no cloud refusal and so remains invisible until registry state is distributed over the LAN, which is tracked as the remaining gap in `plans/wave-0/sec-review-followups.md`. **Amended August 2026 — the gap is closed by `01-F74`, and the LAN half as built INVERTED this FR's own posture.** "The hub evicts a peer the cloud has refused" was implemented as an in-memory set of observed refusals, so a hub restart re-admitted every revoked device on the branch: fail-closed state that fails *open* on the most ordinary event there is. The authority is now the durably-cached signed roster (`01-F74`), not a cache of refusals a process happened to see, and the observed-refusal set is deleted rather than made durable. Two readings of this FR are separated by `01-F74` (d) and neither is new: an **unreadable** revocation state refuses, an **old but valid** one admits and says how old — the sentence above already draws that line for revocation, and it draws it the same way for the roster that carries it.

**Training (`DEC-TRAIN-001`, July 2026 — closes `27-F52`, gap G1)**

- 01-F49 **A training session is an ordinary session against a TRAINING BRANCH. There is no training flag anywhere in the kernel.** A branch carries a `class` of `production | training`; a training branch is a real branch with a real ledger holding real events, and everything the kernel already does — branch-scoped credentials (`01-F9`), branch-scoped fan-out (`01-F13`), branch-scoped reporting — isolates it for free.
  - **Why not an `is_training` flag on the envelope**, which is the obvious answer: it makes correctness depend on *every* fold, report, export and analytics query remembering to filter. One forgotten filter and `01-F1` makes the pollution **permanent** — you cannot delete it — and a missing `WHERE` clause is invisible in review. The branch boundary is enforced in one place, at admission, and is already load-bearing.
  - **Why not an ephemeral scratch store:** the things most needing practice are a shift close, a cash count and a day close (`02-F22`, `02-F23`). Training that evaporates cannot rehearse anything that spans a shift.
  - A training branch **never uplinks to the org's production analytics scope**; it is excluded once, at the org level, not per query.
  - **Catalog is mirrored read-only** from the production branch (`01-F21`), so staff train on the real menu and real prices. Mirroring is one-way and a training branch may never write catalog.
- 01-F50 **Entering or leaving training is an explicit, attributed credential swap, never a UI toggle.** The production session **drains first** (`01-F47` drain mode: push-only until the outbox is empty), then the device re-authenticates to the training branch. A device holds exactly one branch credential at a time, so a trainee cannot reach production data by switching mid-flow, and a training event can never be authored under a production identity. Both directions emit `audit.*` (`01-F5`).
- 01-F51 **A training branch is droppable; a production branch is not.** `01-F1`'s append-only law protects *history*, and a training branch is by construction not history — it never fed a report, a tax filing or a payout. So the whole branch may be deleted or reset wholesale, which is the retention answer (`22`) and also what makes repeated RITE rounds (`21-F11`) affordable. Deleting individual events inside a training branch remains **forbidden** — the ledger is append-only within its own boundary, or the rehearsal teaches the wrong thing.

**Catalog distribution on the device (`01-F21` detail — added July 2026 when `apps/pos-electron` found the device had no catalog at all and therefore no screen could render an item name)**

- 01-F52 **Catalog is REFERENCE DATA, not ledger.** It arrives as versioned snapshots and deltas over the sync channel (`01-F9` "plus org-scope reference data") and is edited only via back office (`14`). `catalog.changed` announces that a new version exists; it does not carry the catalog. Consequences that are easy to get wrong: catalog is **org-scoped**, not branch-scoped, so a training branch mirrors it read-only (`01-F49`); and catalog state is **not** an input to any fold — a projected value that read a name would depend on catalog sync state at fold time, which is the `01-F34` break law 1 exists to prevent.
- 01-F53 **Money never depends on catalog sync.** A line's `unit_price_paisa` is captured **into the event at the moment the line is added** and is never re-read from the catalog. So a price edit cannot retroactively change an open order, a settled total or a printed receipt, and a device whose catalog is stale still bills correctly. **Once a line exists, the catalog supplies display text only.** This is the property that makes 01-F54's degradation safe rather than merely tolerable. **Scope, added July 2026:** this FR governs everything *after* capture; the price the capture reads **comes from the catalog** and is specified by `01-F60`. The unscoped sentence was read as "the catalog holds no price", which removed the field from the wire, the gateway store and the device store, and left the counter unable to add a line at all.
- 01-F54 **An unknown or not-yet-synced item degrades to its identifier and NEVER blocks (`01-F17`).** A screen that refuses to render because one item was renamed upstream is a stopped till. The line still shows its quantity and its money — both of which come from the event, not the catalog (01-F53) — so the cashier can complete the sale and the only loss is a word.
- 01-F55 **Deletion is a tombstone, never a row removal.** An open order, an unsettled bill or a reprint may reference an item the owner deleted minutes ago, and that document must still render its name. Removed catalog entries are marked deleted and retained: they stop appearing in the grid but stay resolvable by id. Retention follows `22`.
- 01-F56 **Versions apply monotonically, and a delta whose base does not match is REFUSED — the device asks for a snapshot instead.** Applying an out-of-order delta silently diverges one device's menu from every other's, which is undetectable at the till and shows up as a mispriced or misnamed item days later. An older snapshot or delta than the device already holds is ignored, never applied backwards. Refusal is observable in device health (`15`) like any other blocked cursor (`DEC-SYNC-011`).

**Availability merge semantics (`01-F22` detail — added July 2026; `26`)**

- 01-F57 **`availability.changed` carries an explicit `supersedes` link, and the fold reads nothing else.** The naive design — "the latest toggle wins" — is a **law-1 violation**, because "latest" is either a device clock (banned in folds, `01-F45`) or an envelope-id comparison reaching a projected value (banned, `01-F34`). Availability is toggled from the POS, the pass screen and the manager console (`01-F22`), so concurrent toggles from two devices are ordinary, not exotic. The convergent form is the one `order.table_assigned` already uses: each toggle names the toggles it replaces, and the fold takes the **maximal** (un-superseded) set.
- 01-F58 **A contested item is UNAVAILABLE, and the disagreement is flagged.** When the maximal set disagrees, the fold does not pick a winner (`01-F31` — a fold never picks a winner). It resolves to **unavailable** and raises an `availability_contested` anomaly for the manager surface. This is a semantic choice, not a tiebreak: it is commutative, associative and idempotent, and it errs toward *not selling a dish the kitchen may have run out of*, which is the recoverable direction. Selling one you cannot make costs a refund and a customer; failing to sell one you could costs a re-toggle.
- 01-F59 **Availability is not an `01-F17` block.** Greying an 86'd item is an explicit operational decision by staff, not the system withholding a sale on inventory math, sync state or an approval timeout. An item marked unavailable is hidden from the storefront and pushed to aggregators (`01-F22`), and the counter may still sell it deliberately — `02-F31` owns the oversell path.

**Catalog pricing (`01-F53` detail — added July 2026 when the counter was found unable to add a line at all: `order.line_added` requires `unit_price_paisa` and no layer of the catalog path carried a price. See `plans/wave-1/channel-pricing-and-the-counter-loop.md`)**

- 01-F63 **The closing act's EMISSION contract — who emits `order.settlement_closed`, when, and what it attests (August 2026; founder ruling, closes the first item on `DEC-MONEY-009`'s residual column).** `01-F33` ruled that settlement is an **act, not a derivation** and named the event. It did not say what produces one, and the consequence was measured rather than predicted: the type has had a payload schema, a merge rule and **zero production emitters** for the life of this product, so `settled` is `0` on every order any device has ever held, `01-F30`'s conservation equation — which only runs once settled — has **never executed on a real order**, and `DEC-MONEY-009`'s duplicate-settlement guard had to be built on an arithmetic reading (`pay_total >= billed_effective`) because the column it should have read is constantly zero. `01-F33` is not amended: nothing arithmetic settles an order, reopening does not exist, and the fold still judges no arithmetic. What is added is the missing half — **the act has a producer.**
  - **WHO: the till that appends the tender which completes the cover.** Settlement is the cashier's act (`01-F33`: *"cashier-emitted, offline-legal"*), so the emitter is the device that just recorded a `payment.recorded`, and the envelope's `actor_user_id` is that cashier's live PIN session (`02-F41`/`02-F45` — attribution rides the envelope, never a payload field). No other plane may emit it: a cloud-plane emitter would need a branch-scoped envelope it cannot legally stamp (`01-F62`), which is `05-F28`'s finding one event over.
  - **WHEN: on the edge into "tendered for in full", and on no other trigger.** The emitter hangs off a **completed** append of `payment.recorded` and asks the device's own converged fold one question — is `pay_total >= billed_effective`, with `billed_effective > 0` — exactly the reading `02-F15`'s receipt (`printing.ts`) and `02-F31`'s settlement edge (`line-advance.ts`) already make at the same call site. **One definition of "settlement completes", not four**: `02-F45` refuses a second source for one fact, and this product now has three call sites answering that question, so the closing act joins them rather than inventing a fourth. A `02-F13` split therefore closes **once**, on the tender that covers, not once per tender.
  - **AT MOST ONE PER ORDER, and the emitter — not the fold — is what makes that true.** The fold is a monotone OR over a G-Set, so a re-emission converges identically and is harmless to `settled`; it is **not** harmless to the ledger. `01-F1` makes every emission permanent, so a till that re-emitted on relaunch, on re-delivery of the same payment, or on a later refund-then-repay cycle would write a growing pile of rows each claiming a bill was closed a different time, with no rule for which is true. The emitter therefore checks the same projection it is about to change — an order already carrying the act is not closed again — which is a **local read of converged state**, never a lock and never a peer.
  - **OFFLINE-LEGAL, AND IT NEVER BLOCKS A SALE.** The decision reads one row of this device's own SQLite projection and nothing else: no WAN, no hub, no clock, no ordering metadata (`00 §5.1`, `01-F17`, `01-F34`). It is emitted **after** the money is already in the ledger, on `02-F15`'s receipt precedent — a sale is complete whether or not its closing act, its paper or its uplink follow — so a failure to emit costs a conservation check, never a customer.
  - **WHAT IT ATTESTS — the payload, PINNED (the `T-01-15` addendum's owed follow-up; every field beyond `order_id` has been an additive loose extra since the schema landed).** `order_id` (required, unchanged). The attested snapshot, all integer paisa (`00 §6`): **`billed_paisa`** — the fold's `billed_effective` at the moment of closing, which the merge engine already reads as the `uncovered_addition` ceiling; **`tendered_paisa`** and **`refunded_paisa`** — `01-F31`'s keyed sums, `settles_order` only (`DEC-MONEY-007`); **`settlement_attempt_ids`** — the keys the cover was made of, so a later reader can tell which tenders this act was closing over. **No actor field, and that is forced rather than chosen:** a `closed_by_user` (or `cashier`, or `closed_by`) in this payload would be `02-F45`'s **second source for one fact** — the envelope's `actor_user_id` already carries it, the two can disagree, and an append-only ledger has no rule for which wins. The snapshot is **attested, never re-derived**: `01-F1` forbids silently changing a number the ledger already stated, which is the same reason `shift.closed` carries its `expected_paisa_by_method` rather than recomputing it. ⚠ **`billed_paisa` AND `billed_effective_paisa` ARE TWO FIELDS AND TWO FACTS (amended August 2026, with `01-F33`).** This clause defined `billed_paisa` as *"the fold's `billed_effective` at the moment of closing, which the merge engine already reads as the `uncovered_addition` ceiling"* — one sentence naming two quantities that `01-F82` and `02-F63` then pulled apart. `billed_paisa` is the first half as those FRs left it: `billed_total`, tax-inclusive and rounded, and it is the ONLY record this ledger holds of what the customer was charged. `billed_effective_paisa` is the second half, unchanged in meaning and now unambiguous in name: the fold's own line sum, which is the ceiling. Neither is derivable from the other and neither is recomputable later — the line set moves the moment the exception it guards occurs, and the charge needs a rate and a step no reader will have. Both are additive loose extras on the same `01-F4` schema, so an absent one is read exactly as this FR already says an absent snapshot is read.
  - **A SNAPSHOT IS AN ATTESTATION, AND AN ABSENT ONE IS NOT A ZERO.** The merge rule is already ratified and is not reopened here: an absent `billed_paisa` asserts **no ceiling** (*"no attestation" is not "attested zero"*), an attested `0` is a real ceiling, and a non-integer or negative snapshot raises `close_snapshot_invalid` while **the act still settles** — the act is the fact, the snapshot is evidence about it, and bad evidence must never unmake a fact the cashier performed.
  - **WHAT THIS DOES NOT CLOSE, stated so nobody reads it as more than it is.** It does not make `01-F30`'s three missing right-hand terms appear (`DEC-MONEY-010`); it makes the equation *run*, which is the prerequisite those terms were owed behind. It does not close `DEC-MONEY-009`'s **partition** residual: two tills that never converged still both accept, and now both also close. And it does not decide `EXCESS_TENDER_IS_EXCEPTION` — an over-tendered order closes exactly as a covered one does, and whether its negative residual is a finding remains open.

- 01-F62 **The `01 §4` catalog holds TWO SCOPES, and an org-scoped event carries no branch fields (August 2026, closes `DEC-SYNC-012`).** `EventEnvelope` requires `branch_id`, `branch_created_at` and `time_basis` because `01-F43`..`01-F46` make time branch-consensus and stamped at append by an originating **device**. A back-office catalog edit has **neither a branch nor a hub**, so `14-F3`'s required `catalog.changed` had no legal envelope — found when the back office's publish path built against a port and declined to mint one rather than guess.
  - **The test is who may legitimately emit it, not which doc declares it.** An event type is **org-scoped** when its only legitimate emitter is the cloud plane: `catalog.changed`, `device.registered / revoked`, `user.changed`, `config.changed`. Everything else is **branch-scoped**, including `audit.*` — `audit.login` is emitted by a device at a PIN unlock, and `01-F5`'s chain is explicitly per-device, so the admin *family* does not split cleanly and the emitter does.
  - **An org-scoped event carries `org_id`, no `branch_id`, and no branch stamp.** Its ordering authority is `server_received_at` (`01-F18` already rules exactly this for catalog edits), which is trustworthy precisely because the cloud plane is the one place a clock is not a threat — the inverse of the device-clock threat model `01-F43` was written for.
  - **It never enters a branch stream and no device folds it.** `01-F9` already separates "its branch's merged stream" from "org-scope reference data", and the catalog *artifact* travels that second path (`01-F52`..`01-F56`). A device needs the menu, not its edit history; `14-F3`'s history is a back-office surface. This is why the rejected alternatives were rejected: a `server` value on `time_basis` would put a non-branch value in a branch field, and an org-scoped envelope *variant* would touch every fold and reader for events no fold reads.
- 01-F61 **PIN lockout and the Argon2id cost floor (August 2026).** `01-F26` requires a PIN and `00 §5.4` requires lockout on repeated failure; neither states scope, persistence, an end condition, or a cost floor, and each gap is a way in. A 4-digit PIN on a shared terminal is a **convenience credential, not a secret** — shoulder-surfing is the norm in a restaurant, and what makes it safe enough is that it is paired with a registered device (`01-F25`/`01-F47`), which is exactly why `01-F27` keeps device tokens carrying device identity **only**. The four decisions:
  - **Scope is per (device, user).** Per-device is *forced* by `01-F28` — an offline device cannot know another device's failure count. Per-user is forced by `01-F17`/`00 §5.1`: `01-F26` calls these **shared** devices, so a device-wide counter is a scheduled stopped till, one wrong PIN away from locking a queue of customers out of the only terminal.
  - **The counter PERSISTS across an app restart.** A counter held in memory is defeated by relaunching the app, which makes the lockout theatre — and the attacker who most needs locking out is standing at the device with physical access to do exactly that.
  - **A lockout ENDS on a time cooldown, never only on a human.** A manager-clear path cannot be the sole exit: a T1 branch (`27-F11e`, most deployments) may have no manager present, and a lockout with no automatic end **bricks the till** — which `01-F17` forbids in spirit, since it stops sales to enforce a security control. A manager-clear MAY shorten the wait; it may not be the only way out.
  - **Argon2id parameters carry an explicit floor**, asserted as *parameters*, never as elapsed time — a duration assertion is a timing test (`24-F12` flakiness) and a fast machine reads as a weak one. Without a stated floor a conforming-but-worthless `m=8,t=1,p=1` satisfies every test that checks only the algorithm name.
  - **The unlock surface IDENTIFIES THE USER FIRST, then takes the PIN** (August 2026, forced by the two clauses above). A bare PIN pad that matches the entry against every staff hash on the device is the tempting shape and it breaks both: a failed attempt belongs to **no** user, so the per-(device, user) counter cannot be keyed at all and collapses to the device-wide counter this FR just refused; and two staff sharing a 4-digit PIN become **indistinguishable**, which under `02-F41` ("attribution is whoever's PIN is in") writes the wrong cashier into an append-only ledger `01-F1` forbids correcting in place. **The identification step must not be a text list** — `27-F6` forbids requiring typing and the cashier is plausibly a non-reader (`21 §5`), so it is a fixed grid of staff tiles whose **positions never move** (`27-F4`'s positional-memory law, which here is an asset: a tile learned by position is usable without reading it). **Stated cost:** `C1` runs 20–60× a shift and gains one tap. That is a real tax on the most frequent action in the product, accepted because the alternative is an unattributable ledger and a till any wrong PIN can lock for everyone.
  - **Selecting a person is not submitting an attempt** (August 2026). Identification is revocable until the PIN is submitted: tapping a different tile before submit costs nothing, and the per-(device, user) counter is charged **only** when a PIN is actually submitted against that user. Without this, a mis-tap on a grid charges a failed attempt to someone **who is not in the building** — the same "a wrong PIN must not lock out a bystander" argument this FR already uses to refuse the device-wide counter, reappearing one step earlier in the flow. This is a constraint on *when the counter increments*, not a new UI mechanism; nothing here requires a "change user" control beyond re-tapping the grid.
  - **A staff record carries an explicit `grid_ordinal`, and roster changes land at the business-day boundary.** Ordering the identification grid by any *derived* key — `user_id`, name, recency — means a new hire **inserts wherever it sorts and shifts every tile after it**, so the muscle memory `27-F4` protects is destroyed by an ordinary Tuesday hire. The first build ordered by `user_id` and the defect is invisible to a test that only re-renders the same roster, which is precisely how it survived review. So: position is an explicit ordinal on the record and **new members append**. ⚠ **The second half of this clause is AMENDED (August 2026, founder ruling R31) and the amendment is a widening, not a reversal.** It read: *"a change to the roster applies at the **05:00 business-day boundary** (`01-F46`) rather than mid-shift"* — with **no choice offered to anyone**, which is the strictness R31 overturns: an owner who hires a cashier at 11am could not put her on the grid until 05:00 the next morning, and no FR let her decide otherwise. **A roster change now carries its application time as part of the ACT: immediate, at a time the owner picks, or at the business-day boundary** — `14-F28`/`14-F36`'s model for menu edits, which this clause always cited as its own precedent, now applied with that precedent's *choice* rather than only its default. The muscle-memory reason is untouched and is why the boundary REMAINS the default: a grid that reorders under a cashier's hand is `27-F4`'s breaking change, so moving a tile mid-shift stays a deliberate act with its consequence on the control, never a silent one. **Two things this amendment does NOT do.** It does not reach `01-F46` itself — that is the *business-day* anchor, a reporting fact about which day a sale belongs to, already a configurable cutover hour per `00 §7`, and it is not a scheduler. And it does not make a **deactivation** schedulable: R27 rules that immediate and R31 does not reopen it, because an act whose entire purpose is to take effect now is the one act "when would you like this?" is the wrong question for. (Frecency, "most recent first", and alphabetical are all banned by `27-F4` already; this clause names the mechanism that makes obeying it possible.)
  - **A staff record carries a `display_name`, because the identification tile must render something.** `packages/sync-client`'s `StaffMember` shipped as `user_id` + `pin_hash` + `assignments`, and a grid of tiles labelled by opaque id is unusable. It rides the same `01-F21` reference-data chain as the rest of the roster. **Owed, and better:** `21 §5`'s non-reader evidence says a *name* is the weakest possible label for this population — a photo or a fixed per-person mark would be materially better, and that is `27`'s to specify. The name is the floor, not the target.
  - **Two implementations of ONE algorithm, and that is not a split hashing story.** `18 §` names `argon2` under *Backend* and it stays there for the cloud plane; the **device** path is Core/shared, where `argon2` — a native addon — would break every browser workspace that imports `domain`. The device path therefore uses `@noble/hashes`' pure-JS `argon2id` (already a dependency). Same algorithm, same parameters, two bindings; `01-F26`'s "the hashing story stays single" binds the *algorithm*, not the package.
- 01-F60 **The catalog carries the price, per branch and per channel, and it is the source `01-F53` snapshots FROM.** Every sellable entry (`item`, `variant`) carries an integer-paisa price for **each (branch, channel) pair the org has enabled** (`00 §7` layer 2: "channels enabled" and the org's branches; the closed channel set is `02-F42`). **`modifier` is SELLABLE** (founder ruling July 2026): a paid add-on carries the same commission exposure as the dish it sits on, so "extra raita" is priced per `(branch, channel)` like anything else and falls under the writer's completeness check. The consequence is stated rather than discovered: **a free modifier carries an explicit `0` on every enabled pair**, which is the point — it distinguishes "this costs nothing" from "somebody forgot foodpanda", and those are indistinguishable under any rule that lets an unpriced modifier through. Non-sellable kinds (`category`, `modifier_group`) carry none. At line-add the price resolves from the **appending device's branch** and the **order's own channel** — the latter fixed at creation and never inferred later (`02-F1`) — and is captured into the event, after which `01-F53` governs entirely: it is never re-read, so a later price edit cannot retro-price an open order.
  - **Why per channel, and why not a markup rate.** Aggregator commission is 25–35%, so a restaurant prices the same dish differently per channel deliberately — higher on foodpanda, discounted on WhatsApp to steer demand onto a channel it owns. Prices are stored as **integer paisa, never as a rate or a delta off a house price**: a stored markup would put money arithmetic on the line-add path, which `DEC-MONEY-005` bans everywhere. A percentage adjustment is an *editing* affordance that computes numbers the owner then sees and approves (`14-F8` already specifies bulk % edits as individual per-item events for exactly this reason).
  - **Every enabled (branch, channel) pair is priced, and this is enforced at the WRITER.** A publish containing a sellable, non-tombstoned entry that omits an enabled pair's price is **refused**, naming the entry, the branch and the channel. **The enabled set is a REQUIRED input to the publish** (founder ruling July 2026) — not an optional one defaulting to "check nothing". `00 §7`'s config plane does not exist yet, so the caller states the set explicitly, even where that is a constant; making it optional would mean a caller who simply forgot the argument silently received no completeness check at all, which is precisely the omission this FR refuses a fallback in order to prevent. The cost of requiring it is smallest now, while the only production caller is an onboarding path. There is deliberately **no fallback to a house price**: a fallback makes a forgotten aggregator price sell at the in-restaurant rate while commission still takes its cut — invisible at the till, frozen permanently by `01-F53`, and surfacing months later as unattributable thin margin. Refusing at publish turns that into one failed save with a message. The one-number convenience belongs in the editor (`14-F29`), which a bulk import (`15-F8`) or an API client bypasses and this check does not.
  - **An unpriced item is not an 86'd item.** If the order's channel has no price, the item cannot be added: selling requires a number and inventing one is worse than refusing. It is rendered disabled in place with its reason (`27-F4`), never removed from the grid, and the rest of the order completes normally — `01-F17` forbids blocking a **sale**, not an item. This is the opposite disposition to `01-F59` above, and deliberately: an 86'd item has a known price and stays deliberately sellable; an unpriced one has nothing to sell at. Given the publish check this path should be unreachable, and it is specified because a device may hold a version published before the check existed.
  - **The branch axis is DATA, not a second scope — the catalog stays org-scoped and byte-identical everywhere (founder ruling July 2026, `06-F6`).** A chain genuinely prices the same dish differently by location (a DHA outlet above a Saddar one), so the price is keyed by `(branch, channel)`. It would be a serious error to implement that by serving each branch a filtered catalog: `01-F52`'s org scope is what lets a training branch mirror production read-only with no special case (`01-F49`), and per-branch responses would make one version number mean **different bytes on different devices**, destroying the premise `01-F56`'s `divergent` detection rests on. Instead **the published artifact carries every branch's prices**, one version, identical for all; the device resolves its own row from the `branch_id` already in its identity. The cost is that a device can read another branch's prices — accepted, and strictly smaller than the org-wide menu it already holds.
  - **Most orgs have one branch**, for which this collapses to one price per channel. The combinatorial case is the chain, and it is handled by the editor prefilling the whole grid from one number (`14-F29`) rather than by a fallback here.

**One device, one store (added August 2026)**
- 01-F64 **A device database is BOUND to the identity it was created for and refuses any other.** The store records `org_id`/`branch_id`/`device_id` when the file is created — not derived from its contents, because a store that has been opened and not yet written must be bound too — and every subsequent open compares. A mismatch on any of the three **refuses to open**, naming both the identity on disk and the identity that asked (`00 §5.7`), rather than merging. This is a reading `01-F2` ("every **device** persists events locally") and `01-F8` (a device drains **its own** outbox in **its own** `lamport_seq` order) already imply and no clause stated: two identities sharing one `events` table interleave one lamport sequence between two origins (`01-F3`), each store then serves the other's events as its own, and both push them upward into a log `01-F1` forbids unwinding. **Refusing is the whole of the requirement** — `01-N5`'s replacement path is a fresh `device_id`, and no merge, split or re-stamp of a store that has already forked is specified or may be invented. The binding lives with the store core, so it holds for every host and every storage driver (`18 §4`), including the ones that build their own adapter; a check in one host's open path is not this requirement. Two corollaries: (a) **no two apps on one machine may resolve to one device-database file** — each host gets its own OS-level application identity, and the collision is a *directory* collision, not only a filename one; (b) the device database sets an explicit **SQLite `busy_timeout`**, because the default is `0` and this schema's own open path writes, so ordinary multi-handle contention (`01-F2`'s WAL) surfaced as an immediate `database is locked`. The timeout does not cover `SQLITE_BUSY_SNAPSHOT` — a deferred transaction upgrading a stale read snapshot, which no busy handler retries; that case is a transaction-mode question and is **not** closed by this FR.
- 01-F65 **A device host that was not TOLD which device it is refuses to start.** The three ids of `01-F13` are read from configuration (`00 §7` layer 3), and an **absent** key is refused, naming the key an operator must set. The refusal is a *separate, named* resolution rather than a flag on a permissive one, so that a call site states which discipline it is under and a later edit cannot re-enable a fallback by dropping an argument. **Exactly one exemption, and it is a development affordance rather than a policy:** the counter app's documented no-environment launch may seed all three from a marked dev identity, because that seed is the counter's own. Every other host on the same machine falling back to it does not produce an unconfigured device — it produces *the counter*, silently, which is the `01-F64` fork one layer earlier and with nothing on disk to refuse it. A value that is present but blank or padded is refused on both paths alike; a value that is merely not a UUID is **not** refused, because `device_registry` stores `text` and a device stricter than the registry that admits it would reject credentials that work. **⚠ NARROWED BY `01-F80` (g) (August 2026), and the narrowing is one case wide.** This FR was written when the only way a device got an identity was an operator typing three keys, and it therefore reads *absent* as *misconfigured*. Pairing makes **absent** a legitimate state — a device nobody has commissioned yet — so: **all three ids absent AND no stored pairing** is UNCOMMISSIONED and presents `01-F80`'s pairing surface and nothing else, opening no device database (`01-F64` binds one at creation and there is nothing to bind to) and joining no LAN (`01-F72` (d)). **Every other incompleteness — one id set and another not, blank, padded — is refused exactly as this FR says**, because that is a misconfiguration and not a new device; a partial identity admitted into pairing would let a half-configured till silently acquire a *different* one. Once paired, this FR binds unchanged: the ids pairing wrote are read from configuration like any other, and a later edit that empties one is refused.
- 01-F66 **A SECOND HOST PROCESS ON ONE DEVICE STORE MUST NOT SILENTLY PROCEED (August 2026).** `01-F64` binds a store to its identity and refuses *another* identity; it does not reach the case a dress rehearsal actually produced — **the same app, the same identity, launched twice** (a double-clicked shortcut, an operator "restarting" a till that was already up, `ops/startup/restos-counter.bat`'s `:loop` firing over a process that had not exited). Measured on the built binary: both instances started, **neither said anything**, the second signed in, rang four items and showed `Nothing added yet` against `TOTAL Rs 0` while its main log carried `SqliteError: database is locked`. That breaks `01-F2` at its hinge — *"persists events locally **before acknowledging** the action to the UI"* — and `01-F8` underneath it, since two processes each keep their own high-water mark over one `events` table and neither is that device's own `lamport_seq` any more (`01-F3`). **The requirement is on the OUTCOME and not on the mechanism:** the second process may be refused before it opens the store, or refused by the store itself on `01-F64`'s pattern; what is forbidden is *two live tills on one file* and *a refusal nobody can see*. Three clauses. (a) The second process **does not become a usable till** and **returns** (`01-F67`). (b) The FIRST process is **untouched and goes on selling** — last-one-wins is refused explicitly, because a guard that takes a working till down mid-service is worse than the defect it closes (`01-F17`, `00 §5.1`). (c) **Nothing may be left behind that refuses the NEXT launch**: a stale lock survives the power cut that produced it, and a till that will not restart unattended is a stopped till. What this does **not** decide: whether the surviving instance raises its window, or says anything at all — on a counter the running till *is* the honest answer.
- 01-F67 **A REFUSAL TO START MUST REACH SOMEBODY AND RETURN TO ITS LAUNCHER (August 2026).** `01-F64` and `01-F65` each say a host *"refuses to start"* and each say what the refusal must NAME (`00 §5.7`); neither says what a refusal *is as a process*, and both shipped as a **hang**. Measured on the built binaries: the counter's ready callback was wired `app.whenReady().then(cb, fatal)`, and a promise's rejection handler cannot catch a rejection thrown inside its own fulfilment handler — so a `01-F64` refusal produced an unhandled rejection, no window, no dialog and **a process that never exited**; the pass screen's catch did run, wrote its line, and then blocked for ever inside a modal error box waiting for a click nobody makes on an unattended screen. `ops/startup/restos-counter.bat` is a loop around the start script, so **a launcher that never returns never restarts** and the till stays dark until a human walks to it — the failure the loop exists to remove. Therefore every start-time refusal (i) is **delivered** where a person can find it, (ii) **terminates the process with a non-zero status**, and (iii) does neither of those *by waiting for a human*. A modal box is not a refusal on an unattended till: it may accompany the delivery, it may not be the only one and it may not gate the exit. This does not decide the wording, the channel, or the code beyond "non-zero" — and it says nothing about a failure *after* a successful start, which is `01-F17` territory and stays there.

**Tenancy: the org, the branch and the device as NAMED RECORDS (August 2026 — the kernel was org-scoped everywhere and there was nothing for an `org_id` to point at)**

- 01-F68 **The ORG is a first-class record with a NAME, and the org registry is a DIRECTORY — never a gate on ingest.** `§5` has listed `orgs/branches/users/roles` among the cloud tables since Draft 1 and no FR ever said what an org *is*, so the plumbing was built and the record was not: measured August 2026, `org_id` arrives at the gateway as free text, no migration creates an `orgs` table, no code path anywhere creates an org, the only org a running deployment has is assembled at boot from three environment variables into a process-local store that dies with the process, and every surface therefore renders a UUID where a restaurant's name belongs.
  - **Identity:** `org_id`, a UUIDv7 (`00 §6`), minted once at provisioning (`15-F4`) and **never reused**. `01-F1` makes every event under it permanent, so a recycled id merges two restaurants' histories into one ledger with no rule for separating them again. It stays exactly the join key the envelope, the registry and the catalog already share; nothing here changes the key.
  - **The record holds four things, and that is the whole of it:** `org_id`; a required, non-empty `display_name` — what the restaurant calls itself, and the only value `21-F15` permits in an org's name slot; `created_at`; and the `15-F25` lifecycle status. Deliberately absent, each because another FR already owns it: operating profile and hardware capability (`15-F4`, `restaurant-os.md` §6 and its `DEC-HW-003` amendment), the province a fiscal adapter resolves against (`16-F19` — added *there* when the add-on lands, not speculatively here), branding (`06`), and anything to do with plan, billing, quota or metering (`15-F5a`, `15-F24`: metering is measurement only).
  - **⚠ NO LEDGER TABLE MAY CARRY A FOREIGN KEY TO THIS RECORD, EVER.** Events already exist under org ids that no registry row names — that is the state of the deployment today — so a referential constraint would refuse ingest for exactly those orgs, and refusing ingest is refusing a sale that a till has already rung and persisted (`01-F17`, `00 §5.1`, `01-F2`). It also buys nothing: **admission is the gate and it is one layer up.** A device cannot push at all without a registered, unrevoked, unexpired credential (`01-F25`, `01-F47`, `01-F48`), that credential names its org, and `01-F71` (c) already quarantines an envelope whose `org_id` disagrees with it. A second gate at row level can only reject events a credentialed device produced, which is the failure mode and not the protection.
  - **An org with events and no record is UNNAMED, not invalid.** It folds, syncs, prints and settles exactly as any other; it is surfaced to the vendor (doc 15) as a provisioning gap to fill, and rendered per `21-F15` until it is. Reconciliation never writes into the ledger and never withholds service — naming a tenant is an administrative act, not a validation of its history.

- 01-F69 **A BRANCH is a named record under exactly one org; its two discriminators already exist, and one obvious field is REFUSED rather than deferred.** `01-F25` gives a branch its `type` (`branch | prep_kitchen | storage`) and `01-F49` its `class` (`production | training`); neither says a branch has a name, and `15-F4` creates branches at provisioning with nothing stated about what it creates.
  - **Required to run:** `branch_id` (UUIDv7, never reused — `01-F68`'s reasoning applies unchanged), the owning `org_id`, a required non-empty `display_name`, `type`, `class`, `created_at`. A branch is what a device's identity resolves against (`01-F65`) and what fan-out is keyed by (`01-F71` (d)), so an unnamed branch is the same defect as an unnamed org one level down — the till, the pass screen and the fleet dashboard all print it.
  - **A branch carries NO TIMEZONE, and this is a refusal, not a deferral.** `01-F46` anchors the business day to Asia/Karachi *regardless of cloud region or device locale* and states plainly that the cutover hour is the layer-2 setting while **the timezone anchor is not configurable**. A per-branch timezone would be a layer-3 record overriding platform law, which `00 §7`'s strict layer ordering forbids outright, and its failure would be silent: every duration, day boundary, shift report and cash reconciliation would re-date itself against a field nobody remembers setting. A future multi-timezone deployment is an amendment to `01-F46`, not a column here.
  - **Address and phone are DEFERRED to the FRs that will read them** — `16-F19` (province plus branch registration status with the authority) and `06-F9`/`06-F11` (delivery capture) — because a field with no reader is a fact captured by human discretion and left to drift, which is the automation law (`00 §5.8`, `restaurant-os.md` §2 law 1) applied to configuration. What Wave 1 needs from a branch is a name.
  - **A branch record is never deleted.** `01-F51`'s droppability is a *training*-branch property, argued from the fact that a training branch is by construction not history, and it extends to nothing else. Decommissioning a production branch is revoking its devices (`01-F42`, `14-F13`); the record and its ledger stay.

- 01-F70 **A DEVICE carries a human name, it is REQUIRED at registration, and it lives on the cloud REGISTRY row.** Measured August 2026: `device_registry` holds `org_id`, `branch_id`, `device_id`, `device_class` and `revoked_at`, and the provisioning command takes `--class` and no label — so `14-F12`'s device list and `15-F11`'s fleet dashboard can name a till only by its UUID, and the operator reading either is by construction not standing in front of it.
  - **On the registry row, not in device-local configuration** (`00 §7` layer 3). A name typed into a device's own environment is a name only that device knows, and both surfaces that need it are lists of devices nobody is holding. It reaches the device itself by the same admission path that already carries its class and branch; a device that has not yet learned its own name renders per `21-F15`.
  - **Required at registration, on `01-F65`'s discipline:** an absent name is refused, naming the argument an operator must supply, so a nameless device cannot be created and named later — which never happens. "Counter till", "Kitchen screen" is the register; the value is free text and the product asserts nothing about it beyond non-empty.
  - **Renaming is `device.manage` (`14-F30`) from `14-F12`'s list**, and is an ordinary layer-2/3 settings change (`14-F2`). It is **not** `device.registered`, which `14-F30` records as deliberately unemitted for want of an authenticated actor, and this FR does not unblock that.
  - **The name is a LABEL and never an identifier.** `device_id` remains the sole key for admission, fan-out, watermarks, relay attestation (`01-F13`) and `01-F64`'s store binding. Two devices may legitimately share a name; nothing may key on it, and a rename changes no history because no event ever carried it.

- 01-F71 **TENANT ISOLATION IS A TESTED PROPERTY WITH NAMED ENFORCEMENT POINTS.** `00 §5.4` calls org data isolation absolute and `01-F27` puts server-side authorization on every operation, but neither names *where* isolation is enforced nor requires anyone to prove it — and a security property nobody can point at is a property nobody can protect from a refactor. This FR does not invent a mechanism; it names the ones that exist and makes them assertable.
  - **The requirement:** a subject authenticated in one org must never read, write, cause a write in, or be fanned out data belonging to another — on either plane (`18 §6`), through any surface, in any degraded state.
  - **The enforcement points, measured August 2026, each named so a later edit is visible.** (a) The permission matrix refuses when the subject's org differs from the scope's, before any action-specific reasoning — `can()` and `reportScope` both. (b) On the cloud plane the org is taken **from the authenticated subject and never from the request** (`01-F27`'s "not at login" reading), so an org stated by a caller changes nothing. (c) At the sync gateway an envelope whose `org_id` disagrees with its session's is **quarantined, not dropped** (`01-F37`) — it is retained verbatim as evidence and the pusher is notified, per `01-F37`'s identity-failure clause. (d) Fan-out is keyed by the `(org, branch)` pair as a **structured** key, never a concatenation: `("ab","c")` and `("a","bc")` are distinct tenants and a separator-less key maps both to one delivery set, which is a cross-tenant leak with no error in it. **(e) The reference-data serve path derives the artifact key from the SESSION and refuses a request that states another** (`01-F75`/`01-F76`, added August 2026 under this FR's own rule that adding an enforcement point adds a clause here). ~~Spec'd, not yet implemented.~~ **PARTLY IMPLEMENTED, and the halves are named so nobody adds a check that exists or routes around one that does not.** SHIPPED: `services/sync-gateway`'s `handleReference` refuses a `reference_request` whose `scope.org_id` is not the session's — an `AuthRejectedError`, never a clamp — and the response echoes the SESSION's key. ~~OWED: the BRANCH half has no resource to bind to yet (the roster serve path is step 6 of `plans/saas-pivot/staff-over-the-wire.md`; the gateway serves `catalog` only and refuses any other resource by name)~~ **THE BRANCH HALF IS SHIPPED TOO (step 6, August 2026), and it was the RESOURCE that unblocked it rather than any new reasoning:** a `catalog` frame is pinned by the codec to `branch_id: null`, so until the branch-scoped roster was served there was no branch a frame could state and the session's could differ on — a check written earlier would have had no case that reaches it, and a test aimed at it would have stayed RED under a correct implementation. `handleReference` now refuses any `scope.branch_id` that is neither `null` nor the session's, as the same `AuthRejectedError` and by the same sentence as the org half, and the check is written on the SCOPE rather than per resource because `01-F76` gives every resource ONE scope shape. Measured under this FR's own rule — with that check alone deleted, `tenant-isolation-reference-serve.test.ts` §B is **2 failed of 499** and both are its own; a control rewording both refusals kills 0. **What is still OWED is `01-F76`'s device-side `foreign_artifact` belt (step 7)**, and the resource-refusal half of this clause is retired rather than transferred: `01-F75`'s set is closed at two members and the gateway serves both, so there is no unserved resource left to refuse. ~~⚠ Nothing in any suite asserts the shipped half — measured out of tree by deleting it: 0 of 471 gateway tests red — so it is a hand-written assertion owed with step 6's oracle.~~ **COVERED as of 2026-08-19, and the deferral it proposed was refused rather than satisfied.** This clause is not advisory — *"each point carries a test that FAILS when that point alone is removed … the test must run two tenants and mutate the point under test"* — so owing the assertion to a later step was not a reading this FR permits, and an adversarial review said so. `services/sync-gateway/src/__acceptance__/tenant-isolation-reference-serve.test.ts` runs two populated tenants and meets the bar by measurement: with the org check deleted and the file present it is **1 failed of 477**; with the file hidden it is **471 passed, exit 0** — which is the FR's own test, and the number that had made the gap invisible. The resource half is covered the same way (2 of 477), and a control rewording both refusals kills 0. **Two things the round taught, kept because the next enforcement point will meet them:** every fixture in the repo passed the session's own key, so *a fixture that cannot express a foreign key cannot test a refusal of one* — the builders take the key as a varied argument now; and *refused* and *served nothing* are separate claims, because a mutant that answers with the correct error class after already serving the rows passes the first and fails only the second. The catalog frames carry no tenant at all — the org is read from the session and there has never been a client-stated key to check — and `reference_request` puts `(resource, scope)` on the wire for the first time, which is a tenant key in bytes a caller controls.   - **(f) THE BULK DATA-COPYING PATH — backup artifact, restore, and 22-F16's owner export — CARRIES EXACTLY ONE TENANT'S ROWS, AND THE ORG IT IS ABOUT IS NEVER STATED BY A CALLER** (August 2026, added under this FR's own rule that adding an enforcement point adds a clause here). This is the one surface in the product whose entire purpose is to produce a copy of a tenant's data as a FILE, so the leak it can produce is not a row served to the wrong screen but a whole ledger handed to the wrong restaurant, on disk, with no session left to revoke. **Three checks, and each is where it is because the other two cannot cover for it.** (i) **The artifact and the bundle are filtered by `org_id` at the READER**, per table, over the tables the live schema says carry one — a whole-database dump written once and named per org restores perfectly and hands every restaurant a copy of every other restaurant's ledger, which is the same shape as (d)'s concatenated key: a cross-tenant leak with no error in it. (iii) **On the tenant plane the export's org comes from the authenticated subject** — that is (b) restated on a new surface rather than a new rule, and it is named here because an export id is a CAPABILITY (it names a bundle holding a complete ledger), so a lookup by id with no org predicate is the whole leak in one query. **The tests, per the clause below, exist and are named:** `services/api/src/__acceptance__/owner-export.test.ts` §B runs two populated tenants against one host for (iii), and `services/jobs/src/__acceptance__/tenant-backup-restore.test.ts` §B3 (byte-level, both directions), §D2 (a restore beside a live neighbour) and §G5 cover (i) and (ii). ⚠ **What this clause does NOT reach: the artifact once it is on disk.** File-system permissions, `22-F10`'s at-rest encryption and `22-F13`'s export-bundle retention are doc 22's, and none of them is this FR's to assert — isolation here ends at what the writer put in the file.
  - **⚠ AMENDED BY 28-F5 (b′) (August 2026) — clause (b) binds an authenticated SUBJECT on the TENANT plane, and a service credential is not a subject.** `15 §8` puts internal routers on a separate auth domain whose tokens are never valid on tenant APIs; measured August 2026, `services/api` already reaches the gateway's internal tenancy, device, org-event and published-catalog routes with `org_id` **as a query parameter**, and naming which tenant's data a vendor-plane caller wants is what a cross-tenant surface does. Read absolutely, (b) deletes that parameter and leaves the vendor plane unable to serve an org name, a branch list, a device list or a catalog history at all — so the narrowing is recorded here, where a session routed to this doc lands, rather than only in the amending document. **What constrains that hop instead: `28-F18` (c), which puts it in this register as an owed clause, and `28-F17`'s owed boot-asserted internal gate.** Nothing about (b) changes on the tenant plane, where org is not an input to any port and must not become one.

  - **Fail-closed on the org axis**, restating `01-F48`'s posture: where isolation state cannot be read, participation is refused, not granted.
  - **What this FR is not:** it is not satisfied by a `where org_id = …` in a query. That is how one call site implements it. This is the claim that the property cannot be routed around, and that claim is only ever worth what its mutants prove.

**LAN admission (August 2026 — closes the gap `01-F48` names and `plans/wave-0/sec-review-followups.md` §4 calls "the last substantive Wave-0 gap")**

- 01-F72 **THE BRANCH LAN IS A MUTUALLY AUTHENTICATED CHANNEL OR IT DOES NOT RUN.** `01-F27` has required LAN participation to be validated *"hub-side on LAN"* since Draft 1 and nothing has ever validated anything. Measured on the shipped binaries, August 2026: `mesh-session.ts`'s `hello` arm admits a peer after consulting `isRevokedPeer` **and nothing else** — its own comment says *"the mesh hello arm inspects no token"* — both Electron hosts pass the literal string `"lan-member-unauthenticated"` where a credential belongs, the mesh is constructed unconditionally at host start, and `listen_host` defaults to `0.0.0.0`. **So every launch of either app opens an unauthenticated read-write port onto the branch money ledger, on every interface, for anyone on the shop Wi-Fi.** The customer network in a Pakistani restaurant is the staff network.
  - **(a) Admission requires PROOF OF POSSESSION of a pairing-issued device credential (`01-F73`), verified against the branch roster (`01-F74`).** A bearer string carried in a message body is not proof: it is replayable by anyone who observed it, and on a plaintext LAN everyone observed it. This is why the fix is not "check the token the `hello` already carries".
  - **(b) The mechanism is mutual TLS, and the session's device identity is the PEER CERTIFICATE's subject — never a `device_id` read from a frame.** This clause does the most work and is the reason to prefer it: `from` becomes trustworthy at the transport, so every message arm is authenticated by construction. The alternative is a check inside each arm, which today would be eleven checks that must each be remembered — and this corpus already records what happens to a protection that must be remembered. It closes, without naming them individually, the `event_batch` arm that ingests from any sender, the `push` arm that trusts a claimed origin, and the forged `push_ack` that can advance a device's own cloud write-checkpoint past events it has not pushed (`01-F8`) or install a `renewed_token` of the sender's choosing (`01-F47`).
  - **(c) One mechanism, not three.** mTLS delivers authentication, proof of possession, confidentiality (`00 §5.4`, *"TLS everywhere"* — a law this leg has never met) and revocation-by-trust-anchor in one audited implementation. A hand-rolled challenge–response over `ws://` delivers the first two and needs the other two built beside it, plus nonce state and a replay window nobody will test.
  - **(d) Fail closed, and closed means SILENT rather than degraded.** A host that cannot present a credential, or cannot read a roster, **does not listen and does not dial**. There is no unauthenticated mode, because an unauthenticated mode is what shipped; a fallback path is the defect, not the mitigation.
  - **(e) It never blocks a sale (`01-F17`, `00 §5.1`).** A branch with no admissible LAN is a branch of solo tills: each persists locally (`01-F2`), each drains to cloud when it holds WAN. The degradation is **named on the honesty strip** (`00 §5.7`) — a cashier must be able to tell a quiet branch from a broken one, and `01-F15`'s sub-second propagation silently becoming "never" is exactly the aged-number-shown-as-fresh failure `00 §5.7` exists to forbid.
  - **(e·i) A COMPLETED HANDSHAKE IS NOT PROOF OF ADMISSION, and an implementation that reads it as one is wrong in the direction that matters** (measured on the out-of-tree probe, August 2026). Under TLS 1.3 the dialling side's `Finished` precedes the accepting side's verdict on the dialler's certificate, so a refused device's `secureConnect` fires normally and it is then cut off by a fatal alert. A self-signed impostor presenting the till's exact subject name reached `secureConnect` on the client and was refused by the server — both, in one run. The consequence for this product is narrow and must stay written down: **the refusal is observed as the CLOSE**, which the mesh already treats as peer-loss, so nothing extra is owed — but a later "optimisation" that treats a successful dial as admission would re-open the hole from the other end.
  - **(f) What this does NOT decide: the topology.** Under `01-F13`'s election the verifier is the elected hub; under the branch-relay ruling (`plans/saas-pivot/plan-of-record.md` R2) it is the fixed branch authority. Admission is a property of the channel and of who the roster names, not of who won an election — so this FR survives that change without amendment, and the work is not owed to it.

- 01-F73 **THE PAIRING-ISSUED DEVICE CREDENTIAL — `01-F25`'s unbuilt half.** `01-F25` has said *"registration is a one-time pairing via back office code"* since Draft 1. No pairing code has ever existed: devices are provisioned by a shell command on the service host that mints a symmetric bearer, which is why `01-F25`'s own clause is cited by `14-F13` as the thing an owner cannot do.
  - **(a) The keypair is generated ON the device at pairing.** The private key never leaves it, is never transmitted, never logged and never backed up. What travels to the cloud is the **public key** — and nothing else, so there is no state a stolen pairing response can be replayed into.
  - **(b) The cloud returns a certificate naming `(org_id, branch_id, device_id)`** — signed by a **per-org** issuing key. Per-org and not platform-wide: a branch roster from one org must be *structurally* incapable of admitting a device from another (`00 §5.4`, `01-F71`), which a single platform issuer would leave to a field comparison somebody can forget. **Three facts, not four, and `device_class` is deliberately NOT among them** (corrected August 2026 from the out-of-tree probe that proved this design, before any of it was built). Class decides hub eligibility (`01-F39`), it changes when a device is re-purposed, and a certificate is a long-lived credential — so putting it here would mean **re-issuing a credential to change a role**, and would put one fact in two places where the roster (`01-F74`) already carries it authoritatively. Two writes of one fact disagreeing silently is this corpus's most-repeated defect; the certificate answers *who*, the roster answers *what it may do*.
  - **(b·i) The certificate is CONSTRUCTED ON THE CLOUD PLANE, and that placement is a decision, not an implementation detail.** Node's standard library parses X.509 and does not build it, so somebody must encode it: hand-rolled ASN.1 is security-critical encoding well past `18 §15`'s *"or 50 lines of our own code"* bias, and a library placed in `sync-client` would ride into every shipped till for a step each device performs **once, at pairing, while online, against the cloud**. Issuing on the plane that already holds the issuing key puts the dependency where it is cheap and leaves the kernel package and the desktop bundle unchanged. The device sends a public key and receives a certificate; it never encodes a request and never holds issuing material.
  - **(c) This is a SECOND credential beside `01-F47`'s cloud token, and the separation is a decision rather than an oversight.** The cloud leg is TLS to a known endpoint whose verifier may legitimately hold a symmetric secret. The LAN leg has no such endpoint and **no participant who may hold cloud secrets**: verifying an HS256 token on the LAN means handing every till the key that mints credentials for the fleet. The two may reconcile when the signed edge agent becomes the branch authority (R3); they may not be collapsed before that by giving tills the minting key.
  - **(d) The certificate expires and renews on `01-F47`'s pattern** — silently, on any authenticated cloud contact including hub-relayed contact. **Expiry withdraws LAN admission and never the sale** (`01-F17`): an expired-certificate device is a solo till per `01-F72` (e), not a stopped one.
  - **(e) A lost private key is `01-N5`'s replacement path: a fresh `device_id` and a fresh pairing.** No escrow and no re-issue onto the same identity — a credential that can be re-issued to whoever asks is not a credential. This is the same refusal `01-F64` makes about a forked store and for the same reason.
  - **(f) Not decided here:** the pairing surface (`01-F25` says back office; `14` owns it) and whether the org issuing key lives on the cloud plane or under an offline root (`15`/`29`). Both are real questions and neither blocks admission. **⚠ AMENDED August 2026 — the first half was read as deferring more than it deferred, and for a month it deferred everything.** This clause defers the **surface**, which is doc 14's; it never said who owns the pairing MODEL — the code, its lifetime, its claim, its limits — and the answer turned out to be nobody, so `01-F72`'s admission had a credential no operator could obtain and `provision-device.ts` recorded *"building it means inventing policy"* as its reason for not building it. **`01-F80` owns that half now**; the surface is still doc 14's and the issuing-key location is still open.

- 01-F74 **THE BRANCH ROSTER IS THE OFFLINE TRUST ANCHOR, AND STALE IS NOT UNREADABLE.**
  - **(a) The cloud signs, per branch, the set of that branch's devices** — `device_id`, `device_class`, certificate fingerprint, revocation state — and every device caches it **durably** in its own store (`01-F2`), because the whole point is to be right when the WAN is not there.
  - **(b) It is REFERENCE DATA, not ledger, on `01-F52`'s exact pattern:** versioned, distributed as snapshot-plus-delta over the same sync channel, applied monotonically (`01-F56`), and **never an input to any fold** — a projected value that read admission state would depend on roster sync state at fold time, which is the `01-F34` break law 1 exists to prevent. **⚠ AMENDED August 2026 — as of `01-F75` there is no frame this clause can ride, and saying so is the difference between unbuilt and unbuildable.** `01-F75` replaces the catalog triple with one resource-discriminated frame and closes the resource set at `catalog` and `staff`, excluding this roster deliberately: it is a *signed* artifact and that FR specifies no signature envelope. ~~**This clause is therefore OWED and blocked on a named amendment to THIS document** — the signature envelope, plus the `device_roster` member of `01-F75`'s set, in one change. The smuggling ban survives the unblocking and is not retired by it: the roster rides its **own** member of `01-F75`'s set, never a `reference_response` typed for another resource.
  - **(c) Admission is: the peer's certificate verifies against the org issuer, its fingerprint appears in the roster, and that entry is not revoked.** Both the chain and the pin, and an implementer may not drop either as redundant: the chain alone admits anything the issuer ever signed — including a device revoked an hour ago, since there is no CRL on a branch LAN and there is not going to be — while the pin alone would admit a certificate no issuer vouched for if a roster is ever assembled from anything but issuance. Together, a compromised issuer still cannot admit a device the roster does not name. LAN revocation is therefore a *field of the roster*, which **retires `isRevokedPeer`** — an in-memory `Set` populated from observed cloud refusals. That set dies with the process, so a restarted hub today re-admits a device the owner revoked: `01-F48`'s fail-closed rule inverted by its own cache, and inverted in the direction that grants access. Deleting it is the fix; making a negative cache durable is not, because a cache of refusals it happened to see was never the authority.
  - **(d) STALE IS NOT UNREADABLE — the clause that keeps `01-F48` and `01-F17` from contradicting each other.** A roster that is absent, corrupt, or whose signature does not verify is **unreadable**: refuse, per `01-F48`. A roster that verifies and is merely **old**: **admit**, and surface its age (`00 §5.7`). This is `01-F48`'s own distinction — *"an unreadable state is not proof of revocation"* — carried to the other side of the same test. A WAN-down branch cannot receive a revocation, and saying so honestly is the offline-first answer; refusing the LAN because the internet is down would take a whole branch's service off a broken router, which `00 §5.1` forbids in its first sentence.
  - **(e) `01-F48`'s 30 s eviction bound is unchanged and becomes reachable on the LAN for the first time:** a roster delta is fast-path reference data (`01-F15`), and the authority drops the peer's session on applying it rather than at that peer's next voluntary contact. Where no path reaches the branch, the bound does not apply and never did — `01-F48` says *"where any path reaches it"*.

- 01-F80 **THE PAIRING CODE IS A ONE-TIME, SHORT-LIVED CLAIM ON A DEVICE THE OWNER HAS ALREADY DESCRIBED — `01-F25`'s *"one-time pairing via back office code"*, specified for the first time (August 2026).** `01-F73` (f) deferred *"the pairing surface (`01-F25` says back office; `14` owns it)"* and nothing anywhere specified the **credential** half, so `services/sync-gateway/src/provision-device.ts` recorded the gap in its own rejected-alternatives list — *"the pairing-code model — how a code is minted, how long it lives, that it is claimed once, what binds it to a class and a branch — appears in the corpus only as that one clause, so building it means inventing policy"* — and a shell command on the service host stayed the only way a till comes into existence (`28-F13` names the same block from the tenancy end; `14-F13` names it from the owner's). **Doc 14 still owns the SURFACE (`14-F26`, `14-F12`); this FR owns the code, its lifetime, its claim, its limits and its refusals.** ⚠ **It is a different act from R46's vendor invite code (`plans/saas-pivot/plan-of-record.md` §0, now `28-F23`) and the two must not share an implementation:** an invite code admits an **org** to the deployment and is redeemed by a stranger holding no account; a pairing code admits a **device** to a branch and is minted by an authenticated owner inside an org that already exists, and every clause below rests on that difference. ⚠ **Specifically, do not copy (b)'s length or (c)'s TTL across.** `28-F23` leaves its code's *"format, length and TTL"* undecided on purpose and says they must not be invented at a keyboard — and the numbers here are sized for a code **read aloud inside the conversation that mints it**, whereas an invite code is handed to a prospect ahead of time through a channel this corpus does not yet own (`28 §9.21`). Same word, two threat models; a shared helper is how one FR's reasoning silently becomes the other's. ⚠ **THREE NUMBERS BELOW ARE CHOICES WITH NO CORPUS PRECEDENT AND ARE MARKED AS SUCH SO THEY ARE CHEAP TO OVERTURN** — the code's length (b), the TTL (c) and the shape of the limit (e). Everything else is derived from FRs that already exist, and each derivation names the FR it comes from; R4 puts nothing in the field, so the way to overturn any of it is to amend this FR rather than to write a different shape into a pairing service.
  - **(a) The owner MINTS and the device CLAIMS; the device chooses nothing.** Minting fixes `org_id`, `branch_id`, `device_class` (`01-F39`) and `01-F70`'s required name, and mints the `device_id` — UUIDv7, never reused, on `01-F68`'s reasoning. The claim carries **the code and a public key and nothing else** (`01-F73` (a): the keypair is the device's and the private half never travels). Class and branch are not claimable because `01-F40` enforces slice predicates *"from device class + role — never client-declared"*, which is the ground `provision-device.ts` already rejected device self-registration on; the name is not claimable because `01-F70` requires one at registration and nobody types a name on a till. **The claim states no tenant either** — a caller-stated `org_id` would be a client role claim at the one moment in this product's life when there is no session to check it against (`01-F71` (b)) — so a code resolves to exactly one pending pairing **deployment-wide** and a mint that collides re-draws. **The consequence is what makes (e) small: an unauthenticated caller can never cause a registry row to exist.** It can only consume a pending pairing an authenticated owner already created, so guessing cannot manufacture the permanent junk device `01-F68`'s never-reuse rule would otherwise leave behind.
  - **(b) What a code IS: 8 CSPRNG digits, displayed and read as `1234 5678`.** Digits and not letters because it is read down a phone to whoever is standing at the till and typed on the numeric keypad `01-F61` already puts on that surface, while a Latin-letter alphabet assumes a speller — which `21 §5`'s evidence says this population is not. **The stated cost is length**: more characters for the same entropy, which is the trade taken deliberately. **No check digit** — the claimant is online by construction, so a typo costs one round trip, while a checksum is a second encoding to specify and get right on both sides (`03-F40`'s two-interpretations defect is this corpus's own instance). The cloud stores an **Argon2id hash at `01-F61`'s cost floor and never the code**, on `28-F13`'s discipline for a minted secret: a database read then hands over no live pairing. ⚠ **The entropy is sized against an ONLINE guess under (e) and against nothing else** — 26.6 bits is not an offline margin, and what makes that sufficient is the 15-minute TTL, the one-time claim and the hash together. **A change that lengthens the TTL re-opens the length**, and that is why the two are written in one FR.
  - **(c) TTL is 15 minutes and it is NOT an org setting.** A code that outlives the conversation it was read in stops being a claim and becomes a standing credential on a sticky note beside the till. Re-issuing is one act on doc 14's surface and it **kills the previous code**; re-issue is the pressure valve, not a longer life (`00 §7`, presets-not-knobs). **What expiry means, per state, because the two states are not alike.** An **unclaimed** code that expires leaves *nothing* — no registry row, no certificate, no device, nothing to clean up — and the operator asks for another. A **claimed** pairing whose response never reached the device is the case that matters, and (d) answers it rather than leaving it to a retry loop.
  - **(d) ONE-TIME CLAIM, AND THE RACE IS DECIDED BY THE PUBLIC KEY RATHER THAN BY ARRIVAL.** The first claim to commit wins and the pending row records the fingerprint of the key it issued over. Re-presenting the same code **with the same public key** inside the TTL returns **the same certificate** — a dropped response is a retry, not a burned device — and every other presentation is refused `already_claimed`. So two devices presenting one code produce **one** device: the loser is refused rather than handed a second certificate for one `device_id`, which would be `01-F64`'s forked store and `01-F66`'s two-tills-one-identity arriving at the credential layer, interleaving one `lamport_seq` between two origins (`01-F3`, `01-F8`) with nothing on disk to refuse it. After the TTL a claimed-but-undelivered pairing is dead: its registry row is an unusable device that an owner can *see and revoke*, which is what `01-F70`'s required name buys and what `14-F13` removes.
  - **(e) RATE LIMIT: bound the burst, make it observable, and never lock the deployment.** Failed claims are capped per source over a short window and refused `rate_limited` beyond it; sustained failure **also** raises fleet health (doc 15), and the reason it raises rather than escalates the block is `01-F31`'s ratified *detect and alarm, never reject* posture — **borrowed by analogy and said to be so**, since that FR governs money keys at the gateway and rules nothing about pairing. **A deployment-wide lockout is refused rather than deferred:** on R17's pooled deployment it would let one attacker stop every tenant commissioning a till, which is a worse outcome than the guessing it prevents. **What a limit here does NOT have to do is stop junk devices** — (a) makes that unreachable, and a limit sized as though it did would be sized against the wrong threat.
  - **(f) THE CLAIM IS AN UNAUTHENTICATED WRITE — ONE OF EXACTLY TWO — and its refusal SAYS WHICH.** It is served on the cloud plane over TLS to a known endpoint (`01-F73` (c)) because the device holds no credential yet by construction. ⚠ **Named as a PAIR rather than as "the only one", because the absolute was written here first and is false:** its sibling is `28-F12`'s self-serve signup, unauthenticated by the same necessity and gated by R46's invite code. Two is a list somebody can maintain and audit; *"the only unauthenticated write"* is a claim each side makes about itself while the other one exists, which is how a second door stops being counted. **One response carries everything a device needs to become a till:** its identity (`org_id`, `branch_id`, `device_id`, `device_class`, name), `01-F73`'s certificate with its org issuer PEM, `01-F81`'s pinned roster-signing key, and `01-F47`'s device token — **one act, two credentials.** `01-F73` (c) keeps them separate *as credentials*; nothing ever said they arrive separately, and the token issued here is simply the first value of the one `sync-client` already persists and renews (`01-F47`), never a second storage path. **There is no proof-of-possession challenge:** a certificate is useless without the private key, and `01-F73` (b·i) has the device *never encode a request*, so a CSR-shaped step would add a signature format to the till for no gain. **The refusal set is CLOSED — `unknown_code` · `expired` · `already_claimed` · `rate_limited` · `unavailable` — and the till must say which one** (`00 §5.7`): those five send an operator to five different actions and *"pairing failed"* sends her to none. ⚠ **Distinguishing `unknown_code` from `expired` tells a guesser that a code once existed, and that is a deliberate trade, not an oversight**: the guessing budget is already bounded by (e), while an owner reading yesterday's code off a note needs to be told to re-issue rather than left doubting her typing.
  - **(g) A HOST WITH NO IDENTITY AT ALL PAIRS; A HOST WITH A PARTIAL ONE STILL REFUSES — `01-F65` is NARROWED here, by name.** R40 requires a restaurant to reach a paired till *"with nobody touching a terminal"*, so the identity a device runs under is the one **pairing wrote** (layer-3 configuration, `00 §7`); requiring an operator to set three keys first would keep the shell command alive and leave the pairing code a decoration on it. ⚠ **This is a READING of R40 and not a transcription of it** — R40 rules that signup reaches *"a device pairing code"* with no terminal, and the step from there to *pairing supplies the identity* is taken here, because the alternative (operator sets the ids, the code adds only the LAN credential) makes the mint and the machine two writers of one identity. **The narrowing is exact: all three ids absent AND no stored pairing = UNCOMMISSIONED**, which presents the pairing surface and **nothing else** — no device database exists yet, because `01-F64` binds one at creation and there is no identity to bind to; no ledger, no LAN (`01-F72` (d)). **Any other incompleteness is a misconfiguration and is refused exactly as `01-F65` already says**, blank and padded values included. **An uncommissioned device is NOT a `01-F67` refusal and must not be built as one:** `01-F67` forbids waiting for a human because an unattended till that waits is a dark till, and pairing is attended by construction — somebody is standing there with the code. Once paired, `01-F64`, `01-F65`, `01-F66` and `01-F67` bind unchanged.
  - **(h) RE-PAIRING IS A NEW DEVICE, AND THE DRAIN IS AN OPERATOR ACT THIS FR NAMES RATHER THAN ENFORCES.** `01-F73` (e) already refuses re-issue onto one identity, so a lost private key is a fresh `device_id` and therefore — by `01-F64` — a fresh store, **and the old store's unpushed events do not travel with it.** They are not lost, and the reason is the separation `01-F73` (c) already made: the two credentials are independent, so the old identity's `01-F47` cloud token still drains its outbox (`01-F8`) on `01-F50`'s drain-first shape. ⚠ **Nothing enforces the order and this FR invents no enforcement** — it is written down so a runbook can, and so nobody reads a fresh pairing as a migration of the device that came before it.

- 01-F76 **AN ARTIFACT IS `(resource, scope)`, AND A VERSION NUMBER IS MEANINGLESS WITHOUT IT.** R25 makes the staff roster **branch-scoped** — a till receives its own branch's people — and `01-F60` has already recorded what that costs: a branch-scoped artifact means **one version number meaning different bytes on different devices**, which is precisely why the catalog is org-scoped and stays so. It is written here rather than in an implementation because that is the only place it could be reviewed.

  - **THE SERVER REFUSES FIRST, AND THE DEVICE'S REFUSAL IS THE BELT TO THAT BRACE.** `01-F71` (e) is the enforcement point and is written into that FR's register in the same change as this one: the org comes from the authenticated session and the branch from the device's own identity, and a `reference_request` stating any other key is refused as an auth failure rather than clamped. This is not redundancy with the clause below — putting the artifact key on the wire is what creates the exposure, since the catalog frames carried no tenant at all, and a scope a caller may name is a client role claim that commandment 8 forbids trusting. Under R25 the roster's scope IS its credential blast radius (`11-F21`), so a device free to name a branch defeats the whole ruling in one field.
  - **A device REFUSES an artifact whose key is not one of its own** — a roster scoped to a branch that is not this device's, or a resource this device does not consume — and never applies it; the refusal is observable in device health (`01-F56`, `00 §5.7`), and the org/branch axis is fail-closed (`01-F71`, `01-F48`). Without this clause the scope is decoration: a mis-routed roster applies silently as version N, every later comparison agrees with itself, and the divergence `01-F56` exists to detect is undetectable by construction. **The refusal needs a NAME:** `01-F56`'s device-side vocabulary is closed at `stale` / `needs_snapshot` / `malformed` and none of them is this — a foreign key is not a malformed row, and reporting it as one would tell a fleet dashboard that a writer is emitting bad data when what happened is a routing failure.   - **Fan-out is keyed by the artifact key**, on `01-F71` (d)'s structured-key rule: a branch-scoped notice reaches that branch's devices and no others.

- 01-F78 **A BRANCH ROSTER CONTAINS THE PEOPLE WHO CAN ACT AT THAT BRANCH, AND EACH ROW CARRIES ONLY THE ASSIGNMENTS THAT APPLY THERE (August 2026).** `01 §9.7` posed both halves and said in terms that **"nothing selects a roster's rows until this is ruled"**; a first implementation selected them anyway and decided the second half in a query, which is the case this FR exists to stop being decided silently (commandment 2). ⚠ **PINNED INTERPRETATION, not a founder ruling** — every clause below is derived from FRs that already exist, and R4 puts nothing in the field, so overturn it by amending this FR rather than by writing the other shape in a publisher.
  - **Half one — who is in it: every person holding an assignment that REACHES this branch.** That is her own-branch assignments plus `01-F26`'s org-wide ones (`branch_id: null`), which is how an owner holds Appendix A's "everything" and therefore how she unlocks a till at a branch she does not staff. A person assigned to two branches appears in **both** artifacts, because she works at both and `03-F53` lets any member of the branch roster identify at the pass. The rule is exactly `rolesAt`'s existing predicate in `packages/domain` — `branch_id === null || branch_id === this branch` — which matters more than its content: `can()` already answers "may she act HERE" that way, so a roster built on any other rule would populate a grid with people the matrix then refuses, and the till would offer a tile that cannot do anything.
  - **Half two — what her row carries: only the assignments that reach this branch, never all of them.** `01 §9.7` names the cost of the other answer precisely — *"a row carrying every branch's assignment also tells every till the org's branch structure"* — and that is `01-F71`'s isolation boundary crossed by a reference-data artifact rather than by a query. It is also the half R25 was bought for: making the roster branch-scoped to narrow the credential blast radius, and then shipping the org's whole assignment graph inside it, spends the purchase. Nothing on the device needs the rest: `can()`'s subject is evaluated at this device's branch, `reportScope` narrows at this device's branch, and `01-F61`'s grid renders a name.
  - **⚠ WHAT THIS COSTS, STATED RATHER THAN DISCOVERED.** A device cannot compute "she also works at Gulberg" and must not try — that is not a gap to be filled by a later join, it is the property. And a person whose ONLY assignments are at other branches is **absent from this artifact entirely**, so a `02-F41` attribution written by her at this branch is unresolvable here — which cannot happen, because she cannot unlock here either, and the two facts are the same fact by half one.
  - **The status a row carries is THIS branch's**, per `11-F22`'s per-(person, branch) clause; a person `inactive` here and `active` at Gulberg is `inactive` in this artifact and carries no `pin_hash` (`11-F21`). That is not a third rule, it is halves one and two applied to the field `11-F22` already decided.

- 01-F79 **THE TILL ASKS THE CLOUD TO CHANGE ITS OWN OPERATOR'S PIN, AND WHAT TRAVELS IS A HASH — one request/result pair, minted here because `14-F40` cannot be built without it (August 2026, founder ruling R33).** `14-F40` specifies the surface and establishes that it cannot exist yet: `01-F62` makes `user.changed` **org-scoped**, so *"its only legitimate emitter is the cloud plane"* and a till has no legal envelope for it; commandment 5 forbids an operational screen calling `services/api`. The resolution is `05-F28`'s (c) with the planes reversed — **the till REQUESTS and the cloud RECORDS** — and that needs a kind. The message set is declared closed (`20 §2.7` pins it with golden fixtures), so this FR is what opens it.
  - **The pair is `credential_change_request` (device →) and `credential_change_result` (→ device), and it is deliberately NOT a reference-data frame.** `01-F75`'s triple is a **pull**: a device asks what version an artifact is at and is served rows. This is a **command with an outcome**, and folding it into `reference_request` would make one frame mean two things the moment a second command appears. Narrow names over a generic `command` pair for the same reason `01-F75` closed its resource set: a generic frame invites the next author to carry something nobody ruled on.
  - **⚠ WHAT TRAVELS IS THE NEW HASH, NEVER EITHER PIN — and the device verifies the old one ITSELF.** The alternative — send both PINs and let the cloud verify — is refused because it makes `11-F21` false: that FR says a PIN exists in exactly two places for exactly as long as each takes, *"the keypad it is typed on and the argument to a verify call"*, and `14 §2` says PINs are never present in payloads. So: the till verifies the old PIN against its **synced** hash (`01-F28`, which is the whole point of the roster carrying one), hashes the new PIN locally at `01-F61`'s parameters — **one declaration, `packages/domain`'s, because a device and a cloud that hash differently produce an offline refusal of a credential the owner has just set** — and sends the resulting hash. **The cloud does not re-verify the old PIN and cannot**: it never receives it.
  - **What makes that safe is what already makes every device-originated act safe, stated rather than assumed.** The frame rides an admitted device (`01-F47`) inside a session holding a `01-F26` PIN session, and `01-F27` keeps a device token carrying **device** identity only — so the person is the session's, not the frame's. **The request may only ever be about the requester herself** (`14-F40`), and the cloud enforces that by comparing the named user to the SESSION's user, never to a field the device chose. A frame naming anyone else is an auth failure and not a clamp (`01-F71` (e)).
  - **The result is one of a closed set, and one of them is not a failure.** `changed` · `wrong_old_pin` (the till's local verify is the first gate; this is the cloud refusing a request whose user does not match the session) · `not_permitted` · `unavailable`. ⚠ **`unavailable` exists because this act REQUIRES the WAN and that is correct rather than a `00 §5.1` breach** — `14-F40` argues it: the rule protects service, and a cashier who cannot change her PIN during an outage still signs in with her current one and sells. The till must say which of those four happened; *"it did not work"* is `00 §5.7`'s failure.
  - **The cloud's own act is `14-F14`'s PIN reset and nothing new.** It writes `11-F21`'s hash through the credential table's own writer (`11-F23`), emits `user.changed` with `act: "pin_reset"` — org-scoped, cloud-emitted, exactly as `01-F62` requires — and republishes the branch artifacts she reaches (`01-F78`). **The till learns the outcome from the result frame and its new hash from the ordinary roster path**; there is no second delivery mechanism, which is `01 §8`'s *"one replication path to test, not two"* holding.
  - **What this FR does NOT decide.** The permission action (`14-F40` records that it cannot be `user.manage`, because a cashier is `deny` there and widening it would let her change her own role — it needs its own FR-decided action or a self-scope arm on `02-F38`'s precedent, and doc 14 owns that). Rate limiting: `01-F61`'s lockout counts **unlock** attempts and nothing counts change attempts; a till that can ask unboundedly is a fact this FR states and does not resolve. And whether an owner's `14-F14` reset should evict a live PIN session on the tills that hold the old hash — `11-F22`'s R27 clause ends a session on deactivation and says nothing about a credential rotation.

ECDSA P-256 with SHA-256, the one algorithm `packages/lan-pki` already mints certificates under. **Every covered field is covered for a reason a reviewer can check**: the **version**, or `01-F56`'s monotonic apply is decoration — a relaying hub could relabel last week's roster as version N+1 and roll a branch back onto a device the owner revoked; the **key**, or a hub replays another branch's roster into this one; the **base**, or a delta is applied onto a state it was not computed from and the branch diverges with every version number still agreeing. **Verification happens at APPLY, over the assembled artifact, never per frame** — a snapshot applies atomically (`01-F56`), so a paged fetch verifies once its last page has landed, and a run that fails to assemble or fails to verify is `malformed`, which is `01-F74` (d)'s **unreadable** and therefore a refusal. **`signed_at` exists for `00 §5.7`'s age display and nothing else**: `01-F74` (d) admits an old roster, so no implementation may refuse on age, and it is never an input to any fold (`01-F34`, `01-F45`). ⚠ **The domain-separation prefix is a PINNED interpretation, contestable here rather than in an implementation** (`01-F76`'s precedent for pinning a wire shape in the only place it can be reviewed): the signed bytes are the ASCII string `restos.reference_artifact.v1\n` followed by that canonical JSON, so a roster signature can never be read as any other signature this platform makes, nor any other as a roster's.
  - **(c) THE SIGNING KEY IS NOT THE ISSUING KEY, AND THAT IS FORCED BY `01-F74` (c) RATHER THAN CHOSEN.** That clause states a security property outright — *"a compromised issuer still cannot admit a device the roster does not name"* — and the property is **false the moment one key does both jobs**, because a compromised issuer would mint the certificate *and* sign a roster naming its fingerprint. The obvious design (the `01-F73` (b) org issuer signs the roster, whose PEM every device already holds as the chain half of `01-F74` (c)) is therefore refused, and it is refused on a stated claim rather than on taste. So: an org carries a **roster-signing keypair distinct from its issuer**, and its public half is **pinned on the device at pairing** (`01-F80` (f)), beside the issuer PEM the device receives in the same response. **Pinned and not certified by the issuer**, since a chain from the issuer hands a compromised issuer the power to mint a fresh signing key — the same collapse one step further out. Per **org**, on `01-F73` (b)'s reasoning unchanged: a roster from one org must be *structurally* incapable of admitting a device from another. **Rotation is deliberately left open, with the cheapest shape named so nobody invents a worse one**: nothing needs it today (`01-F73` (e) makes a lost device key a re-pairing, and the issuer is long-lived), and when it is needed the old signing key signs the new one — an attacker holding the old key can already sign any roster, so that chain concedes nothing that was not already conceded.
  - **(d) `staff` IS STILL UNSIGNED, THIS FR DOES NOT SIGN IT, AND THE ENVELOPE IS PER-ARM SO NOBODY CAN FORGET TO.** The envelope is a **required** member of the `device_roster` arm and absent from the others, not an optional field on the shared response body: an optional protection is one an implementation can simply not supply — this corpus's most-repeated defect and precisely the shape `seams:check` Rule B exists for — while a required per-arm member makes an unsigned device roster **unrepresentable**, on `01-F75`'s own argument for typing `entries[]` per resource. `01-F75` (iii) already names the asymmetry this leaves: the roster of PEOPLE carries `11-F21` Argon2id credentials with no signature, defensible **only** while its single leg is the cloud's, authenticated end to end. **Extending this envelope to `staff` is therefore the precondition of the LAN reference-data leg** (`01-F75` (ii)'s standing `00 §5.1` breach, where a WAN-less device behind a relaying hub receives no artifact at all), and it is owed to **this doc** as its own amendment; until it lands, a hub relays no reference data of any kind, and an implementer who routes one through anyway has shipped the forgery `01-F74` (a) exists to prevent.
  - **(e) WHAT A THIRD MEMBER DOES TO THE REFUSAL THAT WAS DELETED — decided here, not inherited.** Step 6 deleted the unserved-resource refusal because a closed set of two, both served, made the case unrepresentable, and recorded in the code that *"what re-opens it is adding a THIRD member … a session-killing refusal is what it gets by default"*. **The decision: the negotiation is the answer, and the default stands.** `01-F77` already has `hello_ack.reference_versions` **omit** a key for an artifact a gateway does not serve, and the device asks only for what the session advertised — shipped behaviour on the catalog path, whose own comment reads *"an older gateway that serves no catalog"*. So a `device_roster`-capable device meeting a gateway without it **never asks**, which is the whole of the staged-rollout case, and a request for an unserved resource is then not an ordinary negotiation outcome but a client that ignored the advertisement: our own bug or a hostile peer, neither of which earns a designed degradation. **The requirement this rests on is stated so it is assertable rather than assumed: a device MUST NOT request an artifact key the session's `hello_ack` did not advertise**, for any resource. **The residual is named and bounded**: a session lost that way costs a reconnect and `hello_ack` reconciles every key on the next one (`01-F77`), so no sale and no event is at risk (`01-F2`, `01-F17`). ⚠ **AND A DEADLINE ELSEWHERE JUST BECAME CONCRETE, WHICH IS WORTH MORE THAN THIS CLAUSE:** adding a member is free today only because `01-F77` deferred its N−1 reader *"before the first pilot device is paired"* and R4 puts nothing in the field, so the whole system still moves in one step — and `01-F80` is the FR that makes pairing a thing that can happen. **The first claim served is therefore the moment `01-F77`'s deferred reader, its frozen fixtures and its per-session negotiation stop being deferred**, and neither FR can see that from where it sits.

It is stated at `01-F73` (b) and re-stated in (c) above, which are the two places a reader of the mechanism will look.

So it takes the same two carriers and invents no mechanism: **`config` joins `01-F75`'s closed set as its FOURTH member**, on the frame triple that already exists, adding **zero** message kinds, and inheriting `01-F71` (e)'s serve-path enforcement unchanged (the artifact key comes from the session and a stated one is refused rather than clamped) — which is why, on `01-F81` (f)'s precedent, no clause is added to `01-F71`'s register. **WHY A VERSION AND NOT A STREAM — a version number is a completeness claim and a stream of events is not.** Size is not the argument: measured against `00 §7` (f)'s eight environment keys plus `16-F2`'s posture matrix and R55/R60's two registries, the whole of layer 2 is a handful of scalars and two small tables, and either carrier would move that. What only the artifact gives is *knowing you hold all of it* — a device that missed one event holds a silently wrong rate forever, while a device that missed a version learns so on its next `hello_ack`, which `01-F77` calls *"the correctness mechanism of the whole reference-data transport"*, and `01-F56`'s monotonic apply is what stops two tills diverging undetectably. On `16-F27`'s owner-typed rate a silent miss is a legal exposure; on `05-F19`'s threshold it is an unapproved paid-out. **`form: "snapshot"` may well be the only form this resource ever answers, and that is legal rather than a gap** — `01-F75`'s rule is about the BASE (a delta is sent only where one is constructable from it) and never about the resource, and stating the rule instead of today's state is that clause's own corrected lesson. **ORG-SCOPED, WITH THE BRANCH AXIS AS DATA — `01-F60`'s ruling applied, not a new one.** `00 §7` names layer 2 *"Organization (back office)"* and `01-F62`'s emitter test already puts `config.changed` on the org side, so the artifact and the event agree rather than one having to be explained against the other: `01-F76`'s shape with **`branch_id: null`**. Layer-2 keys with a branch axis are ordinary and already shipping — station fulfilment routes (`03-F51`) and the enabled `(branch, channel)` set (`01-F60`) — and that axis is **DATA inside one org artifact**, on `01-F60`'s stated reasons unchanged: a branch-scoped artifact makes one version number mean different bytes on different devices, destroying the premise `01-F56`'s divergence detection rests on. **The roster's opposite answer does not transfer, and the reason is checkable rather than stylistic:** `01-F76` scopes `staff` to a branch *because that artifact carries an Argon2id hash and its scope is its blast radius* (`11-F21`), and measured against `00 §7`'s layer-2 list **no layer-2 key carries key material, a hash or a person's credential** — thresholds, rates, routes, signal owners, tier and enabled sets are all policy. The accepted cost is `01-F60`'s verbatim: a device can read another branch's routes, which is strictly smaller than the org-wide menu and price grid it already holds. ⚠ **That is a measurement of today's key set and a future key can break it**, so a layer-2 key that ever carries a secret is a re-scoping act **here** rather than an implementer's judgement. **THE POINT-IN-TIME READ `01-F85` REQUIRES IS A CAPTURE, NOT A QUERY — which is the third reason the event carrier fails.** The till resolves the value from the artifact it holds **at the moment of the act** and writes it into the event, exactly as `01-F53` freezes a price and `01-F60` resolves one; `01-F85`'s *"snapshotted at settlement and never re-read"* and `16-F29`'s *"the version applicable to an order is pinned at order creation"* are both that mechanism, and neither needs history at all. The alternative the event carrier forces — reconstructing *the rate at time T* by ordering an org stream on `server_received_at` — is legal on the cloud plane (`01-F18`) and unavailable to an offline till by `01-F62`. **And no `effective_at` field is added, deliberately:** `§9.5` (R31, `14-F36`) rules that application time belongs to the ACT and is staged above the publisher, so a change the owner schedules for 18:00 publishes at 18:00 and the `server_received_at` on its `config.changed` **is** its effective date; a second field would be a second answer to one question, which is `01-F81` (b)'s named defect. ⚠ **That is a READING of `16-F29` and is disputable by that id** — its words are *"a rate change is a `config.changed` event with an effective date"* — and a **past**-dated rate is unrepresentable here on purpose, since `01-F18`, `01-F53` and `01-F85` all forbid retro-pricing a settled order and `16-F29` itself says *"never rewrites a past order"*. If doc 16 means an authority's statutory date distinct from the moment of publication, that is an amendment owed **here**, because `01-F75` specifies no scheduling field and says so. **NO FOLD READS CONFIGURATION, FOR ANY KEY — the general rule `01-F85` stated for one.** `01-F85` bans a fold arm keyed on an owner-typed tender id and `01-F52` bans catalog state as a fold input; both are `01-F34`, and configuration is the same hazard with a wider surface, since a renamed tender, an edited rate or a moved threshold would otherwise change a projected value. **The sharp part is that `01-F34`'s existing property test cannot catch this.** That test is bijective envelope-id relabel plus clock injection over an equal delivered SET, and a configuration read is not an ordering read at all: it makes a projection a function of `(delivered set, artifact version)`, so both harness devices hold the same configuration, relabel invariance holds, and two real tills at different versions still project different money. **Enforcement is therefore structural — what a fold is allowed to take as input — and not a property test**; where a fold needs a configured value it is put into the event at the act, which is `26 §7`'s carried key and `01-F86`'s own answer for a split's channel. **What is NOT a fold, stated because this is where the line will be argued:** a rendering computed at display time reads configuration freely — `03-F14`/`03-F47`'s aging thresholds are the shipped example, and measured they are read by `ageLevel` at `packages/ui/src/components/AgeBadge.tsx:41` at render time, over an age basis the materialized row (`01-F6`) already carries. ⚠ **The break is one keystroke away and is named rather than left to be discovered: memoizing such a rendering into a materialized state table**, at which point the value stops being recomputed per frame and becomes a projected one.
  - **(a) `config.changed`'s PAYLOAD — and both of its open ends are refusals rather than laxity.** Measured 2026-08-23, `packages/domain/src/registry.ts` declares **34** payload schemas (`payloadSchemas`, :204) plus seven `audit.*`, and `config.changed` is not among them — `28-F14`'s own measurement and `01-F84`'s finding one type over: under `01-F4` the emit throws, so `16-F1`'s *"enabling any posture … recorded as `config.changed`"* and `16-F29`'s rate change are **unauditable rather than unbuilt**. The payload, modelled on `catalog.changed`, its nearest sibling in both `§4`'s admin family and the registry: **`key`**, required, the setting that changed; **`layer`**, required; **`version`**, required positive integer — the `01-F76` artifact version this change produced, so the ledger record and the published artifact are joinable, not because a device reads the event (`01-F62` forbids that) but because `14-F3`'s history and `20 §4.2`'s refold must be able to say which version carried a change; and **`before` / `after`**, each the key's value **or `null`**, where `null` means *the key was on its default* — so a first configuration (`null → v`) and a reset (`v → null`) are both statable, which (b) requires. **The key space is OPEN, and that is commandment 2 rather than laxity.** No FR supplies a closed list: `00 §7` says *"every module doc's Customizability section lists exactly which settings it exposes at which layer"*, so the key space is the union over every module doc and grows with each one. `01-F84`'s precedent is exact — `order.rejected`'s `reason` is closed **because `06-F20` supplies the list**, and `order.cancelled`'s is open because nothing does. A closed enum here would additionally make every future module's first setting an `01-F4` runtime error until this doc is amended, which is the absorption debt `§4` records fourteen instances of. The check moves to the **WRITER**, which is `01-F60`'s move for prices and `01-F85`'s for tenders and for their reason: a typo caught once at a failed save instead of frozen forever under `01-F1`. **The value is loose in the schema and typed BY THE KEY at the writer** — the same two-level split `catalog.changed`'s own `price_changes` already makes (*"optional HERE and required at the WRITER"*) — and commandment 1 requires it, since a closed value union is a closed key space wearing a type and re-typing it later would retroactively refuse the history this schema exists to read. **`00 §6` is not weakened by that, and this clause says so:** a money-valued key is integer paisa and a rate-valued key is integer basis points, declared in the key's own schema and refused at the writer — `05-F19`'s threshold and R60's per-provider commission are the two live instances. **`layer` is a CLOSED enum and its numerals are the corpus's own** — `00 §7` numbers its three layers 1/2/3, so an integer is transcription where a name (`org`, `branch_device`) would be invention, and `01-F76`'s precedent for pinning a wire shape in the only place it can be reviewed applies. It is required because this type already spans layers: `15-F25` routes an org's `active ⇄ suspended` through it, which is layer 1, while R55/R60/R63 are layer 2 — and a reader that cannot tell them apart can neither render `14-F3`'s history nor scope an isolation check. **No actor field.** The envelope's `actor_user_id` is the one home for who acted (`01-F84`, `02-F45`), and a registry row is not where an authorization is decided (commandment 8, `18 §5`).
  - **(b) THE DEFAULT LIVES IN THE BUILD, THE SOURCE TRAVELS WITH THE VALUE, AND AN UNKNOWN KEY IS IGNORED WHILE A MALFORMED ONE REFUSES.** `00 §7` (d) requires every layer-2 key to declare a default that is safe to be wrong about; the kernel half is what a device does when nothing has ever arrived. **A device that has never received the artifact uses the declared default and never blocks** — `01-F17` and `00 §5.1`, since the alternative is a till that cannot act until the WAN has been up once, which is the breach (d) exists to prevent. **The default is DECLARED IN THE BUILD and never delivered, and that is forced rather than chosen:** a delivered default is a configured value that has not arrived yet, and the case being specified is precisely the device that has had no contact. Two consequences are stated rather than left to be discovered — **changing a declared default is a spec act** in the doc that owns the key, never an implementation edit; and **two devices on different builds can hold different defaults for a key no org has configured**, a real divergence `01-F56` cannot see because no version is involved. It is tolerable only because (d) makes a default safe to be wrong about and because the next sentence makes it visible, and a key for which that is untrue fails `00 §7` (b)'s admission test rather than earning an exception here. **`00 §7` (e)'s resolved source is `configured | default`, per key, and it travels with the value.** This is a shipped pattern rather than an invention: `apps/pos-electron/src/main/hardware-tier.ts` resolves `derived | configured | assumed` and `packages/device-config/src/panel-density.ts` resolves `measured | configured | assumed`, both printing the source at boot on the argument that a wrong value looks exactly like a right one from the screen. The kernel minimum is that the device's health surface (`01-F11`, `00 §5.7`) **names every key still on its default**, so an operator can tell *the owner set this* from *the owner never has* — a sharper case than staleness, because a value that never arrived has no age to show. **An UNKNOWN key is ignored; a MALFORMED known key refuses the whole artifact.** The split is `01-F81` (a)'s forward-skew rule set beside `01-F75`'s writer-validation rule, and it is not arbitrary: an unknown key means the CLOUD is newer, so refusing punishes a device for the cloud's progress and produces the stopped-till-through-a-validator `01-F75` names, while a malformed value means the WRITER emitted bad data, which is a defect and must be loud (`01-F56` `malformed`, observable in device health). A refused artifact leaves every key at the version the device already holds, or on its default, which is what makes that degradation survivable at all; the writer is where it is prevented (`01-F60`, `01-F85`). `01-F76`'s `foreign_artifact` applies unchanged, and for an org-scoped artifact it is the org axis that can produce it.
  - **WHAT THIS DOES NOT CLOSE.** **The permission action gating the write is doc 14's**, as `00 §7` (f) already owes it there: the matrix carries no configuration action and `services/api` refuses at boot to host an ungated procedure, so the back-office write cannot be booted until doc 14 lands one. ⚠ R63's words are *"the owner or ops lead"* and `ROLES` has no ops lead; that is not decided here and is not decided by this FR existing. **`05-F19`'s threshold DEFAULT is doc 05's** — `00 §7` (d) argues an approval threshold's default toward the strict end, while `PAID_OUT_APPROVAL_THRESHOLD_PAISA = 200_000` at `apps/pos-electron/src/main/authorize.ts:161` is merely today's pinned value, and inheriting it here would be exactly the un-chosen default (d) refuses. This FR requires that **a** default exist and never says which. **Each key's declared schema — type, unit, bounds, refusals — belongs to the doc that owns the key**, per `00 §7`'s vendor-designs-the-schema rule: `16-F27`'s posture and rate, R60's per-provider commission, `03-F51`'s routes, `03-F14`/`03-F47`'s thresholds, `03-F52`'s signal owners, `01-F60`'s enabled set. This FR carries them and declares none of them; a key string an implementation invents is a `01-F4`-shaped error one layer down. **The unattributed emitters stay blocked, and removing the `01-F4` blocker does not unblock them:** `15-F27`, `28-F14` and `14-F30` each refuse to write a permanently-`null` `actor_user_id` into an append-only store (`01-F1`), so `15-F4`'s *"provisioning emits the org's first `config.changed`"* remains owed to a surface with an authenticated user rather than to this schema. **Layer 3 is untouched and layer 1 is not decided.** `00 §7` (f)'s environment ban covers layers 1 and 2, so `01-F65`'s device identity and every layer-3 key legitimately remain device configuration; whether any layer-1 fact (`15-F25`'s suspension, entitlement) ever needs this transport is doc 15's and doc 28's, and the `layer` field lets the ledger state one while this artifact does not carry it. **The LAN leg stays shut for this resource exactly as for the others** (`01-F75` (ii)): a WAN-less device behind a relaying hub receives no artifact of any kind, and `01-F81` (d)'s signature question is not re-opened — `config` carries no credential, so it needs no envelope today, and if that leg opens the question is asked then. **None of the eight environment stopgaps is retired by this FR**; `00 §7` (f) makes each a named stopgap and retiring one is a per-key migration in its owning app, which this transport makes possible rather than performs. **And the writer's act is not specified beyond `01-F75`'s named-producer clause** — one write mints the version, fans out the `reference_notice` and emits the `config.changed` — because *when* publication happens relative to the write is `§9.5`'s and `14-F36`'s, unchanged here.

## 5. Data

- **Device SQLite:** `events` (own + branch stream, rolling window), `event_outbox` (unacked own events), materialized state tables per host app, `reference_data` (catalog/users snapshot + version — **one snapshot and one version per `01-F76` artifact key**, since a version number is meaningless without the `(resource, scope)` it counts), and this device's own LAN credential with the trust anchors pairing pinned on it (`01-F73`, `01-F81` (c) — inside the store because `01-F64` already binds it to this identity).
- **Cloud Postgres:** `events` partitioned by org + month (retained forever); `device_registry`, `orgs/branches/users/roles`; **pending device pairings** (`01-F80` — the Argon2id hash of the code, never the code, plus the identity the owner fixed at mint and the claimed key's fingerprint); per-org LAN issuing and roster-signing key material (`01-F73` (b), `01-F81` (c) — cloud plane only); per-module read models (owned by their modules, rebuildable).
- **Compaction:** devices prune the branch stream beyond the rolling window but always retain events referenced by open entities (unsettled orders, open shifts).

## 6. Non-functional requirements (module-specific)

- 01-N1 Replay determinism: folding the same event set in any received order (respecting per-device lamport order) yields identical state — property-tested (00 §4).
- 01-N2 Clock skew: device clocks are untrusted; skew > 5 min against server time raises a device health flag (doc 15) but never blocks operation. **Un-deferred into Wave 0 with DEC-TIME-001** — this is the *detection* half of the time layer, and a time layer that silently absorbs arbitrary skew (01-F43) without reporting it is undiagnosable in the field. Skew is measured against **hub time** (01-F43) — the leg Wave 0 implements, since the hub offset is the only server-anchored clock the device actually holds. A direct device↔cloud skew measurement is **explicitly deferred**: nothing in the protocol carries a server clock at hello time (`server_received_at` arrives asynchronously at merge), so it needs a protocol field and is out of Wave-0 scope rather than silently unimplemented. The flag is observational only and never blocks (01-F17). Reading the raw `device_created_at`/device clock here is the named 01-F45 exemption.
- 01-N3 Storage budget: kernel footprint on a 2GB-RAM tablet ≤ 500 MB at the default rolling window under rush-simulation load.
- 01-N4 Cloud ingestion: sustain 50 orders/min × 200 branches on baseline infrastructure without backlog growth.
- 01-N5 A cold-started replacement device is operational (registered, reference data + branch window synced) < 10 min on 4G.

## 7. Customizability

- Layer 1 (platform admin): org/branch/device provisioning, revocation, rolling-window default.
- Layer 2 (org): roles/permissions within the matrix, approval thresholds, branch topology.
- Layer 3 (device): none beyond registration identity and station class.
- **Not configurable, ever:** append-only behavior, conflict rules, envelope schema, audit hash-chaining. These are platform law.

## 8. Tech notes

- Sync protocol: custom, over WebSocket (cloud) and LAN sockets; protobuf-free — JSON + zstd batch compression is sufficient at this event volume and keeps debugging trivial.
- **Build-vs-buy (DECIDED — full analysis in `19-sync-engine-decision.md`):** custom engine. Research (July 2026) confirmed no mainstream engine (PowerSync, Electric, Zero, Turso, LiveStore) provides LAN device↔device sync with WAN down; the only product that does (Ditto) is an opaque proprietary CRDT store conflicting with our auditability and self-host requirements. Our hub-relay topology matches Toast's documented production pattern. Exit ramp: Ditto evaluation if the Wave 0 spike fails twice (19 §6).
- Wave 0 spike exit criteria: 3 devices (Electron + 2 RN) + virtual printer; scripted rush replay with WAN cut mid-run; plug-pull mid-print; partition + rejoin with zero lost/duplicated events and identical folded state; LAN p95 < 1 s on shop-grade Wi-Fi.
- Hub election runs inside `packages/sync-client`; host apps only expose "I can be hub" capability class.
- ~~Reference-data distribution reuses the event channel (config/catalog versions as events) — one replication path to test, not two.~~ **Amended August 2026 — `01-F75` describes what is actually built and what is now required.** This note was never true of the shipped catalog and was drifting further with every reference-data set added: an artifact does not travel as an event at all (`01-F52` — `catalog.changed` announces that a version exists and does not carry the catalog; `01-F62` keeps org-scoped events out of every branch stream and out of every fold), so the catalog has had its own frame triple since it was built. Reference data rides the **same connection and the same session** as the ledger stream, on its own frames. *"One replication path to test, not two"* survives as the requirement it was written for, and `01-F75` is what now makes it true: **one frame triple for every resource**, discriminated by `resource` and scoped by `01-F76`, rather than one triple per resource — which is the count this note was worried about, arrived at from the other direction.

6. ~~**What a till does with a staff roster it cannot fetch, or one that is old — BOTH HALVES**~~ **RULED (founder, August 2026, R28): AN OLD ROSTER ADMITS, WITH ITS AGE SURFACED; A NEVER-RECEIVED ROSTER REFUSES, LOUDLY, AT BOOT.** That is `01-F74` (d)'s ruling for the *device* roster — *stale is not unreadable* — applied to people, and the two halves are decided by opposite reasoning rather than by symmetry. **Admitting on an old roster** is what `00 §5.1` requires: refusing because the WAN is down is precisely the breach `01-F74` (d) exists to prevent, and `01-F17` forbids the stopped till it would produce. **Refusing on a never-received roster is not the mirror of that, it is the other case entirely:** a device that has never received a roster has *nobody* who can sign in, which is already a stopped till, and `00 §5.7` requires that to be **loud at boot** rather than discovered at 07:00 by a cashier who cannot open the day. **No staleness bound is set, and setting one is refused rather than deferred** — any bound eventually stops a disconnected branch selling, which is the failure `00 §5.1` names. The cases this covers, kept because they are what an implementation must handle: a till whose roster is a week old **admits**, and a departed cashier therefore keeps selling until the roster reaches it — accepted, and it is why R27 makes a removal immediate rather than deferred. A till that has **no roster for its key at all** — never fetched one, or refused every one it was sent (`01-F76` `foreign_artifact`, which a mis-set `branch_id` produces forever) — **refuses, and says so at boot.** ⚠ `11-F22` still decides only what a PRESENT row's status means and says nothing about an absent artifact; that separation is why this question is answered here and not there.
