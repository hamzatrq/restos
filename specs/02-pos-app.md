# 02 — POS / Counter App

**Module spec — Draft 1, July 2026** · Parent: `00-platform-overview.md` (conventions §5–§7 inherited), `01-kernel-sync.md` (events, sync, auth). Seed detail: `restaurant-os.md` Appendix B. Wave 1.

## 1. Purpose & scope

The POS is the billing and order-capture surface of the branch: order entry for every service mode, payments and receipts, staff attribution, shifts and cash, phone/call-center order entry, and manual foodpanda quick entry. Used by cashiers, branch managers, counter staff, and call-center operators.

Two builds from shared `packages/domain` + `packages/sync-client` + `packages/escpos`:

- **Windows counter:** Electron + React. The Electron counter is the preferred branch hub (01-F13) and hosts the print service (doc 03).
- **Android:** React Native (Expo), for tablet-counter and secondary-terminal setups.

All tiers run it. In **T1 the POS is the entire restaurant** — one device, printers attached, statuses auto-advancing (02-F31). In T2/T3 it is the counter node of the branch mesh. Catalog and configuration are never edited here (doc 14 owns that); the POS is an operating surface.

## 2. Position in platform

- **Depends on:** kernel (doc 01) for ledger, sync, catalog snapshots, customer file, PIN auth; print service (doc 03, co-resident on the counter device) for KOT/receipt/drawer output.
- **References:** doc 05 (remote approval interrupts; day/cash ownership boundary), docs 06/07 (storefront/WhatsApp orders arriving in the queue), doc 08 (foodpanda item mapping for quick entry), doc 09 (rider dispatch surface at the counter — owned there, rendered alongside POS), doc 14 (catalog/config editing), doc 16 (fiscal receipt fields when the tax module is active).
- **Events emitted:** `order.*`, `payment.*`, `void/comp/discount.recorded`, `availability.changed`, `shift.*`, `day.*`, `cash.*`, `customer.created / address_added`, `receipt.*` (extension, §5), `audit.*`.
- **Events consumed:** branch order stream (all channels), `availability.changed`, `order.line_state_changed`, `approval.granted / denied` (doc 05), `kot.print_failed`, reference-data versions.

## 3. Functional requirements

**Order capture**
- 02-F1 Order types and channels:
  - types: dine-in (table), takeaway, delivery (own);
  - channel tags: counter, phone, storefront, WhatsApp, foodpanda;
  - every order carries `order_type` + `channel` from creation (`order.created` / `order.channel_tagged`); neither is ever inferred later.
- 02-F2 Menu grid: category tabs, item search, big touch targets (≥ 48 dp), optional item photos, English labels (00 §5.6). A simple order is ≤ 2 taps from grid to confirm.
- 02-F3 Modifiers/variants: size, add-ons, spice level. Price is snapshotted on the line at add (01-F18); each variant may carry its own recipe (deduction, doc 10 — invisible here).
- 02-F4 Park/resume open orders: `order.parked` / `order.unparked`. A parked order is durable (00 §5.2) and visible to every terminal in the branch.
- 02-F5 Split a bill by item or equal split (`order.split`, child orders referencing the parent); merge tables (`order.merged`); move table (a new `order.table_assigned`). Nothing is deleted in any of these — pure event composition.
- 02-F6 Item notes to kitchen: free text + org-configurable quick-tags ("less spicy") → `order.note_added`, printed prominently on the KOT (doc 03).
- 02-F7 Availability toggle ("karahi finished") from any POS screen → `availability.changed`, fast-path to all devices and channel drivers (01-F22); toggled-off items grey out on the grid within the LAN budget (01-F15).
- 02-F8 Confirm boundary: confirming an order emits `order.confirmed` and hands KOT jobs to the print service (doc 03). Line removal pre-confirm is `order.line_removed`; post-confirm it must be `void.recorded` with an approver (01 §4).
- 02-F9 **Cloud-order inbox (the accept/reject surface for 06-F17a).** Incoming cloud orders (docs 06/07) land in a POS inbox pane, channel-tagged, with an S2 chime (21 interrupt law): one-tap **Accept** → `order.confirmed` (idempotent — at most one confirm per order id; KOT jobs created exactly once, after confirm, never before); **Reject** with a reason from the 06-F20 list → `order.rejected`. When org auto-accept is on, the inbox shows a visible countdown, cancellable with one tap. Items gone unavailable since placement must be resolved before accept: remove the line (customer notified via the channel doc) or reject the order — this explicit line-removal path is the only partial-confirmation mechanism. Aggregator API orders bypass the inbox (accepted upstream, auto-confirmed on ingest per 08-F8) and appear directly in the queue. An unaccepted order past half its confirmation window escalates to S1 per the interrupt law.
- 02-F10 Order queue and recall: open orders searchable by order number, table, or customer phone; settled orders of the current day recallable read-only (receipt reprint per 02-F16). Aging colors follow doc 03 thresholds.
- 02-F11 Multi-terminal coherence: an order started on one terminal can be parked there and resumed, extended, or settled on another; concurrent line-adds from two terminals merge (01-F16).

**Payments & receipts**
- 02-F12 Payment methods (`payment.recorded`), amounts in integer paisas (00 §6):
  - cash (change due computed and displayed);
  - card (manual record at launch, §9);
  - bank transfer / RAAST;
  - khata credit (02-F14).
- 02-F13 Split payment across methods in one settlement (`payment.split_recorded`) — e.g. part cash, part RAAST.
- 02-F14 Khata requires a linked customer (name + phone → customer file, 01-F23); the unpaid balance is a receivable visible per customer on the POS; later repayment is a `payment.recorded` referencing the original order(s).
- 02-F15 Receipt printing 58/80 mm via doc 03: configurable header/footer/logo, optional QR (menu link, or FBR invoice QR when doc 16 is active). Receipt content:
  - order number, channel, date/time, cashier;
  - lines with variants/modifiers, discount lines, totals;
  - payment method(s) and change;
  - fiscal fields when doc 16 is on.
- 02-F16 Success emits `receipt.printed`; reprint is always logged with actor (`receipt.reprint_requested`) — reprints are a classic fraud vector and feed doc 12/13 anomaly alerts.
- 02-F17 Channel + payment method are captured on every settled order — feeds channel economics (docs 12/13) and tax posture (doc 16).

**Staff attribution & controls**
- 02-F18 Per-user PIN login on every device (01-F26); idle auto-lock (device-layer timeout). No anonymous mode exists; a locked device shows only the unlock screen.
- 02-F19 Every action is attributed in the event envelope: order created, line added/removed, discount, void, comp, reprint, drawer open, settlement, availability toggle.
- 02-F20 Manager escalation required for: void after KOT, comp, discount above org threshold, price override (`order.line_price_overridden`, extension §5). Two equivalent authorization paths:
  - local manager PIN on the POS;
  - remote approval via manager console (doc 05, `approval.requested/granted`).
  First response wins; the recorded event carries actor + approver either way.
- 02-F21 No-sale drawer opens: `cash.drawer_opened` with `reason=no_sale`, logged and counted (classic theft vector); surfaced in doc 12 alerts.

**Shifts & cash**
- 02-F22 Day open: opening float entry → `day.opened`. Shift open per cashier → `shift.opened`. A shift binds subsequent cash settlements and drawer events to that cashier. **Role guard:** day open/close and float entry require manager/owner permission (`restaurant-os.md` Appendix A) — a cashier session cannot execute them; where no manager device exists, the local manager-PIN path satisfies the guard.
- 02-F23 Shift close per cashier (`shift.closed`):
  - system-expected cash (by method) vs counted cash; over/short recorded and attributed;
  - the cashier sees their own reconciliation on-screen at close ("I'm clean") — the staff-protection framing;
  - cashiers see only their own shifts (`restaurant-os.md` Appendix A); cross-cashier views belong to manager/owner surfaces (docs 05/12).
- 02-F24 Day close: manager cash count + deposit record → `day.closed`, `cash.deposit_recorded`; a day-summary ticket (sales by channel, voids/comps/discounts, over/short) can be printed via doc 03. Day close triggers the owner nightly summary (doc 12).
- 02-F25 Manager-attributed day/cash flows are also executable from the manager console — the ownership boundary is defined in doc 05 §3; the POS retains the full fallback so a branch without a manager phone loses nothing.
- 02-F26 Paid-outs/petty cash: reason + receipt photo (object storage ref) → `cash.paid_out`; approval above threshold per doc 05.

**Phone / call-center entry**
- 02-F27 Incoming call flow:
  - operator types the caller's number (caller-ID integration is an open question §9);
  - customer file lookup by normalized phone → name, saved addresses, order history, "repeat last order" shortcut;
  - unknown number → inline customer creation (`customer.created`, `customer.address_added`).
- 02-F28 Target: a repeat customer's order entered and confirmed in ≤ 30 s from number entry (tested with a rehearsed operator on reference hardware).
- 02-F29 (Multi-branch profile only, Wave 4) Call-center mode routes the order to the nearest branch by address zone (zone→branch mapping maintained in doc 14); the order lands in that branch's queue as channel `phone` and prints there. If the target branch is unreachable, the operator is told immediately and may pick another branch — never a silent drop.

**Foodpanda manual quick entry**
- 02-F30 Dedicated quick-entry mode: channel pre-tagged `foodpanda`, item picker restricted to the mapped menu (mapping owned by doc 08), no settlement step (aggregator-collected; economics handled by doc 08). Target ≤ 30 s per order. Quick-entry orders behave identically downstream: KOT print, inventory deduction, channel reporting.

**T1 mode & sync honesty**
- 02-F31 T1 mode — the entire restaurant runs on this one device:
  - detection: the branch device registry contains no pass/KDS/waiter device;
  - the POS shows a compact order-queue panel with aging timers (doc 03 thresholds);
  - line statuses auto-advance where no device exists to signal them: `kot.printed` → lines `in_prep`; settlement → lines `served` — **dine-in/takeaway/pickup only**. Delivery lines are NEVER advanced by settlement (COD settles at the door or on rider return): they advance only via `rider.picked_up / delivered` or the counter's on-behalf dispatch entries (09) — canonical rule in 01 §4;
  - no `ready` state is fabricated — the timing pipeline honestly receives no ready samples in T1 (03-F26), and T1 restaurants therefore never get learned ETAs (aging timers only).
- 02-F33 Ready-marking on POS (T2/T3): when the org's ready-signal ownership (03-F24) is assigned to **counter**, the POS queue panel exposes per-order ready marking (marks all remaining lines ready, one tap); otherwise the panel is read-only for states.
- 02-F32 Sync honesty on-device (00 §5.7): a persistent, non-blocking indicator shows outbox depth and last cloud ack (01-F11). Local operation is never gated on it.

**Delivery dispatch surface (Wave 2 — logic owned by doc 09, hosted here and on doc 05)**
- 02-F34 Dispatch panel: delivery orders with all lines ready listed oldest-first; assign or batch-assign to a rider (staff registry), or record on-behalf status entries for app-less riders (09); COD due shown per order; rider rows show last-event age so stale state is visible, never assumed fresh (09-F13).
- 02-F35 Rider COD settlement runs here per doc 09 (expected vs returned, over/short attributed, manager-PIN above threshold); failed deliveries surface for resolution (return to pool, or void via the normal approval path) per 09-F18.

**Refunds & post-settlement corrections (01 money contract, Wave 1)**
- 02-F36 From any recallable settled order (02-F10): full or partial refund (by line or amount) → `payment.refunded` per 01-F29 — manager approval always (remote interrupt or local PIN), method cash-out / RAAST-reversal reference / khata credit, linked `void.recorded`/`comp.recorded` when food is returned or remade, `settlement_attempt_id` idempotency (01-F31). When the tax add-on is active, the refund triggers the linked fiscal credit note automatically (16-F12). The refund prints a refund slip (doc 03) and lands in doc 12 exception reporting.

**Gaps closed from the Wave-1 role inventories (July 2026)**

- 02-F37 **Settling with no shift open succeeds, and records that it did (gap G4).** `02-F22` binds settlements to a shift but never said what happens when none is open, and `01-F17` forbids blocking the sale — so the only legal behaviours are "succeed" or "succeed and lie". The settlement is recorded with a **null shift reference plus an `unbound_settlement` anomaly**, which surfaces on the manager's reconciliation (`05`) and on the cashier's own day view (`02-F23`). Never a modal, never a block: a customer is standing there, and a rule that stops a sale to protect a report has its priorities inverted. Opening a shift later does **not** retro-bind it — that would be a mutation (`01-F1`); the anomaly is resolved by an explicit linked correction.
- 02-F38 **A requester never sees an approve control for their own request (gap G16).** Implied by `02-F20` and `05-F6` but never stated, which made it unenforceable as an anti-scope test. The control is **absent from the requester's screen** *and* refused server-side by the `domain` permission matrix (Commandment 8 — a client that renders it anyway must still fail). Stated so it can be tested rather than assumed.
- 02-F39 **Quick-tags are capped at one page at the target posture (gap G10).** `02-F6` and `04 §7` made kitchen quick-tags org-configurable with no bound, while `27-F2` forbids scrolling to reach a primary action and `27-F6` forbids requiring typing — so an org configuring 40 tags breaks both laws at once and the cashier is left with no legal path. The cap is **not a fixed number** (that would repeat the `27-F2` category error): back office computes the page capacity for the target surface and refuses to save beyond it, showing the count against the limit. An org needing more tags needs fewer, better tags.

- 02-F40 **In a printer-only kitchen, 86-ing is a counter action and the chef must say so out loud — a stated tier consequence, not a defect (gap G14, founder ruling July 2026).** `02-F7` puts the toggle on the POS and `03-F16` on the pass screen; a T1/T2 kitchen (`27-F11e` — most deployments) has neither, so stopping the platform selling a finished dish means the chef tells the counter. **No new mechanism is added**: not a kitchen device (hardware in the worst environment in the building for a handful of taps a day), not a WhatsApp path (`00 §5.1` — no in-branch feature may require WAN). The residual risk is real and named: the walk happens during the exact rush where an oversell is most likely, and `02-F31`'s oversell handling is what absorbs it.

- 02-F41 **Attribution is whoever's PIN is in, with no "acting for" concept (gap G12, founder ruling July 2026).** `27-F51` makes second-order usability a design requirement — a shift lead driving the terminal for a junior who is stuck — and no FR owned it. **Ruled: no mechanism.** The supervisor's PIN means the supervisor is accountable, which is true anyway the moment they choose to take over, and modelling dual identity would add a concept to the permission matrix that must be got right under exactly the time pressure that caused the takeover. `27-F51` still binds the *design* — a screen must be operable by someone standing beside its owner — but not the *ledger*.

- 02-F43 **Drawer events with no shift open succeed, are COUNTED, and carry the same anomaly treatment as settlements (August 2026).** `02-F22` binds "subsequent cash settlements **and drawer events**" to a shift, and `02-F37` then resolved only the *settlement* half. The drawer half was left open, and the omission is not cosmetic: a drawer legitimately opens before the first shift of the day (making change, a supplier at the door), `01-F17` forbids blocking, and `02-F21` requires a no-sale open to be **"logged and counted"** — so an implementation that logs the event and then drops it from every total satisfies the word *logged* while defeating the theft-detection the FR exists for. `cash.drawer_opened` and `cash.paid_out` therefore carry a **nullable `shift_id`** on exactly `02-F37`'s terms: the event is accepted, recorded against a **null shift reference**, counted into an **unbound bucket**, and raises `unbound_drawer_open` / `unbound_paid_out` — surfaced on the manager's reconciliation (`05`) and the cashier's own day view (`02-F23`). Never a modal, never a block. As with `02-F37`, opening a shift later does **not** retro-bind it (`01-F1`); the anomaly is resolved by an explicit linked correction. **What this forbids is the silent path**: an unbound no-sale that is stored and uncounted, or unbound petty cash that leaves the drawer accounted for in no shift, no day, and no anomaly — money vanishing from `02-F23`'s expected cash and `02-F24`'s day close with nothing to point at.
- 02-F44 **`cash.paid_out` carries `amount_paisa` (integer paisa, non-negative) (August 2026).** `02-F26` named "reason + receipt photo" and no amount, which makes `02-F23`'s *"system-expected cash (by method)"* uncomputable the moment any cash leaves the drawer as a paid-out: the drawer is short by an amount the ledger never recorded, and the variance is unattributable in an append-only log where `01-F1` allows no correction in place. The direction is carried by the event type, not by a sign — a negative `amount_paisa` is an `01-F4` error at emit.
- 02-F45 **Shift attribution is read from the envelope, never from a payload field (August 2026).** `02-F41` rules that attribution is whoever's PIN is in, and `01-F27` puts user identity in the PIN session, which the envelope carries as `actor_user_id`. A `cashier` field duplicated into the `shift.opened` payload would be a **second source for one fact**, and the two can disagree — in an append-only ledger, with no rule for which wins. `packages/sync-client/FOLDS.md`'s `cashier` column is therefore a **projected** column sourced from the envelope's `actor_user_id` field, not a declared payload field. **CONFORMED (August 2026).** `packages/sync-client/src/folds/shift-cash.ts` reads `actor_user_id`, and the oracle's stale PIN #2 (*"no FR says which one the fold reads"*) is retired rather than annotated — it predated this FR and was superseded by it, which is the `01-F60` shape: a green test defending a rule that had already been overruled. A `shift.opened` member is now its payload PLUS the envelope's actor, so two devices claiming one `shift_id` under two different PINs are two contested heads under `01-F31` (nothing picked, `cashier` null, both retained, `shift_open_divergence` raised) — a disagreement the payload cannot express, because the two payloads are byte-identical. The envelope's field overwrites any same-named payload key by construction, so a `cashier` from a non-conforming writer is never read. A `day.opened` member stays the payload alone: the day row projects no attribution, and folding the actor in would zero the branch's opening float over a disagreement about which manager opened the day, which no FR asks for. `26 §7`'s fork detector was re-checked and still reads the **carried** `prev_shift_id`, not the actor — kill count unchanged at 3 either side of the change. Reading `actor_user_id` does not breach `01-F34`: it is a **delivered** field of the event, stamped once at the origin's append (`01-F43`) exactly as `payload` is, never derived from the reading device's state. **Still owed:** the doc comments in `apps/pos-electron` (`CLAUDE.md`, `main/authorize.ts`, `main/gateway.ts`, `main/__acceptance__/report-scope.test.ts`, `renderer/me-tab.dom.test.tsx`, `renderer/cash-tab.dom.test.tsx`) that describe the fold as reading the payload's own `cashier` field are now stale, and `02-F23`'s own-shifts scoping — which those comments say narrows nothing — now narrows for real whenever a PIN session is in.
- 02-F42 **`channel` is a CLOSED set and it is a price key.** The channel tags `02-F1` already names — **`counter`, `phone`, `storefront`, `whatsapp`, `foodpanda`** — are the whole set; `order.created.channel` accepts nothing else and an unknown value is an `01-F4` error at emit. **`channel` and `order_type` are different axes and neither substitutes for the other**: `dine_in`, `takeaway` and `delivery` are order *types* (`02-F1`), and a channel value drawn from that vocabulary is invalid.
  - **Why it must be closed now.** A channel selects the price (`01-F60`), so a typo is not a mislabelled report row — it is a **wrong price**, snapshotted into the line by `01-F53` and frozen in an append-only ledger where it cannot be corrected in place. This is the argument that closed `payment.recorded.method` (`02-F12`, `01-F32`): an open string fails nowhere and quietly becomes a category no report counts. With money attached, it fails as silent mispricing instead.
  - **The order's channel is the resolution key**, set at creation and never inferred later (`02-F1`). So a foodpanda order keyed in at the counter (`C21`, `02-F30`) bills at foodpanda prices — which is the entire point of pricing per channel, and would be lost if the price resolved from the *device* rather than the *order*.

- 02-F46 **The availability toggle is its own permission action, and a CASHIER holds it (August 2026).** `02-F7` puts the 86 on the POS and `02-F19` names "availability toggle" an attributed action, but `restaurant-os.md` Appendix A has **no availability row**, so Commandment 8's matrix had nothing to refuse against and the fail-closed default (`WRITE_ACTIONS`, `apps/pos-electron/src/main/authorize.ts`) denied every toggle. The feature could not exist without this row. The action is **`availability.toggle`**.
  - **It lives in doc 02 rather than in Appendix A**, on `14-F30`'s precedent: an FR-decided action does not extend the seed appendix, and several shipped actions already have no appendix row. Appendix A is a seed, not a closed vocabulary.
  - **The verdicts are `order.create`'s row — cashier ✔, branch manager ✔, storekeeper —, owner ✔ — and the cashier cell is the load-bearing one.** `02-F40` rules that in a printer-only kitchen *"86-ing is a counter action and the chef must say so out loud"*, and `27-F11e` makes that most deployments. A cashier-denied toggle would mean that on a T1 branch with no manager present **nothing can 86 an item at all** — the platform would go on selling a dish the kitchen has run out of, for the rest of the shift. That is the same argument `01-F61` makes when it refuses a lockout with no automatic end: a control whose only holder may not be in the building is a control that does not exist. The storekeeper cell is `—` for `order.create`'s reason: Appendix A's storekeeper column is stock-only and this is a counter act, not a stock one.
  - **It is deliberately NOT folded into `order.create`.** The two are different acts with different blast radii — one rings a sale, the other stops the whole organisation selling an item (`01-F22` fast-paths it to every device and channel driver) — and sharing a cell would mean a later narrowing of one silently narrowing the other.
  - **It is not `catalog.edit_menu_prices` either**: `01-F22` and `14 §1` both state that availability is an **operational** event and not a catalog edit, and the back office explicitly does not host it.

- 02-F47 **Recording the caller is its own permission action, and a CASHIER holds it (August 2026).** `02-F27` puts inline customer creation on the POS — *"unknown number → inline customer creation (`customer.created`, `customer.address_added`)"* — but Appendix A has **no customer row**, so Commandment 8's matrix had nothing to refuse against and the fail-closed default (`WRITE_ACTIONS`, `apps/pos-electron/src/main/authorize.ts`) denied both event types for **every role including owner**. `02-F27`'s creation clause was therefore UNBUILDABLE rather than merely unbuilt — the third instance of the shape `02-F46` records for `availability.toggle` (*"the feature could not exist without this row"*) and `14-F30` for `device.manage`. The action is **`customer.record`**.
  - **It lives in doc 02 rather than in Appendix A**, on `02-F46`'s and `14-F30`'s precedent: an FR-decided action does not extend the seed appendix, and several shipped actions already have no appendix row. Appendix A is a seed, not a closed vocabulary.
  - **ONE action for BOTH event types**, on `14-F30`'s own reasoning about splitting a cell four ways: `02-F27` names `customer.created` and `customer.address_added` as one operator act in one clause, and two actions whose cells are identical differ in nothing an implementation can observe. It is also the safer direction — a matrix that allowed the create and denied the address would leave a delivery order with a customer and nowhere to send the food (`09-F10` reads that text off the assigned order). Splitting later is additive; the split has to be justified by a difference, and today there is none.
  - **The verdicts are `order.create`'s row — cashier ✔, branch manager ✔, storekeeper —, owner ✔ — and the cashier cell is the load-bearing one.** `02-F27` puts the operator on the phone with the caller and `02-F28` measures **30 seconds from number entry**; `27-F11e` makes a branch with no manager on the floor the common deployment. A cashier-denied create would put writing down a caller's number behind a manager PIN, inside a 30-second budget, in the branch least likely to have one — `02-F46`'s own argument, and `01-F61`'s: a control whose only holder may not be in the building is a control that does not exist. The storekeeper cell is `—` for `order.create`'s reason: Appendix A's storekeeper column is stock-only and this is a counter act.
  - **It is deliberately NOT folded into `order.create`.** They are different acts with different blast radii and different lifetimes: an order closes at settlement, while `01-F23`'s identity is **permanent** in a ledger `01-F1` forbids correcting in place, and `01-F24` scopes it as customer data with `DEC-DATA-001`'s erasure question still `proposed`. Sharing a cell would mean a later narrowing of either one silently narrowing the other — and the plausible future narrowing is on this row, not on ringing a sale.
  - **A refused customer record never refuses a sale** (`01-F17`). `08-F2` has aggregator orders reach settlement writing no customer file at all, so a denied verdict here costs a name and an address and nothing else. Whatever this cell says, the order is created, lined and confirmed.

- 02-F48 **A tender of NOTHING is not a sale, and declining to record one is not blocking one (August 2026; founder ruling, closes the open `TAKE CASH`-on-an-empty-entry defect).** The Pay surface reads its keypad as rupees and converts to paisa, so an **empty pad is zero** — and pressing the primary action on an empty pad has been recording a permanent `payment.recorded` worth `amount_paisa: 0` against a real bill. `01-F1` forbids removing it, so one accidental tap per shift is one phantom settlement in `02-F23`'s reconciliation and on `02-F15`'s receipt for ever. The arithmetic is unharmed — zero adds nothing to any total — which is precisely why it survived: this is **ledger honesty and cashier trust**, not a money error, and nothing in the system was ever going to flag it.
  - **`01-F17` PROTECTS A SALE, AND THIS IS NOT ONE — the corpus has already read the FR this way once, in its own words.** `01-F60`'s unpriced-item clause rules that an item with no price *"cannot be added … `01-F17` forbids blocking a **sale**, not an item"*, and `01-F59` distinguishes an 86'd item — deliberately still sellable — from that case for the same reason. A `payment.recorded` of zero moves no money, discharges no part of the bill, changes no total and leaves the order in exactly the state it was in. There is no sale to block, because nothing was tendered.
  - **It is NOT `02-F13`'s partial tender, and the difference is not a matter of degree.** A partial is a **positive** amount that does not cover, recorded as itself with the remainder still owed — that path is untouched and must stay untouched, since a split is what happens whenever the first tender falls short. Zero is not a small partial; it is the absence of a tender. The contrast the corpus draws elsewhere is the test: `day.opened` accepts `opening_float_paisa: 0` because *an empty drawer is a real, stated fact*, and `order.line_price_overridden` accepts `0` because it *"distinguishes 'this costs nothing' from 'somebody forgot'"*. Neither reading is available here — a zero tender states nothing a positive one could not, and no operator ever means it.
  - **REFUSED AT ORIGINATION, never at ingest, and never in the schema.** The till declines to originate the event; the decision is made on the **payload alone**, synchronously, consulting no shift, no day, no session scope, no peer, no clock and no network — so it cannot break `00 §5.1` or `01-F17` by construction, and there is nothing about it that a WAN outage can change. **The schema is deliberately NOT tightened to `positive()`:** `payment.recorded` already parses at ingest and on every `01-F6` replay, this defect has shipped, and a device whose own ledger holds a Rs 0 payment must go on reopening its store and merging its peers' history. Tightening a schema on an append-only log is retroactive, and it would quarantine real history to prevent a future typo (`01-F37`, `01-F17`).
  - **`27-F5` IS HONOURED BY CONSTRUCTION: THE CONTROL IS NEVER DISABLED, GREYED, MOVED OR HIDDEN.** An inert primary control is that FR's own failure mode, and `DEC-MONEY-009` already refused the greyed-button shape on this exact surface in favour of a sentence. `TAKE <METHOD>` stays present, labelled, full-size and pressable in every state; what changes is only that an empty entry produces no event. The surface owes the cashier the reason in `27-F12`'s shape — a **word and a number** — where she is already looking, and it must never be a modal (`02-F37`: nothing goes between the cashier and the customer).
  - **What this deliberately does NOT extend to.** `payment.refunded` carries the same non-negative field and the same argument would apply, but refunds are manager-approved (`01-F29`) and have no keypad path in this product, so a rule written for them now would be a rule with no reachable case — named here rather than silently included. And this decides nothing about `01-F30`'s **excess** tender (`EXCESS_TENDER_IS_EXCEPTION`), which is the opposite sign and open on purpose.
  - **⚠ A MEASURED WARNING FOR WHOEVER IMPLEMENTS IT.** `apps/pos-electron`'s guide records that *"the plausible safe repair — gating settlement on a precondition — kills six existing `02-F37` tests"*. That measurement is real and it is about a **different precondition**: those tests exist to stop a settlement being gated on an **open shift**, and every one of them types a real amount before pressing the control. A guard on the **amount** is orthogonal to all of them. Any implementation that reddens a `02-F37` assertion has gated on the wrong thing.

- 02-F49 **`02-F8`'s confirm boundary is enforced AT ORIGINATION, on the till's own converged fold — the `01 §4` dagger made executable (August 2026).** `02-F8` and `01 §4`'s dagger both split one act at one line: *"Line removal pre-confirm is `order.line_removed`; post-confirm it must be `void.recorded` with an approver."* Nothing in the product enforced that split, and **nothing in the kernel can**: `01-F4` validates a payload, and whether an order is confirmed is a **fold** fact that no payload carries. So a `order.line_removed` appended after the KOT printed would have been schema-valid, permanent (`01-F1`), attributed to a cashier with no approver, and would have removed a cooked dish from `01-F30`'s `billed_total` with no `void_value` term to balance it. That is Appendix A's *"Void after KOT printed → needs Mgr PIN"* row bypassed by an event type, which is the theft vector the append-only rule exists to make impossible.
  - **The enforcement point is `main`, against `store.openOrders()`, on `DEC-MONEY-009`'s exact pattern** (`apps/pos-electron/src/main/settlement-guard.ts`): a synchronous read of **this device's own SQLite projection**, consulting no peer, no lock, no clock and no network. `02-F8`'s boundary is `order.confirmed`, and the fold already publishes it as `OpenOrderRow.confirmed_at` — the same anchor `03-F25`'s timers and `02-F9`'s inbox read. A till that asked the cloud whether an order was confirmed would stop selling when the WAN dropped (`00 §5.1`, `01-F17`); a till that reads its own converged state and declines is refusing a **mis-routed act**, not blocking a sale.
  - **A refusal is never a dead end, and this is the clause an implementation gets wrong.** The refusal must hand the operator `02-F20`'s escalation for the SAME line in the same gesture — the local manager-PIN path that already ships (`ManagerApproval`, `CHANNELS.escalationFor` / `CHANNELS.escalate`) — so the act completes as `void.recorded` with an approver. A refusal that merely says no leaves a cook holding a dish nobody can take off the bill, and `27-F5` forbids the control that disappears instead.
  - **"Pre-confirm" and "pre-KOT" name ONE boundary and are not two rules.** `02-F8` writes the first, `01 §4`'s dagger writes the second, and `02-F8`'s own sentence joins them: confirming *"hands KOT jobs to the print service"*, which `02-F9` sharpens to *"KOT jobs created exactly once, **after confirm, never before**"*. `kot.printed` is therefore never the test — it is a device fact that may lag, fail (`03-F5`) or never arrive on a paperless branch, and a boundary keyed on it would let a removal through for exactly as long as a printer was offline.
  - **Neither correction gets a new permission action, and that is the opposite of `02-F46`/`02-F47`.** Those two exist because Appendix A had **no row at all** for availability or for the customer file, so the fail-closed default denied every attempt. Here the row exists and is already mapped: `order.line_added → order.create` ships today, Appendix B names the attributed acts as *"order, **line add/remove**, discount, void, comp, reprint, drawer open, settlement"* — add and remove in one clause, one act — and lists *"item notes"* under **Order capture**. So `order.line_removed → order.create` and `order.note_added → order.create` are transcription, and minting a third action would be the speculative widening `24-F23` forbids. The post-confirm path keeps its own row unchanged (`void.recorded → order.void_after_kot`, `escalate` for a cashier), which is what makes the boundary observable in the matrix and not only in a guard.
  - **A pre-confirm removal carries NO reason and NO approver, deliberately.** `02-F8` calls it a *plain* event and Appendix B puts *"reason + PIN"* on the post-KOT void alone. `C8` runs 10–25× a shift; requiring a reason would put `27-F6`'s banned typing on a critical path, and requiring an approver would delete the distinction this FR exists to enforce. The remedy for a mis-tap is re-adding the item — one tap, the surface's most practised gesture — and the ledger holding both facts is `02-F19` attribution working, not a defect. **No confirmation step**: `02-F37` keeps anything from coming between the cashier and the customer, and a modal on a 10–25× act is the friction that teaches an operator to work around the control.

- 02-F50 **Wave 1's item note is the QUICK-TAG PICK LIST, and free text is deferred with `03-F8`'s reason (August 2026).** `02-F6` names two input routes for one event — *"free text + org-configurable quick-tags"* — and Wave 1 ships the second only. This is a partial implementation with a stated reason, not a narrowing of the FR.
  - **The reason is that free text on this surface can stop the kitchen printing.** `03-F8`'s July 2026 founder ruling rests on a premise it states outright: *"No Wave-1 input path can put non-Latin text on a ticket … **order notes are not wired (`C7` is unbuilt** …)"*. Wiring free text falsifies that premise. A cashier typing Urdu would produce a note the encoder must refuse (`raster_font_unavailable`, `03-F34`'s *"hard refusal to print, never a silent degradation"*), and because the KOT is the only kitchen channel where paper is the only kitchen channel (`27-F11g`), the refusal costs the whole ticket: the sale completes (`01-F17` is unharmed) and **the food is never cooked**. A note is the one field on the chit whose content an operator types, so it is the one place this can happen.
  - **The pick list is what `27-F6` already asks for.** That FR permits typing *"as an optional escape hatch"* and names `02-F6` notes among the legitimate cases — *"The test is whether a non-typing operator can complete the task by another route"*. 24 of 27 field subjects could not type a single word; a tag tile is the route, and `21 §5`'s *icons + numbers dominant, minimal words* and `00 §5.6`'s memorized-position reading make the tile the primary surface rather than the fallback. `02 §7` already carries **kitchen quick-tags** as layer-2 org config, so the list has a home and needs no new `00 §7` key.
  - **The refusal MOVES rather than disappears, and that is the honest gain.** An owner can still type a non-Latin tag into the layer-2 list, and it will still refuse at the encoder. What changes is *where and when*: in the back office, before service, against one list an owner can see and fix — not at the counter mid-rush, against one order, with a cook waiting. Nothing here claims the raster question is answered; `03-F8` and `27-F61` still own it, and the first consumer that genuinely needs Urdu on paper (`06`/`07`) is still where a font and a shaping engine must be chosen.
  - **One tag is one `order.note_added`, and tags ACCUMULATE.** A pick list whose second tap erased the first would be a control that silently discards an instruction — and `27-F59`'s reasoning about removals (*"a removal that is missed is an allergen incident"*) applies with full force to *"no peanuts"* typed as a note. `01 §4` names the type `note_added` and offers no `note_removed` or `note_changed`, which is the catalog stating the same thing. The merge consequence is `26 §7`'s and is settled in `packages/domain`'s and `packages/sync-client`'s oracles: a grow-only set per line, needing no causal link, converging with no clock and no id comparison (`01-F34`).

- 02-F51 **A terminal's current order is one it CHOSE, and `02-F10`'s recall is how it chooses an order it is not already on (August 2026).** `02-F10` makes open orders *"recallable"* and `02-F11` has an order *"resumed, extended, or settled"* on another terminal, but no FR ever said what a cashier PRESSES to get back to one — so the counter shipped an open-orders list whose rows carry no control at all, and starting a second order made the first **unreachable**: no further lines, and **no settlement**. The order is not lost (`01-F1`); nothing on any screen can reach it.
  - **(a) One tap on an open-order row makes THAT order this terminal's current order.** The cart, the grid's `01-F60` price channel, `02-F8`'s confirm and `02-F12`'s tender all read the one order, and pressing the SECOND row recalls the second order rather than the first. It is the row's ONE control (`27-F9`; `packages/ui`'s `OrderList` takes exactly one by design) and it is reachable on arrival. Recall is not a line-state change, so `02-F33`'s read-only posture for STATES is untouched, and the inbox row keeps `02-F9`'s Accept and gains nothing.
  - **(b) It appends NOTHING to the ledger.** `02-F4`'s `order.parked` / `order.unparked` are the branch-wide, ledger-visible form of this question and carry no `01-F4` payload schema, so that emit is unbuildable today — and a recall that wrote would file a permanent row (`01-F1`) every time a cashier looked at her own queue. **Which order a TERMINAL is on is terminal state; which orders a BRANCH has open is the ledger's**, and `02-F11` already publishes that. So this is `02-F4` in the half Wave 1 can build, with the cost stated rather than hidden: a recall here is invisible to every other terminal, so two tills may hold one order — the state `02-F11` describes and `DEC-MONEY-009` already refuses at settlement.
  - **(c) A chosen order is RELEASED when its money side closes, and the cart never falls through to another order.** Once released this terminal has NO current order until it chooses again: the surface returns to its resting state and a tile tap adds a line nowhere. Both halves have a real case behind them. Adding to a closed bill is what a live till did in August 2026 — `01-F33` does not reopen, so the lines landed as `uncovered_addition` against a settled order. Falling through is the worse half: `orders` is BRANCH-wide (`02-F11`), so the cart would silently re-point at whatever another terminal has open and the next tap rings a dish onto a stranger's bill, at a price `01-F53` freezes and `01-F1` forbids correcting. **A PARTIAL tender never releases** (`02-F13`) — the test is the closing reading `DEC-MONEY-009`'s guard already makes (tendered in full against a positive bill, `01-F30`), never *"some money has arrived"*.
  - **(d) What this does NOT decide, stated so silence is not read as blessing.** A terminal that has chosen NOTHING at all — a fresh launch — still shows the branch's first open order as its cart, and a tap there still rings onto an order this cashier never started. That fallback is the `01-F17` compatibility path `DEC-MONEY-009` left behind; roughly a dozen of this app's renderer suites reach the cart through it and one asserts it by name. Retiring it is a ruling with a measured blast radius across oracles this FR does not own, not a clause to slip in beside (c).

- 02-F52 **The operator-facing name for `02-F7`'s state is `Sold out`, and `86` is not English (August 2026).** `00 §5.6` makes the interface English-only, and *86* is American restaurant slang: it is not a word, it is a number that has to be TAUGHT, and `21 §5` puts this operator at plausibly non-reading. The jargon stays in the FRs and the code comments — `02-F7`, `02-F40` and `01-F59` all write it, and this FR does not touch that — but it never reaches glass or paper. The two rendered strings are **`Sold out`** and, for `01-F58`'s unresolved disagreement, **`Sold out — disputed`**.
  - **It is a defect being closed, not a preference being stated, and the evidence is that the product already contradicted itself on one screen.** `Counter.tsx`'s Sold-out tab computes its own labels from the fold's `sold_out`/`contested` facts and has always read `Sold out`; the **Order tab** passes `gateway.menu()`'s `unavailableReason` straight to `ItemGrid`, and that string read `86`.   - **The join is where it belongs and the fold is untouched.** `01-F22`'s availability fold projects booleans and knows no names (`01-F52`), so the vocabulary is decided at the one place the catalog and the fold meet — the host app's display join. Nothing about `01-F57`'s supersedes link, `01-F58`'s contested resolution or `01-F59`'s still-sellable rule changes; this FR is about the word, and `02-F46`'s permission action, `02-F7`'s emit and `27-F4`'s disabled-in-place geometry are all as they were.
  - **`no price set` is deliberately NOT renamed and stays a separate string.** `01-F60` calls the unpriced case the OPPOSITE disposition to the 86 — price known and deliberately sellable, against nothing to sell at — and collapsing the two names would tell an operator an item is sold out when nobody has touched it.

- 02-F53 **Until a capture seam exists, the paid-out's receipt precondition is an operator ATTESTATION and the glass may not claim an image (August 2026).** `02-F26` makes a paid-out *"reason + receipt photo (object storage ref)"* and `02 §8` fixes the sequence — *"captured locally, uploaded opportunistically to object storage, and referenced by id in the event"*. **No capture step exists anywhere in this product**: no camera, no file picker, no image bytes and no uploader, on any device. The counter's control nonetheless minted an identifier on press, reported **`captured`**, and stamped that identifier into `cash.paid_out.receipt_photo_ref`, where `01-F1` makes it permanent — so every paid-out this product has ever taken asserts that an image exists in object storage, and a manager auditing one finds a reference that resolves to nothing. `05-F19` is where the assertion is cashed: it has the over-threshold approval arrive *"with the receipt photo inline"*, which is an interrupt built to display a picture that was never taken. This is `02-F37`'s **"succeed and lie"** standing on the one control `02-F26` puts between petty cash and the drawer.
  - **The control is RELABELLED, not removed, and the choice is forced rather than preferred.** `02-F26` makes the receipt a precondition of money leaving the drawer and the `01 §4` payload makes `receipt_photo_ref` required and non-empty, so removing the control has only two outcomes and both are worse: paid-outs stop entirely — a capability loss no FR authorizes, on an act `02-F43` says legitimately happens before the first shift of the day — or the minting moves to where the operator cannot see it, which is the same false record with the witness taken away.
  - **What it says is what it records: the operator states she has the paper receipt.** Neither the label nor its state word may claim an image was taken, stored or uploaded. The identifier itself stays, because it is the object-storage key a capture step will fill (`02 §8`: *"the event never waits for the upload"*); what changes is that the glass stops asserting the upload already has something to carry. An attested fact with a name against it is the ordinary shape here — `02-F19`/`02-F41` put the actor on the envelope — and it is honest in a way "the device photographed this" is not.
  - **The event, its schema and every fold are UNTOUCHED, and that is deliberate.** Renaming or tightening `receipt_photo_ref` is retroactive on an append-only log and would quarantine real history to improve a word (`01-F37`, and `02-F48`'s identical refusal). The field's meaning never changed: it is the reference, it was always only the reference, and the defect was the *surface* claiming the referent existed.
  - **`27-F4` is not engaged.** No control is added, removed, resized or reordered; the paid-out sequence keeps the geometry that FR's August 2026 amendment (c) approved. A label that stops making a false claim is not a positional change.
  - **What this does NOT do, stated so silence is not read as blessing.** It does not build the capture seam and it does not rule on whether a paid-out should be refused without one — `02-F26`'s photo requirement stands exactly as written and is **OWED**, with `05-F19`'s inline-photo interrupt as the reader that most wants a real image. - 02-F54 **A cashier ENDS her own session with one visible control, and a handover is not a ten-minute wait (August 2026).** `02-F18` gives this device exactly two ways out of a session and both are passive: `01-F26`'s *idle* auto-lock on a device-layer timeout, and nothing else. `02-F41` then rules that attribution is whoever's PIN is in, so from the moment one cashier steps away until that timer fires, every `order.created`, `payment.recorded` and `cash.paid_out` the NEXT cashier makes is stamped with the leaving cashier's `actor_user_id` — permanently, and uncorrectably in place (`01-F1`). **Measured on the shipped counter, August 2026, not predicted:** no surface renders a sign-out or lock control of any kind, and the idle timeout is ten minutes. A handover at a counter running `01-F61`'s 20–60 unlocks a shift is over long before that.
  - **A control, not a surface and not an event.** `App.tsx` already gates the whole app on `DeviceState.user` being `null` (`02-F18`) and the seam already carries a lock decided anywhere — the idle timer proves it. What is missing is the operator's way to decide it. **No `01 §4` type is added** (commandment 2): a session end is not a ledger fact in this product, `01-F5`'s `audit.login` is main's to write, and inventing an event here would put a permanent row on a gesture that happens 20–60 times a shift.
  - **Reachable from the shipped rail, and `27-F4` is NOT engaged.** No tab is added, removed or reordered — that is a breaking change for every operator who learned five, paid on every surface, for a control used once or twice a shift. A control placed inside a surface that already exists is what that FR permits, and `27-F5` binds it: persistent, visible, labelled, never behind a hold or a menu.
  - **Ending a session is not closing a shift, and neither implies the other.** `02-F23`'s close is a money act with a count, an expectation and a variance; this is an identity act with none of them. A cashier locks the till to answer the door, and a lock that closed her shift would file a variance nobody counted (`02-F56`). Conversely `02-F43` has drawer events legitimately happening with no shift open, so a closed shift may not sign anyone out either.
  - **It never blocks and it never asks a question** (`01-F17`, `02-F37`). An open order, an unconfirmed order and an open shift all survive untouched — they are the branch's (`02-F11`), not the session's — and the arriving cashier reaches them through `02-F51`'s recall. A confirmation step is refused on `02-F49`'s reasoning: friction on the one control that protects attribution is what teaches an operator to stop using it.
  - **What this does NOT decide.** The timeout VALUE stays `00 §7` layer 3 where `01-F26` puts it; no wording is fixed beyond `00 §5.6`'s English-only; and nothing here touches `02-F20`'s second session, which exists so an approver can be recorded without moving the actor.

- 02-F55 **The counter's confirm is idempotent and the surface says whether the kitchen has it (August 2026; closes `03-F55`'s owed clause (1)).** `02-F9` already fixes the property for the cloud inbox — *"one-tap Accept → `order.confirmed` (idempotent — at most one confirm per order id; KOT jobs created exactly once, after confirm, never before)"* — and `02-F8`'s counter confirm is the same act on the same event reached from another surface. No clause ever said so and the till never checked. **Measured on the shipped counter, August 2026:** three presses of *Send to kitchen* on one order wrote **three `order.confirmed` rows**, all permanent (`01-F1`). `03-F55` already names why the third press is expected rather than careless — the control reads *Send to kitchen* whether or not the kitchen has been told, so nothing on the glass separates *sent* from *not sent*.
  - **The surface distinguishes THREE states, and the fact that separates them is what this FR adds.** (i) *nothing to send* — no order; (ii) *the kitchen has not been told*; (iii) *the kitchen has it and owes nothing*. State (iii) is the one that did not exist, and its absence is the whole of the operator half: a cashier who cannot see that the ticket went has no reason not to press again.
  - **The separating fact is "lines this device has not yet committed to paper for this order", and it is projected by MAIN.** `03-F55` already defines *committed* — a job exists — and `printing.ts` already computes it per station off `03-F4`'s durable spool. It crosses `18 §9`'s bridge as a projected field on the open-order row beside `confirmed_at`, and a host that does not supply it degrades to state (ii) — pressable — because `01-F54` says degrade to what you know and a duplicate row is a smaller harm than a naan nobody cooks.
  - **In state (iii) no second `order.confirmed` is originated.** The refusal is `02-F49`'s pattern exactly — a local, synchronous decision against this device's own converged fold and its own spool, consulting no peer, no clock and no network — and it is not a schema tightening: `01-F8`'s dedupe covers transport duplicates, `01-F31`'s keys cover money, and neither can see two genuinely distinct envelopes carrying one intent. A device whose own ledger already holds two must go on folding both (`01-F37`, `01-F17`).
  - **In state (ii) the press must still reach the kitchen, and `03-F55`'s addendum mechanism is UNTOUCHED.** What this FR forbids is the second **event** in the state where nothing is owed, never the second **chit**: one is a permanent false record and the other is a dish somebody is waiting for. **The residual is named rather than glossed:** `03-F55`'s addendum is triggered today by a repeat confirm, so an order owing the kitchen new lines still originates a second `order.confirmed`, which `02-F9`'s literal *"at most one confirm per order id"* does not permit. Giving the addition its own trigger is doc 03's seam and is **OWED**; until it exists the two FRs are reconciled only in state (iii), which is the state the measured defect occurred in.
  - **It is not an `01-F17` block and it is not a modal** (`02-F37`). Nothing is refused that has anything to send, no sale is stopped, and a cashier who has genuinely lost her ticket reaches `03-F55`'s reprint rather than a second confirm — `03-F5`'s band is what tells her the paper failed, and that path is untouched.
  - **What this does NOT decide.** No wording is fixed beyond `00 §5.6`; whether state (iii) greys the control or relabels it is `27-F4`'s disabled-in-place rule applied by the implementer; and `03-F55`'s ordinal, band and spool are that FR's throughout.

- 02-F56 **A drawer that was not counted is never recorded as a drawer counted at zero (August 2026).** `02-F23` closes a shift on *"system-expected cash (by method) vs counted cash; over/short recorded and attributed"* — three facts, of which the count is the operator's act and the other two are derived from it. **Measured on the shipped counter, August 2026:** *Close my shift* was live with the keypad untouched, and one press wrote `counted_cash_paisa: 0` with a `variance_paisa` of the entire expectation — an observed **Rs 1,080 shortage recorded against the cashier's own name** (`02-F41`), permanent under `01-F1`, and read downstream as a real shortage by the manager's reconciliation and the owner's nightly summary. That is `02-F37`'s **"succeed and lie"** standing on the one control `02-F23` calls the cashier's own protection.
  - **It is not an `01-F17` block.** No sale is stopped and nothing is lost: `01-F30`'s money is already in the ledger, the shift stays open, the drawer and `02-F21`'s no-sale stay reachable, and she closes the moment she has counted. `01-F60`'s unpriced-item clause and `02-F48`'s zero tender have both already read `01-F17` this way — it protects a **sale**, and a shift close is not one.
  - **The event and its schema are UNTOUCHED** (`01-F37`, and `02-F53`'s identical refusal): `shift.closed` keeps a required non-negative `counted_cash_paisa`, because tightening a schema on an append-only log quarantines real history to prevent a future mis-tap.
  - **`02-F24`'s day close is the same act with the same hazard and binds identically.** Named rather than left to be inferred: its count is a manager's, it feeds `cash.deposit_recorded`, and an uncounted day close puts the fabricated figure into the deposit as well as the variance.
  - **What this does NOT decide.** Whether an opening float belongs in a SHIFT's expected cash is still open — `02-F22` makes the float a day fact and `02-F23` makes the variance a shift fact — and nothing here touches it. - 02-F57 **A REFUSED WRITE IS VISIBLE ON THE COUNTER (August 2026).** `Counter.tsx`'s shared write helper is `void op.catch(() => {}).then(reload)`, and its own comment recorded the cost instead of paying it: *"What is deliberately NOT here: a visible alarm … Recorded rather than improvised."* Measured on a live till: a cashier holding no `day.open_close` pressed **Open the day** and **nothing whatever happened** — the surface after the refusal is identical to the surface before the press, so *"you may not do this"*, *"this device is offline"* and *"this till is broken"* are one picture. `02-F47`'s caller strip closed exactly this for ONE write and said the rest was out of its scope; this is the rest.

Not `03-F5`'s band: `27-F14` allocates red to a closed list this is not on, `21 §5` reserves alarm severities to itself (*"no module invents its own alarm behavior"*), and `27-F11g` makes that band the only signal that food is not being cooked. `27-F12` is the non-colour channel and `27-F5` forbids paying for this with a control that disappears.

  - **What this does NOT decide.** The wording (`00 §5.6` binds it and nothing else), whether the refusal names the permission or only the act, and whether it clears itself or waits to be superseded by the next attempt.

## 4. Key flows

**Dine-in order (happy + print failure)**
1. Cashier PIN-unlocks → taps table → builds order from grid (lines persisted locally as events before UI ack, 01-F2).
2. Confirm → `order.confirmed` → print service routes KOTs by category (doc 03).
3. Failure path: a routed printer is offline → spooler retries → loud on-device alert names printer + order (03-F4); the order remains valid; cashier reroutes or reprints after fixing.
4. Later: settle (any method/split) → receipt prints → lines close → table frees.

**Split bill & settle**
1. Table asks to split → cashier splits by item → `order.split` creates two child orders referencing the parent → each settles independently (one cash, one card) → both receipts print; reporting sees two settlements, one service.

**Void after KOT with remote approval**
1. Cashier initiates void with reason → `approval.requested` (type `void`) goes to the manager console; the POS simultaneously offers local manager-PIN entry.
2. Manager one-tap approves on their phone (doc 05) → `approval.granted` propagates over LAN < 1 s → POS emits `void.recorded` with actor + approver. Denial or timeout leaves the line intact.

**Phone order (repeat customer)**
1. Number entered → customer card renders with addresses + history → "repeat last order" → adjust → confirm ≤ 30 s → KOT prints → dispatch handoff per doc 09.

**Foodpanda quick entry**
1. Rider/tablet order shouted from the aggregator tablet → operator opens quick entry → taps 3 mapped items → confirm ≤ 30 s → KOT prints, channel-tagged `foodpanda` → inventory and channel reports stay truthful with zero extra work later.

**Shift close**
1. Cashier taps close shift → system shows expected cash by method → counts drawer → over/short computed, attributed, shown to the cashier → `shift.closed` → manager sees variance on console/day close.

**T1 evening**
1. Single device: orders, KOTs, receipts, availability toggles, shift and day close all on one terminal; queue panel shows aging; statuses auto-advance per 02-F31. WAN state is irrelevant throughout (00 §5.1).

## 6. Non-functional requirements (module-specific)

- 02-N1 Inherited targets apply unchanged (00 §5.3): line add < 100 ms, confirm → KOT start < 2 s, cold start < 6 s — on the PKR 25k reference tablet and the old-Windows-10 reference PC.
- 02-N2 Menu grid stays within the 100 ms line-add budget at 300 menu items × 5 variants; search results < 150 ms keystroke-to-render.
- 02-N3 Phone entry (02-F28) and quick entry (02-F30) each ≤ 30 s, measured in release builds.
- 02-N4 ≥ 5 concurrent POS devices per branch stay LAN-coherent (`restaurant-os.md` Appendix G) within kernel propagation targets (01-F15).
- 02-N5 A parked order is plug-pull safe the moment the park action returns (00 §5.2).
- 02-N6 Any core cashier flow learnable in < 15 min (00 §5.6) — validated with real staff at dev-pilots before Wave 1 sign-off. **Internal target, not a merge criterion (27 §8):** published training-time claims for POS systems span 20 minutes to 40 hours, all vendor or SEO content, so no number here is evidentially grounded. Keep the goal; do not gate a release on it. Note also 27-F53 — a novice-only test cannot detect the flat-vs-hierarchical layout decision, whose benefit appears only in experts, so this check must be paired with an experienced operator at rush tempo.

## 7. Customizability

- **Layer 2 (org):** enabled order types and payment methods; khata on/off; discount threshold % and void/comp approval rules (01-F26); receipt header/footer/logo/QR; kitchen quick-tags; call-center zone→branch routing; channel chime behavior; remote-vs-local approval preference.
- **Layer 3 (branch/device):** printer assignments, idle-lock timeout, default opening float, quick-entry shortcut visibility.
- **Deliberately not configurable:** attribution (no shared/anonymous logins), append-only corrections, escalation bypass below org thresholds, drawer-open logging, channel tag on ingested orders, the sync-honesty indicator.

## 8. Tech notes

- Electron: main process owns `packages/escpos` transports, the hub role, and `better-sqlite3`; renderer is React with a virtualized menu grid. RN build: Expo + `op-sqlite`, Hermes; same fold/domain code.
- Offline PIN auth per 01-F28; role/permission matrix synced as reference data.
- Split/merge/move are pure event compositions — no special sync handling; kernel conflict rules 01-F16/F19 cover concurrent edits.
- Photos (paid-out receipts) are captured locally, uploaded opportunistically to object storage, and referenced by id in the event — the event never waits for the upload.
- Rush-simulation load (00 §4) runs against a full POS + printer rig before each release-channel promotion (doc 15).
