# 14 — Restaurant Back Office (Web)

**Module spec — Draft 1, July 2026** · Parent: `00-platform-overview.md` (conventions §5–§7 inherited; this module **is** the layer-2 configuration surface of 00 §7). References: `01-kernel-sync.md` (catalog model 01-F21, devices 01-F25, conflict rules), `02/03` (routing targets), `10-inventory-supply.md` (recipes, tracked items), `12-owner-app.md` (report parity), `13-intelligence.md` (autonomy config surface 13-F28), `15-platform-admin.md` (layer-1 boundary), `16-tax-module.md` (tax posture), `restaurant-os.md` Appendix A (permission matrix seed). **Wave 1+, grows with modules.**

## 1. Purpose & scope

The back office is the restaurant's administration surface: a responsive Next.js web app, org-scoped and role-gated, where everything in configuration layer 2 lives — catalog, recipes, printing/station routing, devices, users/roles/PINs, tier + signal ownership, approval thresholds, channels, alert thresholds, tax posture — plus desk-sized report views/exports and the onboarding wizard.

Used by owners, permitted managers, and the vendor onboarding team (acting as scoped org users). It is not an operational surface: no order entry, no floor state (docs 02/05), no availability toggling (01-F22 keeps that operational).

Everything here follows **presets, not knobs** (00 §7): a profile + tier choice sets defaults; individual settings adjust within designed bounds; this module introduces no free-form configuration.

## 2. Position in platform

- **Depends on:** api-gateway (tRPC); kernel reference-data distribution (01-F21, 01 §8 — catalog/config versions ride the event channel to devices); read models for reports; export jobs + S3.
- **Emits (extensions to 01 §4 marked):** `config.changed` (every settings change, with actor — module law); `catalog.changed` (extension: entity-level catalog edit with actor + before/after refs); `device.registered` / `device.revoked` (extension, per 01-F25); `user.changed` (extension: create / role change / PIN reset — PINs stored Argon2id, never present in payloads); `audit.*` for all admin actions.
- **Consumes:** report read models; device registry state + heartbeat summaries (doc 15 pipeline); doc 13 autonomy state and alert-config schema; doc 16 tax posture schema.

## 3. Functional requirements

**Shell, scope, audit**
- 14-F1 Org-scoped: a session sees exactly one org. Role-gated per the permission matrix (Appendix A seed via 01-F26) — e.g. recipe editing only for owner/vendor-onboarding roles; menu/price edit per matrix; managers see only what their role grants.
- 14-F2 **Every settings change emits `config.changed`** with actor, entity, before/after values, and a config version bump. No silent edits exist (00 §5.5).
- 14-F3 The change history of any entity is browsable in place ("price changed by Ali, 2 Jul, 450 → 480") — the audit trail is a first-class UI element, not a hidden log.
- 14-F4 Changed reference data propagates to devices via kernel sync (01-F21); each config screen shows distribution state ("live on 4 of 5 devices") from sync status (01-F11), honestly aged per 00 §5.7.

**Catalog management**
- 14-F5 Full editing, within append-only law, of the 01-F21 catalog chain — Category → MenuItem → Variant → ModifierGroup/Modifier — covering:
  - display name (English — 00 §5.6);
  - images (S3), sort order, category tabs;
  - per-channel visibility flags (an item can be dine-in-only or storefront-hidden).
- 14-F6 Pricing: per variant/channel price edits emit `catalog.changed`; price history is viewable per item. Order lines snapshot price at line-add and are never re-derived (01-F18) — the price editor states this ("open orders keep their price"). The editor's shape and its completeness rule are `14-F29`.
- 14-F29 **The item editor collects a price for EVERY enabled (branch, channel) pair, prefilled from one number (founder ruling July 2026).** `14-F6` required per-channel pricing without saying what the editor asks for. Ruled: adding or editing a sellable item shows a price **grid** — a row per branch, a column per enabled channel (`00 §7` layer 2) — **prefilled with a single value and settable across the whole grid in one action**, with overrides typed on top of individual cells. Saving an item that leaves an enabled pair unpriced is **refused** — the same rule the kernel enforces at publish (`01-F60`), stated here because this editor is where an owner meets it.
  - **The grid is the reason prefill is mandatory rather than a nicety.** A single-branch org sees one row and types one number. A five-branch org faces 5 × 5 = 25 cells per item, of which most are usually equal — so an editor without a fill-across action would make the honest schema unusable and drive owners toward whatever shortcut existed. Fill-across, then override the few that differ, is the interaction the ruling names, and `14-F8`'s bulk % adjustment applies per column so a foodpanda uplift can be applied across the menu in one act.
  - **Why prefill rather than a house-price fallback.** The cheap alternative — one base price with optional per-channel overrides — makes a *forgotten* override indistinguishable from a *deliberate* equal price. On an aggregator that means selling at the in-restaurant rate while commission (25–35%) still takes its cut: invisible at the till, frozen by `01-F53`, and surfacing months later as thin margin nobody can attribute. Prefilling buys identical one-number onboarding and leaves no silent case. The completeness rule is enforced in the kernel because a bulk import (`15-F8`) never opens this editor.
  - Channel prices participate in `14-F3` history and `14-F8` bulk edit per channel, and sit beside `14-F5`'s per-channel visibility flags: **visibility says where an item sells, price says for how much**, and neither stands in for the other.
- 14-F7 Archive, never delete: items with sales history are archivable (hidden from menus and POS grids) but remain resolvable for historical reports and event folds.
- 14-F8 Bulk edit: multi-select price adjustment (absolute or %) with preview and a single confirmation, emitted as individual `catalog.changed` events so history stays per-item.

**The catalog editor's SHAPE (added August 2026 — founder review of the shipped form: *"this is very complex interface. What even is this. this is so hard to use. I cant understand a single thing."*)**

`14-F5` said what the editor may EDIT and `14-F29` what the price grid must ASK. Neither said what the surface is shaped **like**, so it was shaped like the storage model: a `kind` discriminator, a hand-typed `id`, a `parent_id`, a `sort` integer, two optional routing fields and a publish-timing fieldset, all at once, on one form that adds a category and adds a dish with the same controls. The owner's task is *"add Ramen to my menu and price it."* `14-F32`..`14-F38` decide the shape; none of them amends `14-F28` or `01-F60`.

- 14-F32 **One task per form: the editor is chosen by the JOB, not by the entity.** Creating an entry begins with a choice of task named in the owner's vocabulary — one task per `01-F21` kind (a dish · a menu section · a size or version of a dish · a choice group · an add-on) — and the kind discriminator never appears as a control the owner operates. The internal kind strings are vendor vocabulary under `14-F38` and are not rendered; the task noun is this surface's name for a kind everywhere, including on a saved entry and in `14-F3`'s history.
  - **A field appears in a task's form only if that kind can carry it.** Prices only for the kinds `01-F60` makes sellable (a section is priced by nothing, and an editor that shows it an empty grid is teaching the owner that the grid is optional); kitchen name and station only where `03-F38`/`03-F50` apply.
  - **The kind is fixed at creation and an existing entry never offers it.** Every reference the product makes to a catalog entry is an id — `parent_id`, `order.line_added`'s item, `01-F54`'s degradation — while the published artifact is versioned per `(kind, id)`; so changing a published entry's kind starts a second lineage under one id and leaves the first resolvable for ever (`01-F1`, `01-F55`). ⚠ **PINNED INTERPRETATION:** the corpus nowhere rules on mutating `kind`, and this rules the narrow direction. An owner who chose the wrong task creates the right entry and archives the wrong one (`14-F7`) — which is the append-only shape rather than a workaround for it.
  - **Rejected: one form with a kind selector and conditional fields.** It is what shipped and it is cheaper by a branch. It also makes the owner answer a schema question — *is a Half Plate a variant or an item?* — before he is allowed to type a name, which is the defect in one sentence.
- 14-F33 **The identifier is generated, permanent, readable and demoted; `BELONGS TO` and `ORDER` stop being raw columns.** No control on this surface accepts an id.
  - **Uniqueness is per ORG across every kind, not per kind.** The catalog is org-scoped (`01-F52`) and every reference to an entry carries an id alone, while storage keys a version by `(kind, id)` — so a cross-kind collision is expressible in the store and unresolvable at the till. The generator refuses one.
  - **Assigned once, never regenerated** — not on rename, not on re-parent, not on archive or its reversal, not on a price edit. `01-F53` has already frozen it into every line rung, `01-F55` keeps a tombstone resolvable by it, and `01-F1` forbids rewriting either. *"Regenerate the id"* is not an operation this module has.
  - **Derived from the name the owner typed, not opaque**, with a numeric suffix on collision. `01-F54` renders the identifier **to a cashier** when an item is unknown or not yet synced, so an id is user-visible in exactly the state where the product is already degraded: `chicken-karahi` degrades to a legible dish and an opaque UUID degrades to nothing. ⚠ **Interpretation** — the corpus rules the consequence (`01-F54`) and not the form; a UUID is the obvious alternative and is refused on that clause alone. The accepted cost is that a renamed dish keeps an id spelling its old name. That is correct rather than tolerated: the id is a key and not a label, and `01-F55`'s tombstones make id-spelling drift permanent whatever this FR chose.
  - **Shown once, demoted, on a saved entry — never on a control.** An owner matching a till's degraded line or quoting an entry to support has to be able to read it (`00 §5.7`); he must never have to invent one.
  - **`BELONGS TO` becomes a question about the menu.** Where the `01-F21` chain gives a kind a parent, the form asks for it by the parent's **name**, chosen from the entries that exist, and pre-selects the section the owner was looking at when he started the task. A kind with no parent in the chain does not ask at all.
  - **`ORDER` is assigned, never typed.** A new entry appends after the last entry under the same parent. Position is changed where position is visible — on the menu list — and a change of position is an operational-grid reorder, so `27-F4` binds it through `14-F28`'s timing exactly as a rename does. This FR forbids the raw sort integer in a data-entry task; it does not specify the reorder gesture (§9.8).
- 14-F34 **Every field says what it is and why you would set it, and a collapsed group says what is inside it before it is opened.** The founder's own condition on progressive disclosure: *"hide until needed, but there are no guidelines like what is what and why something should be entered."* Disclosure without guidance moves the confusion; it does not remove it.
  - **Every control that accepts owner input carries a help sentence, rendered adjacent to it and readable without pointing at it** — never a tooltip, a hover or a `title` attribute as the only carrier. It says two things: what the field is in the owner's terms, and what happens if he leaves it as it is.
  - **The sentences live in the app's string catalog**, so completeness is assertable without rendering anything: every field on this surface has a help string, and no help string is empty. That is the testable form of this FR and the reason it is written as one.
  - **A collapsed group's closed state names what is inside it AND the outcome of never opening it** — *"Kitchen printing — the ticket says Chicken Karahi and prints at Grill. Open to change either."* A disclosure whose closed state says only *"Advanced"* fails this FR.
  - **Nothing a save can refuse may be collapsed.** Hiding a field whose absence blocks the save produces a refusal pointing at a control the owner cannot see, so the name and `14-F29`'s price grid are never inside a disclosure.
  - **Why disclosure is legal here and banned at the till:** `27-F1`/`27-F2` bind *operational* screens, and §1 says this module is not one; `21 §5`'s owner law names progressive disclosure outright — it is written against doc 12's surfaces and the reader is the same person at the same glance budget. The asymmetry between this module and the till is deliberate, not an exemption.
- 14-F35 **An inheriting field shows the value it will inherit, resolved, without opening anything.** `03-F38`'s kitchen name and `03-F50`'s station are optional, inherit down the `01-F21` chain, and blank is the normal case — so blank is exactly what must be legible.
  - The form renders the **resolved** value that will apply and where it came from (*"Grill, from the section Karahi & Handi"*, *"prints as Chicken Karahi — the name above"*), never an empty box, never the bare word *inherit*, and never a value whose origin an owner cannot see.
  - That resolution is visible in the **collapsed** state, which is what makes `14-F34`'s closed-state requirement satisfiable for the printing group rather than aspirational.
  - Where nothing up the chain sets one, the surface names the value that will actually be used **and says it is the platform's, not the owner's** — the terminal station fallback is a pinned constant rather than a specified value, and a screen that presents it as a configured choice is claiming a decision nobody made (`00 §5.7`).
- 14-F36 **Publish timing belongs to the ACT, not to the entry.** `14-F28` is not re-opened: the choice stays per edit, the default stays the 05:00 boundary, apply-now stays explicit with its consequence on the control. ⚠ **R31 (August 2026) widened `14-F28`'s choice from two options to three — now · at a picked time · at the day boundary — and this FR's rule is what carries it:** the picked TIME belongs to the act as well, so an edit staged for 6pm is a property of the publish, never a field on the entry. An entry carrying its own schedule is how two entries published together come to apply at different moments. What this FR decides is **where the question is asked**.
  - The timing control is part of the **commit** — adjacent to the control that performs it — and is never a fieldset in the middle of data entry. *"WHEN DOES THIS APPLY?"* as a section of a create form asks an owner about ledger timing before he has typed a price.
  - **Its resting state is one line stating the default outcome in the owner's terms** (*"The tills get this at 05:00 tomorrow"*), so `14-F28`'s default is chosen visibly and never by silence. It is never collapsed to nothing.
  - **Apply-now is never pre-selected and never remembered between edits, and its consequence is rendered before it can be chosen** — not after, and not as confirmation. This is `14-F28`'s *"not a hidden default"* restated for a surface where the option is one act away from the primary button.
  - ⚠ **Interpretation:** `14-F28` can be read as requiring the two options to be equally prominent. It is read here as requiring the choice to be **available and consequential**, not equally weighted — the FR itself makes one the default and calls the other *"a deliberate act"*.
- 14-F37 **An incomplete price set is obvious BEFORE the save is pressed, and it is counted.** `01-F60` refuses at the writer and `14-F29` restates the refusal at the editor; both fire on a save. This FR moves the fact earlier, because a refusal is a poor way to learn what a screen wanted.
  - **A running count adjacent to the grid, changing with every keystroke** — *"3 of 9 prices still needed"* / *"every price set"*. It is the same completeness rule `assertSavable` enforces, rendered continuously rather than on demand.
  - **An empty cell reads as an absent price and a free one as an explicit zero** (`01-F60`), because a count is worthless if the owner cannot see which cells it means.
  - **The commit control is not disabled.** A disabled control explains nothing; it states what is missing, and on press it names every missing `(branch, channel)` pair (`14-F29`).
  - **The count is not coloured while the item is merely unfinished.** `27-F16` reserves colour for the abnormal, and a half-typed new item is the normal state of a form; colour arrives with a refusal.
- 14-F38 **Owner-facing text on this surface names no internal identifier.** Measured August 2026 — **17 of the back office's 143 string-catalog entries carried an FR id**, counted with comments stripped and concatenated literals joined, because a comment hit is not a rendered string and counting the two together is how a number here goes wrong. One reads *"Leave blank to inherit from the category above (03-F50)"*; one tells the owner to *"Set ENABLED_BRANCHES and ENABLED_CHANNELS on the RestOS service."* To a restaurant owner those are error codes.
  - **No rendered string contains** an FR id, an event type, a config or environment variable name, a code symbol, a table or column name, or a file path. The internal `kind` strings are covered by this rule; `14-F32`'s task nouns are the owner-facing names.
  - **The citation does not disappear — it moves.** It belongs in the string catalog's comment beside the sentence, where commandment 9 and `14-F2`'s traceability are served and no owner reads it. Nothing is lost but the audience, which is what makes this rule cheap enough to be absolute.
  - **A message about something the owner cannot change names the ROLE that can**, never the mechanism: *"whoever runs the RestOS service must enable at least one branch and one sales channel before prices can be set."* `00 §5.7` still binds — the surface says what is true and never implies the state is fine.
  - ⚠ **Scope, stated so it is not over-read: this binds THIS module.** The same defect plausibly exists on other surfaces; widening it platform-wide amends `21 §5`'s language law or `00 §5.6` and is deliberately not taken here.

**Recipes (with doc 10)**
- 14-F9 Two recipe editors, editable by the vendor onboarding team and permitted org users only (Appendix A):
  - **menu recipe:** sold item/variant → ingredient lines (raw or prepared, integer mg/ml/units per 00 §6);
  - **prep recipe:** inputs → prepared output with yield % ("18 kg raw → 15 kg marinated boti").
- 14-F10 Tracked-item discipline surfaced: the editor shows which ingredients are `is_tracked`, the recipe-coverage % of trailing revenue (feeds the 13-F5 margin precondition), and par levels per location.

**Printing & station routing**
- 14-F11 Routing rules: category/item → station(s) → printer(s), per branch; validated against registered printers (doc 03); a test-print button per rule proves the route end-to-end. Station classes are assigned here; physical printer assignment stays a device-layer setting (doc 03).

**Device management**
- 14-F12 Device list per branch: class, app version, last-seen, sync lag. Pairing via one-time codes (01-F25); station class assignment per device.
- 14-F13 Revocation is immediate ("stolen tablet" flow): `device.revoked` → cloud token rejected, LAN participation flagged branch-wide on next contact (01-F25); the list shows revoked state and actor.
- 14-F30 **`device.manage` is the permission action for this §3 block, and it is OWNER-ONLY (August 2026 — a PINNED INTERPRETATION, contestable, not a transcription).** `14-F1` gates this module "per the permission matrix (Appendix A seed via 01-F26)" and commandment 8 requires every request to pass `can()`, but **Appendix A has no device row at all** — so until this FR the device surface had nothing to authorize against, and `14-F12`/`14-F13` could not be built without either inventing policy (commandment 2) or shipping an ungated destructive act. The five decisions:
  - **THE ACTION IS DECLARED HERE, AND APPENDIX A IS NOT EXTENDED — on the corpus's own precedent, counted rather than asserted.** Before this FR the matrix carried **22** actions and Appendix A was a **15-row** table mapping one-to-one onto 15 of them, so **7 of the 22 were already decided by the FR that names them** and not by the appendix: `order.price_override` and `approval.grant` (02-F20, with 02-F38 for the self-approval refusal), plus the five service-surface rows `shift.open_close` · `cash.count` · `cash.drawer_no_sale` · `cash.paid_out` · `refund.issue` (02-F21..02-F26, 02-F36, 02-F43, 05-F19). ⚠ **The count turns on one reading, stated so it is checkable rather than asserted:** Appendix A's *Day open / close, cash count* row decides `day.open_close` **only** and not `cash.count`, because 05 §3 splits the two acts — doc 02 owns the cashier's own drawer count at shift close (02-F23), doc 05 the manager's day-close count entry — which is the reading `packages/domain` already ships. Read the other way, so that one row decides both, it is 6 of 22. Either way the precedent holds and this FR follows it: 01-F26 names Appendix A a **seed** and §7 lists the matrix's hard rules among the things that are deliberately not configurable, so the appendix is a fixed origin, not a register that grows. Extending it per FR would also make it disagree with `restaurant-os.md`, which no code reads.
  - **ONE action, not two.** The simpler split — a read action for `14-F12`'s list and a destructive one for `14-F13`'s revocation — was considered and rejected as *speculative* while every cell is identical: two actions with the same four cells differ in nothing an implementation can observe. It becomes a real question the moment a role is widened into the list, and that is the edit to make then. Precedent: `catalog.edit_menu_prices` already gates the catalog READS for exactly this reason (no Appendix A read row exists, and inventing one is inventing policy). The name comes from this block's own heading, **Device management**, so a later act added here (01-F25 pairing, station-class assignment) inherits it deliberately rather than by omission.
  - **Owner allow · Branch Mgr deny · Cashier deny · Storekeeper deny.** The corpus names exactly one role for this act and names it twice — `14-N2` ("an owner can change a price **or revoke a device** from their phone") and §4's *Device revocation* flow ("**Owner** marks a tablet stolen"). No FR puts a manager, cashier or storekeeper on it. §9's first open question — "whether managers get a scoped back-office slice on phones … or stay manager-console-only until pilots demand it" — is the corpus stating that a manager's back-office reach is **undecided**, so widening one here would be answering an open question by accident. Widening is additive and safe; narrowing later is not, and the wrong guess in the permissive direction is an accidental or malicious revocation, which stops a till mid-service.
  - **The pairing with `catalog.edit_menu_prices` is the structural argument, not an analogy.** `14-N2` puts the two acts in one sentence as the two things an owner does from a phone, and Appendix A's *Edit menu & prices* row is `—` · optional · `—` · ✔ — the only back-office config row it carries, resolved to owner-only in `packages/domain` because "optional" is org-configurable and no FR states its default. A device row drawn by the same hand would look the same.
  - **The ACTOR is the authenticated back-office session, and it is recorded on `device.revoked`** (org-scoped per 01-F62; T-01-09 puts `device.registered / revoked` emission on this doc's emitter and not on the kernel's registry seam). `14-F13`'s "the list shows revoked state and actor" is therefore two reads joined: **revoked state** from the device registry, **actor** from the org-scoped event. `01-F48`'s eviction is unaffected — it reads `revoked_at`, so the ledger row is attribution and never enforcement, and a failed append leaves a dead till with an unattributed revocation rather than a live till with an attributed one.
  - ⚠ **`device.registered` stays unemitted, and this FR does not close that half.** Registration today is an operator command on the service host with no authenticated user, so the only actor it could write is `null` — permanently, into an append-only store (commandment 1), and "somebody registered this and we do not know who" is a worse record than none because it looks like one. It is unblocked by 01-F25's back-office pairing code, not by this FR. The consequence is stated rather than implied: the org-scoped history holds revocations with no matching registrations, so **it is not a device history and no surface may render it as one** — `14-F12`'s list is the authority for which devices exist, and the event supplies only *who revoked*.
  - **No un-revocation.** The corpus is SILENT rather than permissive — no FR, no `DECISIONS.md` row — and 01-N5's replacement path (a fresh `device_id`) is what exists. A restore control here would be inventing security policy.

**Users, roles, PINs**
- 14-F14 User CRUD with role × per-location assignment; per-user permission overrides within matrix bounds; PIN set/reset (never displayed; Argon2id per 00 §5.4); deactivation preserves historical attribution.
- 14-F15 Owner-visible login and audit history per user, rendered from `audit.*` events.
- 14-F39 **`user.manage` IS THE PERMISSION ACTION FOR THIS §3 BLOCK, AND IT IS OWNER-ONLY (August 2026).** Measured: `packages/domain`'s matrix ships **25** actions and not one names a user, a person or a role; `authorized()` takes an action from that closed list and the API host refuses at boot to serve a procedure that names none. So `14-F14` and `14-F15` cannot be built *or* booted — the same wall `14-F30` found in front of the device list, one block down. `28-F13` files this gap, names the surfaces it blocks (its own §4 flow terminates at an owner who then cannot add staff), and routes it here.
  - **PLACEMENT IS NOT RE-ARGUED — `14-F30` decided it and `28-F13` cites that decision by name.** The action is declared in the FR that owns the surface, and Appendix A is **not** extended: `01-F26` calls the appendix a *seed*, §7 lists the matrix's hard rules among the things that are deliberately not configurable, and `14-F30` counted the precedent (7 of the then-22 actions have no appendix row) rather than asserting it. `02-F46` and `02-F47` landed the same way. Deciding it in doc 28 would have put the action in the wrong doc and re-opened `14-F30`'s reasoning where no reader of this surface will look; restating the count here would be a second copy of a number `14-F30` already made checkable.
  - **ONE action, and `14-F30`'s test was RUN rather than assumed.** The candidate split is `14-F15`'s read — login and audit history per user — against `14-F14`'s writes: create, role × per-location assignment, PIN set/reset, deactivation. Under the cells below **every cell of both halves is identical**, so the two actions would differ in nothing an implementation can observe, which is the precise ground on which `14-F30` refused its own split. ⚠ **Unlike the device block, this one has a NAMED trigger for the split, written here so the edit is obvious when it comes:** §9.1 asks whether managers get a scoped back-office slice, and the failure directions are wildly asymmetric — a manager who may write users may make herself an owner, or reset the owner's PIN, and `01-F1` makes both permanent. If any role is ever widened into this block, the read/write split is the edit to make **in the same change as the widening**, never after it.
  - **Owner allow · Branch Mgr deny · Cashier deny · Storekeeper deny — A PINNED INTERPRETATION, CONTESTABLE, NOT A TRANSCRIPTION, and §9.1 is the question that owns the axis.** `14-F30` labelled its own identical decision exactly this way and the label is load-bearing here rather than borrowed: **§9.1 names `users` by name** (*"whether managers get a scoped back-office slice on phones (thresholds, users)"*), so this is the one axis the corpus has explicitly left open, no founder ruling R1–R26 touches it, and `DECISIONS.md` carries no row. What settles the **routing** is `28-F13` (the action is declared in the FR that owns the surface); the **cells** it explicitly declines to decide, saying deciding them there would *"re-open `14-F30`'s owner-only reasoning"*. The pin is owner-only because no FR puts a manager, a cashier or a storekeeper on user administration, so widening here would answer §9.1 by accident, and the failure directions are not symmetric: widening later is additive and safe; narrowing later is not, and the wrong guess in the permissive direction is a self-promotion path into an append-only ledger (`01-F1`, `02-F41`). **The pin resolves when §9.1 does, and it is not evidence for how §9.1 should go.**
  - **What it gates:** `14-F14` entire — creation, role and per-location assignment (`01-F26`), PIN set/reset (which writes `11-F21`'s Argon2id hash and never a PIN, and never displays one) and `11-F22`'s status change — plus `14-F15`'s per-user history. `01-F71` still binds underneath it: the org comes from the authenticated subject and never from the request, so an owner of one org cannot reach another's roster through a procedure this action allows.
  - **It is an ACTION and not an event, and the neighbouring event is BLOCKED.** `user.manage` is the infinitive of an act; `user.changed` is `00 §6`'s `noun.verb_past` and is already in the `01 §4` catalog — the same two-vocabulary distinction `14-F30` draws between `device.manage` and `device.revoked`. ⚠ **But `user.changed` cannot be emitted today: `packages/domain/src/registry.ts` declares no payload schema for it**, and `01-F4` makes producing a type with no schema a build-time *and* runtime error — so `14-F2`'s ledgered write of every settings change is **unbuildable rather than unbuilt**, which is `28-F14`'s state for `config.changed` and `05-F7`'s for the approval family, verbatim. **Owed with a named owner, on `28-F14`'s own routing and not decided here: doc 14 declares the payload — it owns `14-F2`, `14-F14` and this surface — and doc 01 absorbs it** (§9.11). **The payload is a PRECONDITION of the surface, not a follow-up, and this FR says so rather than leaving it to sequencing:** `14-F2` requires *every* settings change to emit `config.changed` with actor and before/after values and says *"no silent edits exist"*, so a user CRUD shipped without a payload to emit does not ship an unledgered feature — it ships a **`14-F2` violation**, and the act it fails to record is a change to who may sell in a restaurant, permanent under `01-F1`. A surface that cannot satisfy the module law that governs it is not ready; the payload lands first.

- 14-F28 **A menu edit's application time is the owner's choice per edit — default DAY-END, with an explicit immediate option (gap G17, founder ruling July 2026).** `27-F4` makes adding, removing or reordering an operational grid item a **breaking change**, because a cashier's speed is muscle memory; but back-office menu editing is a runtime org action, and nothing connected the two. The resolution honours both: **the default is the 05:00 business-day boundary (`01-F46`), so a grid never moves under a cashier mid-shift** — and because menu changes are sometimes genuinely urgent, the owner may mark any edit **apply now**, which is a deliberate act with the consequence stated on the control, not a hidden default. ⚠ **EXTENDED (August 2026, founder ruling R31): the choice is now THREE-WAY — now · at a time the owner picks · at the day boundary.** The binary was the gap: an owner who wants a price live at 6pm before the dinner rush had to choose between *now* (three hours early) and *day-end* (fourteen hours late), and the FR offered her no way to say what she meant. R31 generalises this FR rather than replacing it — *"for every action we should ask the user if he wants it to be immediate or scheduled at a specific time"* — and this FR is the corpus's own precedent for that model, which is why the ruling extends it instead of inventing a second one. The default is unchanged and the reason is unchanged. **`01-F46` is untouched**: it is the business-DAY anchor, not a scheduler, and R31 explicitly does not reach it. Pending day-end edits are visible and cancellable until they land. New items carry a first-days marker on the grid so a cashier can find what changed. **Amends `27-F4`**: the acclimation requirement binds the *vendor's* shipped grid structure absolutely, and org menu content through this timing rule.

  - **This module is already where doc 12 has a desk mirror.** `14 §1` scopes the back office to org configuration *"plus desk-sized report views/exports"*, and `14-F24` is titled the *"desk mirror of doc 12"*. Commandment 5 is satisfied by doc 12 itself rather than by this FR — `12 §8` says the owner app *"stays on the cloud plane (18 §6): it does NOT run `sync-client` and has no kernel outbox"*, `18 §6` lists it on the cloud plane, `01-F7` makes a Postgres read model the sanctioned source, and `00 §5.1` exempts *"cloud-only surfaces (storefront, owner app)"* from commandment 4 by name. Doc 12's Wave-1 emission set is exactly `{audit.login}`, which `01-F62` names as its own worked example of a type that stays branch-scoped **because a device emits it at a PIN unlock** — so an **Expo owner app is exactly as unable to append it as a browser is.** Anyone arguing the RN client on `01-F62` grounds is arguing from a false premise.

## 4. Key flows

**Price change**
1. Manager opens item → edits price → preview shows affected channels + "open orders keep their price".
2. Confirm → `catalog.changed` + config version bump → reference delta distributed (01-F21).
3. Screen shows "live on N of M devices"; an offline device applies it on reconnect.
4. Any order line added before arrival keeps its snapshotted price (01-F18) — no retro-repricing, by design.

**Add a dish (14-F32..F37)**
1. Owner picks the task *"a dish"* → the form asks for a name, and for the section it belongs to (pre-selected if he was looking at one).
2. Kitchen printing is one collapsed line stating what will happen if he never opens it — the ticket name and the inherited station, resolved (14-F35).
3. The price grid is open, not collapsed (14-F34), and states how many enabled `(branch, channel)` pairs are still unpriced as he types (14-F37); one number fills the grid and overrides are typed on top (14-F29).
4. The commit line states *"the tills get this at 05:00 tomorrow"*; the immediate option is one explicit act away with its consequence read first (14-F36, 14-F28).
5. Save → `catalog.changed` with the generated identifier (14-F33), and the entry appears on the list in its section.
- *Failure:* a pair is unpriced → the save is refused naming each one (01-F60), and the count beside the grid had said so before the press.

**Device revocation**
1. Owner marks a tablet stolen → confirm → `device.revoked`.
2. Cloud rejects its token immediately; hub flags it on LAN at next contact (01-F25).
3. Device list shows revoked state; the audit trail records actor and time.

**Signal-ownership change**
1. Owner moves "mark ready" from cashier to pass screen → preview shows affected surfaces and devices.
2. Confirm → `config.changed` → propagates to devices.
3. In-flight orders keep their current state machine; new orders use the new ownership — no ambiguous mid-order handoffs.

**Onboarding**
1. Vendor team + owner run the wizard over 1–2 sessions; recipe mapping happens in the doc 15 workbench in parallel.
2. Go-live checklist passes (14-F27) → tier defaults applied → first `day.opened` on POS.
- *Failure:* a checklist item regresses (printer dies before go-live) → the checklist re-blocks with the failing item named.

**Concurrent edits (failure path)**
- Two back-office users edit the same item → last-writer-wins by `server_received_at` with full audit (01-F18); the losing editor sees a non-blocking "newer change by X applied" notice with both versions in history. No other conflict class exists in this module (01-F20).

## 6. Non-functional requirements (module-specific)

- 14-N1 Config/catalog propagation visible on online devices ≤ 60 s (fast-path classes such as availability are explicitly not this module's concern, 01-F22).
- 14-N2 Responsive down to a phone browser: an owner can change a price or revoke a device from their phone; full editors (recipes, routing) target tablet/desktop.
- 14-N3 Catalog scale: 500 items × 4 variants with modifiers remains editable without pagination pain; a bulk price edit of 100 items completes < 10 s end-to-end.
- 14-N4 Wizard resumability survives session loss and browser change; no step re-entry loses entered data.

## 7. Customizability

This module is the layer-2 surface — §3 enumerates exactly which settings exist. Its own placement in the layers:
- **Layer 1 (doc 15):** which modules/tiers/channels are even visible here (feature gates); take-rate % (read-only here, 14-F20).
- **Layer 2:** everything in §3 — that is this module's purpose.
- **Layer 3 (device):** not set here, except the device detail page delegates device-layer settings (float, idle-lock) for convenience — recorded as that device's own config events.
- **Deliberately not configurable:** anything declared platform law in 01 §7; the permission matrix's hard rules (no role edits history — `restaurant-os.md` Appendix A); signal-ownership options beyond the designed role list; free-form roles, workflow states, or report builders; thresholds outside designed bounds.

## 8. Tech notes

- Next.js (00 §3), tRPC to api-gateway, no direct DB access; Playwright covers every §3 group including the full wizard run.
- Config is a versioned settings tree validated by Zod schemas in `packages/domain` — the same schemas devices use to validate received reference data; a setting without a schema cannot ship (build-time enforcement).
- Image upload direct-to-S3 with server-issued signed URLs; devices receive cached image references, not sync payloads.
- The onboarding wizard shares import/mapping components with doc 15's tooling (`packages/ui`, web side).
- Report rendering and export generation share the doc 12 server-side renderer — one implementation, two surfaces.

4. Whether tier downgrade (T3 → T2) needs a guided decommission flow for orphaned devices/stations, or archive-and-warn suffices.
5. Whether recipe editing should require a second confirmation when it changes theoretical cost by > 20% (fat-finger guard) — decide with doc 10 at build.
6. ~~Whether an owner assigned to a single branch should be able to revoke a device at that branch~~ **RULED (founder, August 2026): YES — a branch-scoped owner may revoke a device at their own branch.** `14-F30`'s cell was already `owner: allow`; what blocked it was mechanical rather than policy — neither device procedure states a `branch_id`, and the registry read happens *inside* the revocation, so a caller-stated branch would have been checked **after** the destructive act. The effective permission was therefore org-wide owner only, and an owner running one branch could not kill a stolen till without calling someone. **Widening is additive and safe; narrowing later would not be** — and the failure it removes is a live security one, since `01-F48` gives revocation a 30 s eviction budget that is worthless if nobody present is allowed to press it. **Code owed, and the ordering is the whole of it:** the device's `branch_id` must be read and checked against the caller's assignment **before** `revoked_at` is set, never after — a check that runs after the act authorizes nothing, and `01-F1` makes the act unremovable. `revokeDevice`'s existing behaviour for an org-wide owner is unchanged.
7. Which of the five `01-F21` kinds a Wave-1 owner actually needs a `14-F32` create task for — a single-branch restaurant may never author a choice group, and `14-F26`'s wizard is where that evidence arrives. Offering five tasks where three are used is the same clutter one form over.
8. The reorder gesture `14-F33` deliberately does not specify (drag on the list vs move up/down), and whether reordering several entries should take **one** `14-F28` timing choice rather than one per entry.
9. Whether a derived identifier should be re-derived on a rename **before** the entry has ever been published, when nothing yet references it. Frozen-from-creation is what `14-F33` specifies because it is the simpler rule to reason about; re-deriving is strictly kinder to an owner who mistypes a name and strictly harder to keep true.
10. ~~**How a person's first PIN is chosen and how it reaches her — BLOCKING**~~ **RULED (founder, August 2026, R29): THE OWNER SETS IT IN THE BACK OFFICE AND TELLS HER.** So an owner may simply **type** her cashier's PIN — the obvious reading of `14-F14`, and the reading `15-F27`'s *"a password is never an input"* does **not** forbid, because that clause binds the vendor→owner leg and nothing binds owner→staff. It matches how a small restaurant actually works, and `01-F61` already accepts the consequence by name: a 4-digit PIN is *"a convenience credential, not a secret"*, safe because it is paired with a registered device (`01-F25`/`01-F47`). It also avoids the alternative `28-F13` records as blocked twice over — `15-F26`'s single-use link has no redemption surface, and **no document in this corpus owns an outbound-mail capability**. **⚠ OWED BY THIS RULING AND NOT OPTIONAL: a change-my-PIN path at the till.** Without one the owner knows every cashier's PIN for ever, and `02-F41`'s attribution quietly means *"whoever the owner let in"* — which `01-F1` then makes permanent. That surface is this document's, and it is owed rather than specified: no FR yet gives it a screen, a permission cell or a place in the `01-F61` unlock flow. The neighbouring case is untouched and still open: an owner locked out has no reset path anywhere in the corpus (`28-F19`).
11. **The `user.changed` payload schema — owed, not open, and recorded here so it is not lost.** `14-F39` names the defect: the type is catalogued (`01 §4`) and has no payload schema, so `01-F4` refuses the emit and `14-F2`'s ledgered write of a user change cannot be built. The routing is settled by `28-F14`'s precedent — **this document declares the payload, doc 01 absorbs it** — and what stays genuinely open is its *content*: §2 lists create, role change and PIN reset with *"PINs … never present in payloads"*, and whether before/after assignment sets ride the payload or only the config version is undecided. Note the shipped precedent for the declaration's location before choosing: `device.revoked`'s payload is declared beside its emitter because `domain` ships no org-scoped schemas — follow it or state why not.
