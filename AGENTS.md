**IT IS NOW A CI RAIL: `pnpm seams:check`, inside `pnpm verify`.** Two rules, because the defect has two shapes and only one is a dead export. **Rule A — unreached export:** a value export no shipping code reaches, by a symbol-precise walk rooted at `apps/*/src` + `services/*/src` minus tests/stories; **a barrel re-export is not a use**, which is the hole `createPinSession` fell through. **Rule B — unsupplied seam:** an *optional* member of an options bag on a factory shipping code already calls, that no call site ever passes — instances 2 and 5, half the class by count, and `knip --production` cannot express it (`createSpooler` is imported, called, and its durable queue still dead). Carries `24-F14` empty-match protection: rename `apps/` and it hard-fails rather than passing vacuously. Exceptions are **in-code markers carrying a reason**, and a marker on something now reached FAILS — so the register cannot rot. Current state: **26 `@unreached-by-design`** (test-support, design-time math, drizzle-kit schema, deploy steps) and **44 `@unreached-owed` across 24 files**, printed on every clean run — an honest measure of how far the kernel runs ahead of its apps. **TWO THINGS IT CANNOT CATCH, both measured — do not read a clean run as total coverage.** (i) *Instance 3's shape*: a constant exported so a test **could** assert it, and none did. No reachability walk sees a missing assertion. (ii) **A PORT SUPPLIED WITH A STUB.** Measured on the publish adapter: replace the real gateway publisher with the in-memory stub and `pnpm verify` is exit 0, `seams:check` is **clean**, 111 of 116 API tests pass — and the product ships no menu to any till. Rule B asks whether an optional member is *supplied*, never whether what was supplied is *real*, and a stub is a supply. **Nor can it see a missing PRODUCER for an event type** — a key in an object literal is not an export, which is how `audit.print_acknowledged` sat in the registry with nothing emitting it. For all three, the assertion has to be written by hand; the rail narrows the surface, it does not close it.

**Two properties, and you need BOTH — measured, not argued.** Removing the store from the shipped construction failed **1 of 160** tests (the seam assertion, alone). Leaving the store in place but making its `put` a no-op failed 4 — **and the seam assertion stayed green.** So "a store was passed" and "the store durably works" are different claims: a seam test alone blesses a decorative object, and a durability suite alone blesses a subsystem nothing calls. What finds it: **mutate the SEAM, not the logic** — delete the call site and see whether anything reddens. If nothing does, the subsystem is decorative. **When you finish a subsystem, grep for its production caller before you call it done** — and prefer the grep over the suite as your closing evidence, because for this defect the suite passing proves nothing.

**⚠ TWO MERGE-TIME TRAPS WHEN A WORKTREE BRANCH LANDS.** (1) **A branch that adds a WORKSPACE DEPENDENCY needs `pnpm install` in the main repo after the merge.** The agent ran it in its worktree, so its numbers were real there; in the main tree the module does not resolve, one test FILE fails to load, and the count silently reads 121 where the branch reported 152 — with a `Cannot find module` that looks like a broken merge rather than an unlinked workspace. (2) **A single RED run is exactly as untrustworthy as a single green one.** `domain` read 4-failed under the parallel turbo run and 306/306 run alone; re-running the full suite gave 24/24. That is the documented subprocess-oracle flake, and it nearly got reported as a K-7 regression that did not exist. Re-run before believing a red, the same way you re-run before believing a green.

**⚠ A NEW GIT WORKTREE IS CREATED FROM A STALE BASE — CHECK IT BEFORE YOU WRITE A LINE.** Parallel agents each get their own worktree (isolation is what stops one capturing another's half-written files), but **both worktrees cut this session started behind HEAD — one by 14 commits, one by 96** — far enough back that the packages they were sent to implement barely existed and their own oracles had not been written. Both agents noticed and fast-forwarded; that was two independent strokes of diligence, not a property of the system. **First command in any worktree: `git log --oneline -1` and compare against the target branch; fast-forward if behind.** Implementing against a stale base produces a green suite that means nothing, because the tests you were sent to satisfy are not there. Setup cost is small — `pnpm install --prefer-offline` is ~4 s off pnpm's global store, and native addons work without a rebuild.

**⚠ NEVER `git add -A` WHILE AGENTS ARE RUNNING — STAGE EXPLICIT PATHS.** An orchestrator running parallel agents shares one working tree with all of them, so a blanket stage captures whatever every other agent happens to have half-written. It has already happened here: `8c03e4d`, whose message is entirely about the unlock oracle, also carries 132 lines of a *concurrent* session's `packages/escpos/src/__acceptance__/spooler-oracle-surface.ts` — **a protected path, committed under a message that does not mention it**, splitting that agent's work across a commit it did not make and an uncommitted remainder. Nothing was lost (the content was byte-identical), and it was caught only because the affected agent read the log and said so. `git add <explicit paths>`, and if a stray path appears in `git status` that your task did not touch, leave it: it belongs to someone still working. Corrections follow commandment 1's spirit — a new linked record naming the earlier commit, never a rewrite.

**⚠ MUTATION TESTING OF A SECURITY PARAMETER HAPPENS OUT-OF-TREE. NEVER IN-TREE.** The round-3 law makes mutation mandatory, and for a *security constant* the obvious way to run it — weaken the value, run the suite, revert — is unsafe here for a reason this repo has already demonstrated: **agents get killed mid-task** (three times in one session, at 1.3–1.7 h each), and one killed between "weaken" and "revert" leaves live weakened crypto in the working tree with every test green. A real instance: `PIN_ARGON2ID_PARAMS` was flagged at `m=8,t=1,p=1` by an automated scan while an agent was proving the `01-F61` cost floor actually bites; the tree was correct minutes later, and nothing but that scan's timing would have caught the other outcome. Copy the package to a scratchpad and mutate the copy — the same discipline every oracle author in this wave already used for implementation mutants. The rule is narrow on purpose: in-tree mutate-and-revert stays fine for ordinary logic, where a stranded mutation reds a test instead of silently downgrading a credential.

**Three standing laws every session must know (all now RATIFIED and shipped — the earlier "not yet implemented" warnings are retired):**
1. **The ordering design is per-fold merge semantics (`26`, `DEC-PERF-001`).** `01-F34`: folds declare explicit merge rules and read **no ordering metadata** — no `global_seq`, no `lamport_seq`, **no device clock**, no envelope-id comparison that reaches a projected VALUE. Tested by bijective id-relabel + clock-injection invariance; plain convergence testing is insufficient (a min-id tiebreak passes it while smuggling wall clock in through the UUIDv7 prefix). `global_seq` = delivery cursor + compaction watermark only. `causal_seq` remains refuted; `lamport_seq` keeps its gap-free transport/audit role. **This is the law most often broken by accident** — twice in the post-review round, each time by a projected value quietly depending on id sort order or on the reading device's state.
2. **Time is branch-consensus and stamped at APPEND (`01-F43..F46`, `DEC-TIME-001`).** Durations need a *consistent* clock, not a correct one. `branch_created_at` + `time_basis` travel INSIDE the event, because a fold applying its own offset would break law 1 silently. `device_created_at` is an untrusted forensic hint with exactly one sanctioned reader (`01-N2` skew detection). Branch time is continuous across hub re-election — the hub serves the clock, it does not define it. Business day = Asia/Karachi, 05:00 cutover (layer-2 configurable).
3. **Money is integers-in-a-double, and the double is the hazard.** Integer paisas only; rates as integer basis points; `splitPaisa`/`applyRateBps` for division and rates (`DEC-MONEY-005`). Folds accumulate in **BigInt** — float `+` is non-associative near 2^53, so a running double total lets delivery order decide a money outcome (a live law-1 break, not a theoretical range concern). A total that cannot be represented exactly contributes **zero** and raises `money_overflow`; never truncate, never throw on the ingest path (`01-F17`). The GritQL ban covers bare identifiers **and** money-named member expressions incl. `as` casts — comparisons and plain assignment stay legal on purpose.

## Commandments (always binding; each is also machine-enforced — violating code fails CI regardless of what you read)

1. **Append-only ledger.** Never mutate or delete history; corrections are new linked events (`01`).
2. **Never invent events, states, or policy.** Event types live in the `01 §4` catalog; order states in `01 §4` only. If the spec doesn't cover your case: STOP → check `specs/DECISIONS.md` → propose a spec change. Do not fill gaps with plausible behavior. **Any policy you assert must cite an FR ID that resolves** (`grep -rn "02-F9" specs/`) — an ID that greps to nothing means you invented it.
3. **Money = integer paisas; quantities = integer mg/ml/units.** Branded types from `domain`; floats in ledgers never (`00 §6`).
4. **Offline-first.** No in-branch feature may require WAN; confirmed = locally persisted before UI ack (`00 §5.1–5.2`). A sale is never blocked — not by inventory math, sync, or approval timeouts (`01-F17`, `05-F8`).
5. **Two-plane law.** Operational screens: `sync-client` reads/writes only. Cloud screens: tRPC + TanStack Query only. Never mixed silently (`18 §6`).
6. **UI = closed vocabulary.** `packages/ui` semantic components only; no raw primitives, no Tailwind arbitrary values in app code (`21 §2`).
7. **English-only UI; user content is Unicode** and renders/prints faithfully (`00 §5.6`).
8. **Server-side authorization always** via the `domain` permission matrix; client role claims are never trusted (`18 §5`).
9. **Spec change before behavior change.** Behavior-carrying code changes cite their FR ID (e.g. `02-F9`) in tests/commits; no matching FR = write the spec PR first (`20 §4.1`).
10. **Protected paths need senior review:** `domain`, `sync-client`, `sync-protocol`, `escpos`, tax, auth (`20 §4.4`).

## Working rules

- One module per session; load only the routed docs (a task needs ~2–4 specs, not the corpus).
- Build tasks follow the `24 §3` loop: approved plan → acceptance tests exist first (written by a different session; read-only to you) → implement → the named check passes → evidence (captured command output) in your final message. **"Done" is the check passing — never your own judgment.**
- Craft rules (`24 §3b`): **surface assumptions in the plan** (ambiguous task → state interpretations, name the simpler alternative — don't silently pick); **minimum code that closes the FR** (no speculative features, flexibility, or error handling for implausible cases); **surgical diffs** (touch only the task's files; never "improve" adjacent code — cleanup is scheduled consolidation work, not a drive-by).
- Editing a spec: follow the template in `00 §8`; new FRs continue the doc's numbering; never renumber or delete existing IDs.
- New event types / states / config keys: spec PR to the owning doc **and** `01 §4` / `00 §7` first, code second.
- Anything here that seems to conflict with a spec: the spec wins — and flag the drift so this file gets fixed.
