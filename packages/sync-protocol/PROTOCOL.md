# Wire protocol design (24-F8 artifact for spec 01 — implementation follows in T-01-02)

Transport: WebSocket (cloud + LAN, one framing), JSON messages, permessage-deflate. Every message: `{ v: 2, kind, ...body }` (`01-F77` — see the breaking-change note below; `v: 1` is REFUSED, and the refusal names the version this build speaks). Idempotency: event `id` dedupes everywhere (01-F8); no message requires ordered delivery beyond per-device `lamport_seq`.

**THE REFERENCE-DATA GENERALISATION IS A BREAKING CHANGE AND IS THE FIRST `v` BUMP (`01-F75`..`01-F77`; IMPLEMENTED August 2026).** Removing three kinds is not additive, so the rule this document already states applies without interpretation: `v: 1` → `v: 2`, with an N−1 reader (`00 §6`). ⚠ **THE N−1 READER IS DEFERRED, NOT WITHDRAWN, AND NOTHING BELOW IS BUILT (`01-F77`, founder ruling).** R4 puts nothing in the field — no deployment has ever run `v: 1` — so a reader, three retained fixtures and their tests would be a compatibility target that does not exist, which is the speculative work `24 §3b` forbids by name. What SHIPS today is one version the whole system moves in: a `v: 1` frame is REFUSED, and the refusal names `v: 2` rather than reporting an unknown kind, because telling an operator mid-rollout the wrong thing about which end to look at is `00 §5.7`'s failure. What is OWED, before the first pilot device is paired, is everything in the rest of this paragraph. Concretely: the server keeps a `v: 1` reader for **exactly one version**, so a device on the old build asks with the catalog triple, is answered on it, keeps its menu and goes on selling (`01-F17`) — and receives **no roster**, because it has no frame that could carry one. Retiring the `v: 1` reader is its own spec act. **⚠ A READER IS NOT ENOUGH AND THIS CODEC MAKES THAT CONCRETE:** `PROTOCOL_VERSION` is one shared `z.literal` on every kind, so a gateway that parses a `v: 1` `hello` and answers `v: 2` is rejected by the old device's own literal — no session, therefore no `push_ack`, therefore an outbox that never drains (`19 §5`). The version is **negotiated per session from `hello.v` and the server encodes at the session's version**, which makes a `v: 1` WRITER part of the deliverable and makes this a codec change rather than a constant edit (`01-F77`). Deployment order follows: **server first, then devices** — a `v: 2` device against a `v: 1` gateway gets no session at all. **`20 §2.7` is the review gate and the fixtures are the deliverable — stated precisely, because the obvious phrasing points at the wrong files:** the three catalog fixtures are **FROZEN at `v: 1` for as long as the N−1 reader lives**, since they are the committed record of what an old device actually sends and regenerating them deletes the only artifact pinning that leg — and that reader does not live yet, so as of August 2026 the three files are DELETED and land again with it. The deliverable is **SIX new `reference_*` fixtures** — both resources on all three kinds, because a frame family pinned by one resource is a family whose discriminator is exercised by nothing — the `v: 2` fixtures the bump requires for every other kind carrying `v` (including `purge_command`, which had never had one), `01-F79`'s pair, and a transcript per direction of the nightly matrix (`fixtures/transcripts/` already holds that shape; the N−1 direction is owed WITH the reader, since a transcript of a version nothing speaks pins nothing) — which is precisely the event `fixtures.test.ts` says requires a spec review of `01 §8` and this file, and it is why the FRs landed before any of this exists in `messages.ts`. `purge_command`'s row above already states the standing rule this obeys: **the message set is closed**, and a kind is added or removed by spec, never by an implementation. Nightly both directions of `20 §2.7`'s matrix (client N−1 vs server N and the reverse) are what make the paragraph a tested claim. ⚠ **No deployment holds field state** (`plans/saas-pivot/plan-of-record.md` R4), so the N−1 reader is here because a staged rollout is by construction a mixed fleet — a reason to make it cheap, never a reason to skip it.

LAN vs cloud: identical message set; hub relays `push` upward and fans `event_batch` branch-wide (01-F13). Slice predicates (waiter/rider classes) are enforced at the sender (hub or cloud), never client-declared. Schema evolution: additive within a version; breaking bumps `v` with an N−1 reader (00 §6). The first such bump is `01-F77`'s `v: 1` → `v: 2`.

**Compressed framing (additive under `v: 1`; T-01-16, 01 §5 "JSON + zstd batch compression", DEC-SYNC-010 **accepted**).** A frame MAY be carried as zstd-compressed bytes instead of the plain JSON text — `encodeCompressed`/`decodeCompressed` are exactly `zstd(utf8(JSON))` and `JSON.parse(utf8(unzstd(bytes)))` over the identical message body, so compression is **transparent**: the decoded message deep-equals the plain-codec message for every `kind`, no field or semantics change, and folds/consumers see identical events (26 §6.4 — the catch-up transfer is part of the <60 s/4G budget, not an optimisation). The plain JSON codec is unchanged (T-01-02 golden fixtures do not drift); the compressed pair is a separate, additive framing. The compressed frame carries a **zstd content checksum** (`ZSTD_c_checksumFlag`, +4 bytes; close-now follow-up audit-1 #D): a plain zstd frame has no integrity check, so a single-byte-corrupted frame could decompress to a schema-valid but *wrong* message that `decodeCompressed` would return as real — with the checksum, decompression of a corrupted frame **fails loudly** (checksum mismatch → throw) rather than silently mis-parsing. The decoder auto-detects the flag from the frame header (additive). zstd is Node's built-in (`node:zlib`, 18 §14).

**Negotiation (T-01-19; DEC-SYNC-010 accepted).** Which framing a connection uses is negotiated **per connection, at `hello`/`hello_ack`, opt-in from both ends**: `hello` carries `accepts_compression?: boolean`, and `hello_ack` answers `compression?: "zstd"` — granted iff the client advertised **and** the server accepts. Absent means plain JSON for the life of that connection. Both handshake messages are themselves **always plain**: `hello` is what establishes what the peer can read, and the `hello_ack` crosses the wire while the client's decoder is still plain. Support comes from the negotiated contract and **never** from sniffing the zstd magic number — a peer that can decode a frame today may not after a rollback, and content-derived framing would make the wire format depend on the message rather than the agreement. A peer that does not advertise therefore receives plain JSON forever, which is the property that matters: a newly-deployed gateway can never send frames an un-updated device cannot parse, and in this product that failure is a counter terminal that silently stops receiving orders.

**Scope: the CLOUD connection only.** The LAN mesh does not negotiate compression and never advertises it. Two reasons, both decisive. (a) The budget this exists for is the **cloud** catch-up transfer (`26 §6.4`, <60 s on 4G); LAN propagation is shop-grade Wi-Fi at <1 s p95 (`01-F15`), where compression buys nothing worth a wire change. (b) The LAN transport wraps every message in a JSON envelope (`{ t: "wire" | "announce", message }`) whose discriminant lives *inside* the JSON, so a compressed LAN payload would need either a new binary frame variant or base64 inside the wrapper — the first is a spec-reviewed protocol change, the second throws away most of the gain. Compressing the LAN would be speculative work against a budget that is not under pressure (`24 §3b`). If a LAN transfer budget ever binds, that is its own spec change.
