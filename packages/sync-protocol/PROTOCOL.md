# Wire protocol design (24-F8 artifact for spec 01 — implementation follows in T-01-02)

Transport: WebSocket (cloud + LAN, one framing), JSON messages, permessage-deflate. Every message: `{ v: 1, kind, ...body }`. Idempotency: event `id` dedupes everywhere (01-F8); no message requires ordered delivery beyond per-device `lamport_seq`.

| kind | direction | body | notes |
|---|---|---|---|
| `hello` | device → hub/cloud | `{ device_id, device_class, branch_id, token, last_global_seq, own_high_water }` | auth + resume point; server validates class/slice (01-F40) |
| `hello_ack` | ← | `{ session_id, hub: bool, resume_from, relay_authorized?, catalog_version? }` | **Additive (DEC-SYNC-009):** `relay_authorized: true` advertises the hub-relay GRANT. **Clarified (T-01-09, implemented):** the grant is composed server-side — the token's `hub_relay` claim AND an unrevoked registry row whose device_class is hub-eligible (01-F13/01-F39); the claim alone grants nothing (registry veto), registry eligibility alone grants nothing (claim required, 18 §5). Absent otherwise; a device must not push third-party events on a session that was not advertised — an unadvertised relay attempt quarantines `device_mismatch` **Additive (T-C1):** `catalog_version` is the org's current authoritative catalog version and is **the correctness mechanism of the whole catalog transport** — the device compares it against its own and fetches if behind, so every reconnection reconciles and the `catalog_notice` push is pure latency on top. Omitted (never sent as `0`) when the org has published nothing, so that case is indistinguishable from an older gateway serving no catalog: in both the device simply never asks, which is right for both. |
| `push` | device → | `{ events: Envelope[], watermark: lamport_seq }` | own events, lamport order (01-F8). **DEC-SYNC-009 (implemented, T-01-12):** a session whose token carries the hub-relay capability may also push events whose `device_id` is a same-org/branch WAN-less peer's — relayed verbatim, attested not re-authored (01-F1); the cloud tracks lamport contiguity per ORIGIN device and `watermark` is per-origin. One origin per relay push message (the scalar ack below answers that origin). Additive under `v:1` |
| `push_ack` | ← | `{ acked_watermark, origin_device_id? }` | device advances outbox only on ack (write-checkpoint, 19 §5). **Additive (DEC-SYNC-009):** `origin_device_id` is present iff the ack answers a relay push — it names the ORIGIN device whose stream `acked_watermark` describes. The same shape carries the relayed CLOUD ack hub→origin over LAN (`origin_device_id` = the receiving origin's id); that relayed cloud ack is the ONLY LAN `push_ack` that may move the origin's cloud write-checkpoint — the plain LAN hub ack stays session-local and volatile (19 §5) |
| `event_batch` | hub/cloud → device | `{ events: (Envelope & { global_seq?: int })[] }` | merged stream, slice-filtered per class (01-F39/F40); `global_seq` present once cloud-assigned (01-F3) |
| `catchup_request` | device → | `{ from_global_seq }` | range fetch (01-F9) |
| `catchup_response` | ← | `{ events, complete: bool, next_from }` | paged |
| `quarantine_notice` | → origin device | `{ event_id, reason }` | 01-F37 — event excluded from folds; correction flow is operator-side. **Clarified (T-01-08, DEC-SYNC-008/DEC-SYNC-009):** the cloud live-sends to the PUSHING session and durably redelivers on the origin's next own `hello`; when the pusher was a relaying hub, the hub forwards the notice over the LAN to the WAN-less origin (same body, at-least-once — duplicates legal). No new kind or field; additive under `v: 1` |
| `purge_command` | → device | `{ scope }` | revocation (01-F42); device wipes local DB and re-registers (fresh device_id — 01-N5 cold-start path). **Clarified (T-01-09, implemented):** no purge-ack wire kind exists (the message set stays closed) — delivery is at-least-once by re-send: a revoked device's EVERY hello gets `purge_command { scope: "all" }` and no session (AuthRejectedError); on an already-open session revocation binds on the next operation as a rejection, never a quarantine |
| `catalog_request` | device → | `{ have_version, from?, at_version? }` | **T-C1 (additive under `v: 1`; `01-F9` "plus org-scope reference data", `01-F52`..`01-F56`).** ORG-scoped, not branch-scoped — the catalog is the one thing a device reads that is not branch-filtered, which is why it needed a frame pair of its own rather than riding the merged stream. `have_version` is what the device holds (`0` = nothing, gets a snapshot). `from` is the paging cursor, echoed from `catalog_response.next_from`. `at_version` is the version a CONTINUATION page is toward, echoed from page 1 — **required on every continuation**: without it the server re-reads the current version per page, so a publish landing mid-fetch changes both the version and the ordering the offset indexes into, and the device commits a mixture of two menus under one number (`01-F56`, and it is silent and permanent) |
| `catalog_response` | ← | `{ form: "snapshot" \| "delta", version, base_version?, entries[], complete, next_from }` | The SERVER decides snapshot vs delta from `have_version`: a delta if it can construct one from that exact base, a snapshot otherwise (including `have_version: 0` and a base too old to reconstruct). The device's `needs_snapshot` refusal is the belt to that braces. Paging copies `catchup_response`'s vocabulary rather than inventing a second idiom. **A snapshot applies ATOMICALLY** — pages accumulate on the device and commit on `complete`, because a till holding half a menu mid-service is worse than one holding none. `entries[].deleted` is a TOMBSTONE (`01-F55`): a delete travels as a MARKED ENTRY, never as an absence, so a reprint of an order placed before the deletion still renders the name |
| `catalog_notice` | → device (org-scoped) | `{ version }` | **Freshness only, never correctness.** The system is correct if every one of these is dropped: `hello_ack.catalog_version` is what actually reconciles, on every reconnection, including for a device offline a week that could not have heard an announcement. This exists so a menu edit does not wait for the next reconnect, and nothing is allowed to depend on it arriving — which is the property that matters, because a notice is exactly the kind of message a lossy link loses |
| `ping` / `pong` | both | `{ t }` | liveness for hub election (HUB-ELECTION.md) |

LAN vs cloud: identical message set; hub relays `push` upward and fans `event_batch` branch-wide (01-F13). Slice predicates (waiter/rider classes) are enforced at the sender (hub or cloud), never client-declared. Schema evolution: additive under `v: 1`; breaking bumps `v` with an N−1 reader (00 §6).

**Compressed framing (additive under `v: 1`; T-01-16, 01 §5 "JSON + zstd batch compression", DEC-SYNC-010 **accepted**).** A frame MAY be carried as zstd-compressed bytes instead of the plain JSON text — `encodeCompressed`/`decodeCompressed` are exactly `zstd(utf8(JSON))` and `JSON.parse(utf8(unzstd(bytes)))` over the identical message body, so compression is **transparent**: the decoded message deep-equals the plain-codec message for every `kind`, no field or semantics change, and folds/consumers see identical events (26 §6.4 — the catch-up transfer is part of the <60 s/4G budget, not an optimisation). The plain JSON codec is unchanged (T-01-02 golden fixtures do not drift); the compressed pair is a separate, additive framing. The compressed frame carries a **zstd content checksum** (`ZSTD_c_checksumFlag`, +4 bytes; close-now follow-up audit-1 #D): a plain zstd frame has no integrity check, so a single-byte-corrupted frame could decompress to a schema-valid but *wrong* message that `decodeCompressed` would return as real — with the checksum, decompression of a corrupted frame **fails loudly** (checksum mismatch → throw) rather than silently mis-parsing. The decoder auto-detects the flag from the frame header (additive). zstd is Node's built-in (`node:zlib`, 18 §14).

**Negotiation (T-01-19; DEC-SYNC-010 accepted).** Which framing a connection uses is negotiated **per connection, at `hello`/`hello_ack`, opt-in from both ends**: `hello` carries `accepts_compression?: boolean`, and `hello_ack` answers `compression?: "zstd"` — granted iff the client advertised **and** the server accepts. Absent means plain JSON for the life of that connection. Both handshake messages are themselves **always plain**: `hello` is what establishes what the peer can read, and the `hello_ack` crosses the wire while the client's decoder is still plain. Support comes from the negotiated contract and **never** from sniffing the zstd magic number — a peer that can decode a frame today may not after a rollback, and content-derived framing would make the wire format depend on the message rather than the agreement. A peer that does not advertise therefore receives plain JSON forever, which is the property that matters: a newly-deployed gateway can never send frames an un-updated device cannot parse, and in this product that failure is a counter terminal that silently stops receiving orders.

**Scope: the CLOUD connection only.** The LAN mesh does not negotiate compression and never advertises it. Two reasons, both decisive. (a) The budget this exists for is the **cloud** catch-up transfer (`26 §6.4`, <60 s on 4G); LAN propagation is shop-grade Wi-Fi at <1 s p95 (`01-F15`), where compression buys nothing worth a wire change. (b) The LAN transport wraps every message in a JSON envelope (`{ t: "wire" | "announce", message }`) whose discriminant lives *inside* the JSON, so a compressed LAN payload would need either a new binary frame variant or base64 inside the wrapper — the first is a spec-reviewed protocol change, the second throws away most of the gain. Compressing the LAN would be speculative work against a budget that is not under pressure (`24 §3b`). If a LAN transfer budget ever binds, that is its own spec change.
