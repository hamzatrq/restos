# Wire protocol design (24-F8 artifact for spec 01 — implementation follows in T-01-02)

Transport: WebSocket (cloud + LAN, one framing), JSON messages, permessage-deflate. Every message: `{ v: 1, kind, ...body }`. Idempotency: event `id` dedupes everywhere (01-F8); no message requires ordered delivery beyond per-device `lamport_seq`.

| kind | direction | body | notes |
|---|---|---|---|
| `hello` | device → hub/cloud | `{ device_id, device_class, branch_id, token, last_global_seq, own_high_water }` | auth + resume point; server validates class/slice (01-F40) |
| `hello_ack` | ← | `v: 1` — `{ session_id, hub: bool, resume_from, relay_authorized?, catalog_version? }` · `v: 2` — `{ session_id, hub: bool, resume_from, relay_authorized?, reference_versions?: { resource, scope, version }[] }` (`01-F77`, spec'd not implemented) | **Additive (DEC-SYNC-009):** `relay_authorized: true` advertises the hub-relay GRANT. **Clarified (T-01-09, implemented):** the grant is composed server-side — the token's `hub_relay` claim AND an unrevoked registry row whose device_class is hub-eligible (01-F13/01-F39); the claim alone grants nothing (registry veto), registry eligibility alone grants nothing (claim required, 18 §5). Absent otherwise; a device must not push third-party events on a session that was not advertised — an unadvertised relay attempt quarantines `device_mismatch` **Additive (T-C1):** `catalog_version` is the org's current authoritative catalog version and is **the correctness mechanism of the whole catalog transport** — the device compares it against its own and fetches if behind, so every reconnection reconciles and the `catalog_notice` push is pure latency on top. Omitted (never sent as `0`) when the org has published nothing, so that case is indistinguishable from an older gateway serving no catalog: in both the device simply never asks, which is right for both. **Amended August 2026 (`01-F76`/`01-F77`, spec'd not implemented):** `catalog_version` is **superseded by `reference_versions`** — an ARRAY of `{ resource, scope, version }`, one number per `01-F76` artifact key, because a version means nothing without the artifact it counts. An array and not a map, since a map key over two fields is the concatenation `01-F76` bans. The two are never both authoritative on one session: a `v: 1` session reads `catalog_version` and nothing else, a `v: 2` session reads `reference_versions` and nothing else. `catalog_version` is retained for exactly as long as the N−1 reader is. **`catalog_version`'s omitted-never-zero rule survives per key:** an artifact the org has published nothing for is omitted rather than sent as `0`, so it is indistinguishable from a gateway that does not serve that resource — in both the device never asks, which is right for both. **What must NOT change is what this field IS** — the correctness mechanism of the whole reference-data transport, per artifact now rather than for the menu alone. |
| `push` | device → | `{ events: Envelope[], watermark: lamport_seq }` | own events, lamport order (01-F8). **DEC-SYNC-009 (implemented, T-01-12):** a session whose token carries the hub-relay capability may also push events whose `device_id` is a same-org/branch WAN-less peer's — relayed verbatim, attested not re-authored (01-F1); the cloud tracks lamport contiguity per ORIGIN device and `watermark` is per-origin. One origin per relay push message (the scalar ack below answers that origin). Additive under `v:1` |
| `push_ack` | ← | `{ acked_watermark, origin_device_id? }` | device advances outbox only on ack (write-checkpoint, 19 §5). **Additive (DEC-SYNC-009):** `origin_device_id` is present iff the ack answers a relay push — it names the ORIGIN device whose stream `acked_watermark` describes. The same shape carries the relayed CLOUD ack hub→origin over LAN (`origin_device_id` = the receiving origin's id); that relayed cloud ack is the ONLY LAN `push_ack` that may move the origin's cloud write-checkpoint — the plain LAN hub ack stays session-local and volatile (19 §5) |
| `event_batch` | hub/cloud → device | `{ events: (Envelope & { global_seq?: int })[] }` | merged stream, slice-filtered per class (01-F39/F40); `global_seq` present once cloud-assigned (01-F3) |
| `catchup_request` | device → | `{ from_global_seq }` | range fetch (01-F9) |
| `catchup_response` | ← | `{ events, complete: bool, next_from }` | paged |
| `quarantine_notice` | → origin device | `{ event_id, reason }` | 01-F37 — event excluded from folds; correction flow is operator-side. **Clarified (T-01-08, DEC-SYNC-008/DEC-SYNC-009):** the cloud live-sends to the PUSHING session and durably redelivers on the origin's next own `hello`; when the pusher was a relaying hub, the hub forwards the notice over the LAN to the WAN-less origin (same body, at-least-once — duplicates legal). No new kind or field; additive under `v: 1` |
| `purge_command` | → device | `{ scope }` | revocation (01-F42); device wipes local DB and re-registers (fresh device_id — 01-N5 cold-start path). **Clarified (T-01-09, implemented):** no purge-ack wire kind exists (the message set stays closed) — delivery is at-least-once by re-send: a revoked device's EVERY hello gets `purge_command { scope: "all" }` and no session (AuthRejectedError); on an already-open session revocation binds on the next operation as a rejection, never a quarantine |
| `reference_request` | device → | `{ resource, scope, have_version, from?, at_version? }` | **`01-F75` (spec'd August 2026, NOT yet implemented; `v: 2`, see the breaking-change note below).** The ONE reference-data request, for every resource. `resource` is the closed set `01-F75` declares — `catalog` and `staff` today, and adding a member is a spec act plus a fixture, never an implementer's choice. `scope` is `01-F76`'s artifact scope, **structured and never a concatenation** (`01-F71` (d)): `{ org_id, branch_id }` with `branch_id: null` meaning org scope — ONE shape for every resource, so no reader switches on `resource` to parse the key it is about to be authorized against. Org for `catalog`, branch for `staff`. ⚠ **THE SERVER DERIVES THE KEY FROM THE SESSION AND REFUSES A REQUEST THAT STATES ANOTHER** (`01-F71` (e)) — never clamps it to the session's own. This is the first frame that puts a tenant key in bytes a caller controls (`catalog_request` carried no tenant at all and the org was read from the session), and under R25 the roster's scope IS its credential blast radius, so a device free to name a branch defeats the ruling in one field. The device-side refusal below is the belt to that brace, never a substitute for it (commandment 8). `have_version`, `from` and `at_version` are `catalog_request`'s fields unchanged, and every word of their reasoning below survives — `at_version` is still **required on every continuation**, because a publish landing mid-fetch is what makes a device commit a mixture of two artifacts under one number, silently and permanently (`01-F56`) |
| `reference_response` | ← | `{ resource, scope, form, version, base_version?, entries[], complete, next_from }` | **`01-F75`/`01-F76`.** `catalog_response`'s body plus the artifact key, which the response **echoes** so the device can refuse an artifact that is not its own (`01-F76`: a roster scoped to another branch is refused and never applied, under its own named reason **`foreign_artifact`** — a foreign key is not a `malformed` row and reporting it as one would tell a fleet dashboard a writer is emitting bad data when what happened is a routing failure). A version number is meaningful only against `(resource, scope)` — a device holds one version PER KEY. `entries[]` is typed **per resource** and validated at the writer (`01-F75`), never only at the device — the `staff` row is `user_id`, `display_name` (required), `grid_ordinal`, `status`, `assignments`, and `pin_hash` **only on an `active` member**, where a missing hash on a non-`active` member is the specified shape and never `malformed`. `form: "delta"` requires the resource's store to keep a version axis; the cloud's user table has none today, so `staff` answers `snapshot` only until one is built (`01-F75`). Snapshot atomicity, paging vocabulary and the server-decides-snapshot-vs-delta rule are `catalog_response`'s, unchanged. **No removals list, for any resource:** a departure travels as a MARKED ENTRY — the catalog's tombstone (`01-F55`) and, for `staff`, `11-F22`'s status, which decides whether a PIN verifies and decides nothing about whether a past order renders her name |
| `reference_notice` | → device (scoped) | `{ resource, scope, version }` | **`01-F75`.** Freshness only, never correctness — `catalog_notice`'s property generalised, and the one thing that must not be lost in the generalisation: the system is correct if every one of these is dropped, because `hello_ack`'s per-artifact versions are what reconcile on every reconnection. A design that delivers a roster only on a pushed notice gives you a till nobody can sign in to after a lossy week (`01-F17` arriving through the identity path). Fan-out is keyed by the artifact key, so a branch-scoped notice reaches that branch's devices and no others |
| ~~`catalog_request`~~ | device → | `{ have_version, from?, at_version? }` | **SUPERSEDED by `reference_request` (`01-F75`), retained for the `v: 1` N−1 reader only (`01-F77`).** **T-C1 (additive under `v: 1`; `01-F9` "plus org-scope reference data", `01-F52`..`01-F56`).** ORG-scoped, not branch-scoped — the catalog is the one thing a device reads that is not branch-filtered, which is why it needed a frame pair of its own rather than riding the merged stream. `have_version` is what the device holds (`0` = nothing, gets a snapshot). `from` is the paging cursor, echoed from `catalog_response.next_from`. `at_version` is the version a CONTINUATION page is toward, echoed from page 1 — **required on every continuation**: without it the server re-reads the current version per page, so a publish landing mid-fetch changes both the version and the ordering the offset indexes into, and the device commits a mixture of two menus under one number (`01-F56`, and it is silent and permanent) |
| ~~`catalog_response`~~ | ← | `{ form: "snapshot" \| "delta", version, base_version?, entries[], complete, next_from }` | **SUPERSEDED by `reference_response` (`01-F75`), retained for the `v: 1` N−1 reader only (`01-F77`).** The SERVER decides snapshot vs delta from `have_version`: a delta if it can construct one from that exact base, a snapshot otherwise (including `have_version: 0` and a base too old to reconstruct). The device's `needs_snapshot` refusal is the belt to that braces. Paging copies `catchup_response`'s vocabulary rather than inventing a second idiom. **A snapshot applies ATOMICALLY** — pages accumulate on the device and commit on `complete`, because a till holding half a menu mid-service is worse than one holding none. `entries[].deleted` is a TOMBSTONE (`01-F55`): a delete travels as a MARKED ENTRY, never as an absence, so a reprint of an order placed before the deletion still renders the name |
| ~~`catalog_notice`~~ | → device (org-scoped) | `{ version }` | **SUPERSEDED by `reference_notice` (`01-F75`), retained for the `v: 1` N−1 reader only (`01-F77`).** **Freshness only, never correctness.** The system is correct if every one of these is dropped: `hello_ack.catalog_version` is what actually reconciles, on every reconnection, including for a device offline a week that could not have heard an announcement. This exists so a menu edit does not wait for the next reconnect, and nothing is allowed to depend on it arriving — which is the property that matters, because a notice is exactly the kind of message a lossy link loses |
| `ping` / `pong` | both | `{ t }` | liveness for hub election (HUB-ELECTION.md) |

**THE REFERENCE-DATA GENERALISATION IS A BREAKING CHANGE AND IS THE FIRST `v` BUMP (`01-F75`..`01-F77`; spec'd August 2026, not yet implemented).** Removing three kinds is not additive, so the rule this document already states applies without interpretation: `v: 1` → `v: 2`, with an N−1 reader (`00 §6`). Concretely: the server keeps a `v: 1` reader for **exactly one version**, so a device on the old build asks with the catalog triple, is answered on it, keeps its menu and goes on selling (`01-F17`) — and receives **no roster**, because it has no frame that could carry one. Retiring the `v: 1` reader is its own spec act. **⚠ A READER IS NOT ENOUGH AND THIS CODEC MAKES THAT CONCRETE:** `PROTOCOL_VERSION` is one shared `z.literal` on every kind, so a gateway that parses a `v: 1` `hello` and answers `v: 2` is rejected by the old device's own literal — no session, therefore no `push_ack`, therefore an outbox that never drains (`19 §5`). The version is **negotiated per session from `hello.v` and the server encodes at the session's version**, which makes a `v: 1` WRITER part of the deliverable and makes this a codec change rather than a constant edit (`01-F77`). Deployment order follows: **server first, then devices** — a `v: 2` device against a `v: 1` gateway gets no session at all. **`20 §2.7` is the review gate and the fixtures are the deliverable — stated precisely, because the obvious phrasing points at the wrong files:** the three catalog fixtures are **FROZEN at `v: 1` for as long as the N−1 reader lives**, since they are the committed record of what an old device actually sends and regenerating them deletes the only artifact pinning that leg. The deliverable is **three NEW `reference_*` fixtures**, the `v: 2` fixtures the bump requires for every other kind carrying `v`, and a transcript per direction of the nightly matrix (`fixtures/transcripts/` already holds that shape) — which is precisely the event `fixtures.test.ts` says requires a spec review of `01 §8` and this file, and it is why the FRs landed before any of this exists in `messages.ts`. `purge_command`'s row above already states the standing rule this obeys: **the message set is closed**, and a kind is added or removed by spec, never by an implementation. Nightly both directions of `20 §2.7`'s matrix (client N−1 vs server N and the reverse) are what make the paragraph a tested claim. ⚠ **No deployment holds field state** (`plans/saas-pivot/plan-of-record.md` R4), so the N−1 reader is here because a staged rollout is by construction a mixed fleet — a reason to make it cheap, never a reason to skip it.

LAN vs cloud: identical message set; hub relays `push` upward and fans `event_batch` branch-wide (01-F13). Slice predicates (waiter/rider classes) are enforced at the sender (hub or cloud), never client-declared. Schema evolution: additive under `v: 1`; breaking bumps `v` with an N−1 reader (00 §6).

**Compressed framing (additive under `v: 1`; T-01-16, 01 §5 "JSON + zstd batch compression", DEC-SYNC-010 **accepted**).** A frame MAY be carried as zstd-compressed bytes instead of the plain JSON text — `encodeCompressed`/`decodeCompressed` are exactly `zstd(utf8(JSON))` and `JSON.parse(utf8(unzstd(bytes)))` over the identical message body, so compression is **transparent**: the decoded message deep-equals the plain-codec message for every `kind`, no field or semantics change, and folds/consumers see identical events (26 §6.4 — the catch-up transfer is part of the <60 s/4G budget, not an optimisation). The plain JSON codec is unchanged (T-01-02 golden fixtures do not drift); the compressed pair is a separate, additive framing. The compressed frame carries a **zstd content checksum** (`ZSTD_c_checksumFlag`, +4 bytes; close-now follow-up audit-1 #D): a plain zstd frame has no integrity check, so a single-byte-corrupted frame could decompress to a schema-valid but *wrong* message that `decodeCompressed` would return as real — with the checksum, decompression of a corrupted frame **fails loudly** (checksum mismatch → throw) rather than silently mis-parsing. The decoder auto-detects the flag from the frame header (additive). zstd is Node's built-in (`node:zlib`, 18 §14).

**Negotiation (T-01-19; DEC-SYNC-010 accepted).** Which framing a connection uses is negotiated **per connection, at `hello`/`hello_ack`, opt-in from both ends**: `hello` carries `accepts_compression?: boolean`, and `hello_ack` answers `compression?: "zstd"` — granted iff the client advertised **and** the server accepts. Absent means plain JSON for the life of that connection. Both handshake messages are themselves **always plain**: `hello` is what establishes what the peer can read, and the `hello_ack` crosses the wire while the client's decoder is still plain. Support comes from the negotiated contract and **never** from sniffing the zstd magic number — a peer that can decode a frame today may not after a rollback, and content-derived framing would make the wire format depend on the message rather than the agreement. A peer that does not advertise therefore receives plain JSON forever, which is the property that matters: a newly-deployed gateway can never send frames an un-updated device cannot parse, and in this product that failure is a counter terminal that silently stops receiving orders.

**Scope: the CLOUD connection only.** The LAN mesh does not negotiate compression and never advertises it. Two reasons, both decisive. (a) The budget this exists for is the **cloud** catch-up transfer (`26 §6.4`, <60 s on 4G); LAN propagation is shop-grade Wi-Fi at <1 s p95 (`01-F15`), where compression buys nothing worth a wire change. (b) The LAN transport wraps every message in a JSON envelope (`{ t: "wire" | "announce", message }`) whose discriminant lives *inside* the JSON, so a compressed LAN payload would need either a new binary frame variant or base64 inside the wrapper — the first is a spec-reviewed protocol change, the second throws away most of the gain. Compressing the LAN would be speculative work against a budget that is not under pressure (`24 §3b`). If a LAN transfer budget ever binds, that is its own spec change.
